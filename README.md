# Watchgoose

**Централизованный приём логов, метрик и трейсов с накоплением разборов
инцидентов.**

</div>

---

## Что это

Сервис принимает телеметрию по OTLP, хранит логи в Manticore, трейсы
в ClickHouse, метрики в VictoriaMetrics, и держит в PostgreSQL производную
структуру: каталог паттернов, инциденты, причины, статистику применённых
решений.

Поверх хранения работают шесть детекторов на обычном SQL. Найденное проходит
через фильтр («привратник»), который решает, стоит ли событие внимания
и сколько контекста к нему приложить. Отобранное уходит наружу вебхуком.
Внешняя система — ИИ-агент или человек — читает контекст и пишет результат
разбора обратно через MCP.

Накопленный разбор используется при следующем срабатывании того же паттерна:
к событию прикладывается ранее записанная причина и статистика решений
(«помогло N из M»). Это единственный смысл, в котором система «учится» —
никакой модели внутри нет, есть таблица разборов и запросы к ней.

### Границы

| Делает | Не делает |
|---|---|
| принимает и хранит логи, метрики, трейсы | не содержит ИИ внутри и не вызывает модели |
| находит аномалии детекторами на SQL | не выполняет операций над сервисами |
| решает, нужен ли внешний разбор и с каким контекстом | не хранит учётных данных прода |
| отдаёт данные и принимает результаты по MCP | не заменяет Grafana для графиков и трендов |
| накапливает разборы и переиспользует их | |

Эндпоинта «выполнить действие» в API нет. Инструментов действия в MCP нет.
Решение применяет человек или существующая автоматика; система записывает
только факт применения и результат проверки.

### Ключевые технические решения

**ИИ вынесена наружу.** Внутри нет ни ключей моделей, ни вызовов к ним.
Контракт — вебхук наружу плюс MCP-сервер на чтение и запись результата.
Следствие: данные не покидают периметр, модель может быть любой, включая
локальную, а стоимость вызовов лежит на владельце агента.

**Триггеры — не пороги на метриках.** Детекторы ловят появление ранее
не встречавшегося паттерна в логах, всплеск известного паттерна относительно
базовой линии, обрыв ожидаемой последовательности событий, нарушение правил
о бизнес-данных, исчерпание ресурса по линейному тренду и прожигание бюджета
ошибок. Пороги на метриках при этом никуда не деваются — они остаются
в Grafana, где им и место.

**Инварианты над боевыми данными.** Правила вида «на один order_id ровно один
payment.succeeded» проверяются SQL-запросами по логам, а не по базе приложения.
Это ловит расхождения, которых не видно ни в одной метрике: двойные списания,
непробитые чеки, зависшие переводы. Работает потому, что бизнес-ключи лежат
в атрибутах записей, а не в тексте сообщения.

**Сообщения не ограничены по длине.** Стектрейс на мегабайт, дамп запроса,
ответ чужого API целиком — хранятся как есть. Проверено на 16 МБ. Память
защищена пределами на объём пачки и очереди, а не обрезкой текста;
в разбор паттерна при этом уходит только начало сообщения.

**Кардинальность меток ограничена сверху.** На узле, куда пишут тысячи
сервисов, метка со значением из данных — путь к неограниченному росту памяти.
Значения меток проходят через реестр с потолком; сверх потолка всё сходится
в одно значение.

## Как это работает

```
        приложения (OTel SDK / Vector / Fluent Bit)
                          │ OTLP
                          ▼
                 OpenTelemetry Collector
                          │
        ┌─────────────────┼──────────────────┐
      логи             трейсы             метрики
        │                 │                  │
        ▼                 ▼                  ▼
   WATCHGOOSE       ClickHouse       VictoriaMetrics
   (ingest)         (otel_traces)    (+ vmagent)
        │
        ▼
   Manticore ── посуточные RT-индексы
        │
        └────► PostgreSQL ── знание: fingerprints, incidents,
                             причины, инварианты, пути

   ══════════════════════════════════════════════════
   ЗАМКНУТЫЙ ЦИКЛ

   WATCHGOOSE
      │ детекторы (SQL) нашли проблему
      │ gate решил: нужна ИИ и сколько дать контекста
      │
      ├──── вебхук ────►  ВНЕШНЯЯ ИИ  (чужая, любая)
      │                        │
      │                   читает через MCP:
      │  ◄─────────────── логи, трейсы, метрики, история
      │                        │
      │                   пишет через MCP:
      │  ◄─────────────── диагноз, причина, что помогло
      │
      ▼
   знание накоплено → следующий раз ищется быстрее
   ══════════════════════════════════════════════════
```

**ИИ вынесена наружу.** Это может быть Claude Code, агент компании, своя обвязка
над любой моделью, в том числе локальной. Watchgoose разговаривает с ней по MCP
и не знает, кто на том конце.

## Быстрый старт

Нужны Docker 24+ и ~8 ГБ свободной памяти.

```bash
git clone https://git.smorodi.ru/infrastructure/watchgoose-full.git
cd watchgoose-full

cp .env.example .env
$EDITOR .env          # заполните PG_PASS и CH_PASS

make up               # соберёт образ и поднимет весь стек

# первый токен создаётся сам при первом запуске и печатается ОДИН раз
docker compose -f deploy/docker-compose.yml logs watchgoose | grep "ПЕРВЫЙ ТОКЕН"
```

Токена в `.env` больше нет: токены живут в базе, у каждого своя роль,
и выпускаются они этим первым администраторским — через API или командой
`--issue-token`. Подробнее в разделе «Роли и токены».

Поднимаются девять контейнеров: сам Watchgoose, Manticore, PostgreSQL,
ClickHouse, VictoriaMetrics, vmagent, OTLP-коллектор, экспортёр
PostgreSQL. Готовность — `docker compose ps`: все со статусом `Up`,
а `watchgoose` ещё и `healthy`.

⚠️ **Grafana в состав не входит и по умолчанию не поднимается.** Система
работает без неё полностью: поиск, инциденты, графики и дашборды у неё
свои. Раньше Grafana стартовала всегда и публиковала порт 3000 на все
интерфейсы с паролем `admin` — на сервере с внешним адресом это открытая
панель к тем же данным. Кому она нужна — `docker compose --profile grafana up -d`
и обязательный `GRAFANA_PASS`.

| Что | Где |
|---|---|
| Web UI | http://localhost:8080 |
| MCP-сервер | http://localhost:8080/mcp |
| Метрики самой системы | `watchgoose:9090/metrics` — отдельный слушатель, на хост не публикуется |
| Grafana | `--profile grafana`, http://localhost:3000 |
| Приём телеметрии | `localhost:14317` (gRPC), `localhost:14318` (HTTP) |

⚠️ Это адреса **с самой машины**. Приложения шлют в коллектор; порты
`4317`/`4318` на хосте открывает Caddy (профиль `tls`) и проксирует их
в тот же коллектор. Приёмник Watchgoose на хост не публикуется вовсе.
Полная таблица адресов — в разделе «Подключение своих сервисов».

Порты хоста заняты? В `.env` переопределяются те, что слушают на
`127.0.0.1`: `WG_HTTP_PORT`, `OTEL_GRPC_PORT`, `OTEL_HTTP_PORT`,
`GRAFANA_PORT`, `MINIO_PORT`.

А вот порты Caddy — `80`, `443`, `4317`, `4318` — заданы литералами
и переменной не выносятся: в `.env` меняется только адрес привязки,
`WG_PUBLIC_BIND`. Это не упущение. По `80` идёт проверка владения
доменом, `443` — стандартный HTTPS, а `4317`/`4318` — те адреса,
которые вы раздаёте своим приложениям. Если порт занят чем-то ещё,
разводить придётся то, другое.

На **Linux-хосте** имеет смысл добавить сбор метрик железа — без него
не работают два наблюдателя, «свободное место на диске» и «занятая
память»:

```bash
docker compose --profile host-metrics up -d
```

⚠️ Только на Linux. На Docker Desktop этот контейнер монтирует корень
хоста, чего там не бывает в принципе, — потому он и вынесен в профиль,
а не включён всегда.

Проверить, что приём работает. Приём закрыт токеном роли `ingest` — тем
самым `INGEST_TOKEN`, что прописан коллектору; без заголовка запрос
вернёт 401:

```bash
curl -X POST http://localhost:14318/v1/logs \
  -H "Authorization: Bearer $INGEST_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"resourceLogs":[{"resource":{"attributes":[
        {"key":"service.name","value":{"stringValue":"checkout"}}]},
      "scopeLogs":[{"logRecords":[{
        "severityNumber":17,"severityText":"ERROR",
        "body":{"stringValue":"connection refused to 10.0.14.2:5432"},
        "attributes":[{"key":"order_id","value":{"stringValue":"8891"}}]}]}]}]}'

# через пару секунд — токен обязателен, через это API видны
# логи с бизнес-ключами (роль viewer или выше)
curl -H "Authorization: Bearer $WG_TOKEN"      'http://localhost:8080/api/v1/patterns' | jq
```

Ещё проще — не собирать OTLP руками, а взять готовый клиент под свой
язык: см. «Подключение своих сервисов».

### Без Docker

```bash
make build                  # bin/watchgoose и bin/wgsim
make schema                 # накатить схему PostgreSQL
./bin/watchgoose --role=all --config=deploy/watchgoose.yaml
```

⚠️ **Доступ закрыт по умолчанию.** Через REST и Web UI видны логи с
бизнес-ключами и суммами, оттуда же утверждаются инварианты. Первый
администраторский токен создаётся при первом запуске и печатается в журнал
один раз — второго показа не будет. Открыть стенд совсем без токенов можно
только явно: `api.allow_anonymous: true`.

Выпустить токен, не поднимая сервис:

```bash
./bin/watchgoose --issue-token="дежурная смена" --token-role=viewer
```

Внутри мессенджера токен не нужен: Mini App входит по подписи `initData`,
которая проверяется секретом бота (`MINI_APP_SECRET`). Роль такого входа
задаётся `api.mini_app_role` и по умолчанию `viewer`, а не `admin`:
подпись подтверждает, что человек — это он, и ничего не говорит о том,
что ему положено.

## Проверка на живой нагрузке

Рядом лежит генератор — `cmd/wgsim`. Он шлёт **логи, трейсы и метрики** по OTLP
тем же протоколом, что и настоящий коллектор, и умеет две разные вещи.

### Сценарий: система адекватно реагирует

```bash
make sim     # или: ./bin/wgsim --mode=demo --endpoint=localhost:14317 --duration=200s
```

Имитируется сеть заведений: заказы идут через семь шагов
(`order.created → … → order.completed`), у каждого свой `trace_id` и бизнес-ключи.
Параллельно «железо» уходит в перегрузку, и по очереди возникают все шесть
классов проблем:

| Момент | Что происходит | Кого ждём |
|---|---|---|
| +20с | утечка памяти в `payment-worker`, ЦП следом | `predictive` |
| +45с | в логах появляется сообщение, которого не было | `new_fp` |
| +70с | знакомая ошибка идёт в 15 раз чаще нормы | `spike` |
| +95с | 35% заказов встают на `payment.confirmed` | `path_break` |
| +120с | на один `order_id` уходит два `payment.succeeded` | `invariant` |
| +140с | диск растёт линейно к порогу | `predictive` |
| +170с | нагрузка спадает | — |

Проверено на живом стеке (PostgreSQL, Manticore, ClickHouse, VictoriaMetrics,
OTel Collector). Результат прогона на 50 462 логах, 34 449 спанах и 1 400 метриках:

```
new_fp      16 инцидентов
path_break   1   purchase→payment.confirmed
invariant    1   66 двойных списаний
predictive   2   память (critical) и диск (medium)
spike        1   событие → skip, правило 2: инцидент по этому fp уже открыт
```

Майнинг путей при этом сам восстановил эталон и оборванную ветку:

```
95.7% terminal  order.created → order.validated → payment.requested →
                payment.confirmed → order.paid → kitchen.accepted → order.completed
 4.3% оборван   order.created → order.validated → payment.requested → payment.confirmed
```

Каталог событий сошёлся с реальностью: 5 000 `order.created` против 4 783
`order.paid` — те самые 217 зависших процессов, которые и нашёл детектор.

### Нагрузка: система адекватно держит

```bash
make load    # или: ./bin/wgsim --mode=load --endpoint=localhost:14317 --workers=8
```

Шлёт тем же путём, что и настоящие источники, — в коллектор
на `localhost:14317`. Порты `4317`/`4318` самого приёмника на хост
не публикуются, слать туда с хоста некуда.

Если приём и API закрыты токенами, генератору их нужно предъявить —
это два разных секрета:

```bash
# --token     — токен роли ingest, иначе коллектор откажет (Unauthenticated / 401)
# --api-token — токен роли viewer и выше, иначе сверка через REST вернёт 401
./bin/wgsim --mode=load --endpoint=localhost:14317 --workers=8 \
    --token="$INGEST_TOKEN" --api-token="$API_TOKEN"
```

Замер на обычном ноутбуке (Manticore и PostgreSQL в Docker, всё на одной
машине):

```
ПРОПУСКНАЯ СПОСОБНОСТЬ:  67 100 записей/сек

Задержка экспорта пачки из 1000 записей:
  p50 60.6ms    p95 124.1ms    p99 165.2ms    max 248.4ms

За 30 секунд: 2 019 000 записей принято, 21 548 отклонено с backpressure
```

Путь каждой записи здесь полный: нормализация → Drain-фингерпринтинг → фильтр →
батч → Manticore + каталог в PostgreSQL.

**Сверка по трём точкам после прогона:**

```
нормализовано:     1 997 452
записано пачками:  1 997 452
строк в Manticore: 1 997 452
```

Ни одного дубля, ни одной потери. Когда генератор обгоняет запись, система
возвращает `Unavailable` — источник притормаживает, а коллектор повторяет
из своей дисковой очереди. Молча данные не теряются.

Для сравнения: план рассчитан на 200 млн документов в сутки, то есть ~2 300/сек
в среднем и 12 000–18 000/сек на пиках. Запас относительно пика — трёхкратный,
и это на одной машине без тюнинга.

## Подключение ИИ

Watchgoose ничего не знает о моделях. Он делает две вещи: **толкает событие
наружу** и **отдаёт данные по MCP**.

### 1. Куда слать события

Точки вызова заводятся на экране «Вызов ИИ и оповещения». Одной переменной
на всё больше нет: точек может быть несколько, и у каждой своё назначение —
одна зовёт сильную модель на сложное, вторая дешёвую на известное, третья
дублирует критичное в дежурный канал.

**Драйвер `tribly`** — сообщение боту мессенджера:

```
base_url     https://мессенджер.внутренний     ⚠️ не url
bot_token    токен бота                        ⚠️ не token
channel_id   42                                ⚠️ не chat_id
```

Имена полей проверяются при сохранении, и если заполнены `url` или
`chat_id`, отказ так и говорит: «у вас заполнено url — это другое поле».
Точка с забытым полем раньше сохранялась как рабочая и молчала до первой
аварии.

⚠️ **content и ai_context независимы.** Одно сообщение может и оповестить
человека, и запустить ассистента: непустая задача и есть признак вызова.
При назначении «оповестить людей» задача остаётся пустой, и в канале
появляется обычное сообщение с цветом по важности.

**Драйвер `custom`** — запрос собирается шаблонами:

```
url            https://ваш-хаб/watchgoose      обязателен
method         POST                            по умолчанию POST
body           {{ json .Content }}             шаблон тела
content_type   application/json; charset=utf-8
headers        произвольные, тоже шаблоны
sign.secret    включает подпись HMAC-SHA256
```

Прежний вебхук с подписью — частный случай этого драйвера, поэтому
третьего драйвера не понадобилось.

⚠️ **Функция `json` в шаблоне тела обязательна.** Значение, вставленное
без неё, ломает JSON на первой же кавычке в сообщении лога — а кавычки
там всегда.

```bash
MCP_PUBLIC_URL=https://watchgoose.внутренний/mcp   # уходит в задачу ассистенту
```

⚠️ **Обращения во внутреннюю сеть запрещены.** Watchgoose стоит там, куда
снаружи не достучаться: у него есть доступ к базам, к метаданным облака,
к внутренним панелям. Драйвер, отправляющий запрос по любому адресу,
превратил бы его в посредника для чужих запросов. Адрес проверяется
ПОСЛЕ разрешения имени, перенаправления не выполняются. Осознанно
разрешается через `NOTIFY_ALLOW_PRIVATE_NETWORKS`.

Кнопка «Проверить» на экране точки показывает собранное сообщение,
задачу ассистенту и ответ получателя — но не секреты. Без неё о неверной
настройке узнают во время аварии.

Событие приходит с подписью `X-Watchgoose-Signature: sha256=…` — HMAC от
`метка_времени.тело`. Проверьте её на своей стороне.

```json
{
  "event_type": "incident",
  "event_id": "evt_88213",
  "severity": "high",
  "summary": {
    "title": "path_break: order → payment.confirmed (payment-worker)",
    "text": "order → payment.confirmed — 14 за 20 мин (норма 0–1)",
    "impact": "клиентов: 3, сумма застрявших операций: 47 200 ₽",
    "services": ["payment-worker", "checkout"]
  },
  "ai": {
    "required": true,
    "level": "unknown",
    "playbook": "path_break",
    "reason": "ни одна ветка известных причин не подошла",
    "hypothesis": []
  },
  "refs": {
    "incident_id": 4821,
    "fp": "a3f9c1d20b41",
    "mcp_endpoint": "https://watchgoose.внутренний/mcp"
  },
  "known_actions": [],
  "diagnosis": null
}
```

`ai.required` — **единственное поле, на которое хаб обязан смотреть.**

### 2. Что делает агент, получив событие

```
1. get_playbook(refs.playbook)      ← свежие инструкции, не копия из письма
2. incident_context(incident_id)    ← логи + трейсы + метрики одним вызовом
3. шаги playbook'а
4. submit_diagnosis(...)            ← ОБЯЗАТЕЛЬНО, иначе разбор пропадёт
```

Подключение — обычный MCP-сервер по Streamable HTTP, авторизация постоянным
токеном роли `ai`:

```
Authorization: Bearer wgt_…
```

⚠️ **Разовых токенов на инцидент больше нет.** Раньше система выпускала токен
на 15 минут и клала его в тело исходящего события. Это значило, что секрет
уезжал наружу и оседал в журналах принимающей стороны, в истории вебхуков
и в логах посредников — по одному новому секрету на каждое происшествие.

Теперь агент приходит со своим токеном, который живёт только у него и не
появляется ни в одном исходящем запросе. Номер инцидента агент называет
доводом вызова, а не получает вместе с ключом.

### 3. Человеку — тот же MCP напрямую

Выпустите себе токен роли `ai` и подключитесь из Claude Code, чтобы спросить
«что вчера было с оплатами?» голосом, а не SQL.

## Инструменты MCP

Каждый отдаёт **мало данных высокой плотности**. Тула `run_sql` здесь нет
намеренно: с ним модель вытянет десять тысяч строк, забьёт контекст и отупеет.

**Чтение** — по токену роли `ai`, по всей системе:

| Инструмент | Что возвращает |
|---|---|
| `whats_broken` | новые и всплеснувшие паттерны — первый вопрос всегда этот |

| `sample_logs` | пять живых примеров конкретного паттерна |
| `trace` | развёрнутый путь запроса по сервисам |
| `incident_context` | **логи + трейсы + метрики склеенные** — то, чего не даст ни одно хранилище |
| `compare` | что изменилось между окнами — ядро диагностики |
| `deployments` | что катилось рядом по времени |
| `metric` | ряд PromQL с текущим значением |
| `similar_incidents` | история: было ли, что помогало |
| `path_status` | где обрываются процессы |

| `violating_rows` | конкретные нарушители инварианта |
| `spans` | спаны по фильтрам: длительность, статус, атрибуты |
| `code_context` | файл:строка:коммит из версионной карты |
| `should_invoke_ai` | привратник: нужна ли ИИ и на каком уровне |
| `get_playbook` | маршрут диагностики под тип события |
| `search_logs` | **поиск на языке запросов: AND, OR, NOT, диапазоны, маски** |
| `timeline` | **трейс целиком: спаны и логи на одной шкале, плюс паузы** |
| `find_traces` | **процессы по условию на логах — каждый целиком** |
| `query_help` | поля и примеры языка запросов |
| `event_catalog`, `invariant_candidates`, `stale_runbooks`, `gate_stats`, `incident_stats` | сырьё для еженедельных и месячных поводов |

**Запись** — тем же токеном:

| Инструмент | Что делает |
|---|---|
| `submit_diagnosis` | причина, цепочка, влияние + ветка причины в память |
| `submit_action_result` | «применили, помогло / не помогло» → статистика |
| `propose_runbook` | предложить запись знания (verify обязателен) |
| `propose_invariant` | предложить бизнес-правило (создаётся **выключенным**) |
| `submit_fp_verdict` | разметить паттерн после релиза: файл, коммит, вердикт |
| `classify_fingerprint` | шум / ожидаемая ошибка / внимание / критично |
| `close_incident` | закрыть: чем закончился и что помогло |
| `incident_fix_kinds` | какие бывают виды решения — список для `close_incident` |
| `set_incident_severity` | пересмотреть важность по итогам разбора |
| `escalate_incident` | позвать людей: оповещение уходит в те же точки |

> ⚠️ **Без группы `submit` цикл не замыкается.** ИИ отработает, красиво изложит
> вывод — и всё пропадёт. Следующий раз система начнёт с нуля и заплатит за это
> ещё раз.

⚠️ **Закрывает инцидент агент САМ, а не ждёт человека.**

Раньше он умел только поставить диагноз: инцидент висел открытым, пока
к нему кто-нибудь не подойдёт, даже когда всё разобрано и починено.
Список открытых копился и переставал что-либо значить — в нём вперемешку
висело то, что ждёт действий, и то, что давно закончилось.

Вид решения при закрытии обязателен, и неизвестный отвергается: смысл
поля в том, чтобы по нему считать. Пропустив «рестарт», «restart»
и «ребут», система получит три вида вместо одного и статистику, которая
ничего не показывает. В записи остаётся **имя токена**, а не слово «ии»:
агентов бывает несколько, и через полгода вопрос «кто закрыл» должен
иметь ответ.

Важность меняется только с причиной — она дописывается к разбору вместе
с прежним значением. Без объяснения изменённая важность через месяц
выглядит ошибкой в данных, а не решением.

Групп ровно две. Инструментов, выполняющих что-либо над сервисами, нет.

## Поиск: язык запросов

Полноценный булев язык, привычный по Elasticsearch и Lucene.

```
level:ERROR AND service:payment-worker AND NOT "timeout"
service:(checkout OR billing) AND amount_cents > 100000
order_id:8891 OR payment_id:4412
amount_cents:[100000 TO *] AND ts > now-1h
host:worker-* -level:DEBUG
message:/acquirer.*(timeout|refused)/ AND region:south
"payment failed"~4 AND order_id:* AND NOT env:staging
```

| Конструкция | Что делает |
|---|---|
| `AND` `OR` `NOT` | булева алгебра; `&&`, `\|\|`, `!` и `-term` — то же самое |
| `+term` | обязательное вхождение |
| пробел между условиями | неявный `AND`, как в Lucene |
| `( )` | группировка любой вложенности |
| `поле:значение` | точное совпадение по атрибуту |
| `поле:(a OR b)` | несколько значений одного поля |
| `поле > N` | сравнения по числам: `>` `>=` `<` `<=` `!=` `=` |
| `поле:[a TO b]` | диапазон с краями |
| `поле:{a TO b}` | диапазон без краёв; скобки можно смешивать: `[a TO b}` |
| `поле:[a TO *]` | открытая граница |
| `поле:маска*` | маска по строковому атрибуту |
| `поле:/рег.*выр/` | регулярное выражение |
| `поле:*`, `_exists_:поле` | поле заполнено |
| `"фраза целиком"` | поиск фразы, а не набора слов |
| `"два слова"~3` | слова рядом, но не обязательно подряд |
| `ts > now-1h` | относительное время; понимает и ISO-даты |
| голое слово | полнотекстовый поиск по `message` |

Поле, которого нет в схеме, ищется в JSON-атрибутах: `http_route:/api/orders`
найдёт `attrs.http_route`. Список полей и примеры — `GET /api/v1/fields`
или инструмент `query_help` в MCP.

Ответ всегда содержит `explain` — как система поняла запрос. «Нашлось не то»
чаще всего означает «понято не так», и увидеть это надо сразу.

### Как это исполняется

Запрос разбирается в дерево, дерево приводится к дизъюнктивной форме,
каждый дизъюнкт компилируется в выборку Manticore: текстовая часть — в `MATCH()`
с его булевым синтаксисом, атрибутивная — в `WHERE` **параметрами**.
Значения никогда не склеиваются в текст запроса.

Три особенности хранилища, из-за которых всё устроено именно так — каждая
найдена на живом Manticore, не в документации:

- **`текст ИЛИ атрибут` одной выборкой не выражается.** Полнотекстовая часть
  всегда соединяется с `WHERE` через И. Такой запрос раскладывается на ветки,
  результаты объединяются и дедуплицируются. Потолок — 12 выборок, дальше
  честная просьба упростить.
- **`NOT (условие)` в `WHERE` не понимается.** Отрицание выражается инверсией
  оператора: `service <> ?`, а отрицание диапазона — через `ИЛИ`.
- **`REGEX(колонка, …)` перестаёт фильтровать**, если та же колонка есть
  в списке выборки — молча, без ошибки. Маски считаются вычисляемым
  выражением в `SELECT`, фильтр идёт по алиасу.

Запрос из одних исключений (`NOT timeout`) Manticore не исполняет вовсе —
ему не от чего оттолкнуться. Такие условия отсеиваются после выборки,
по границам слов: исключение `order` не выбросит `orders`.

- **`REGEX()` по `message` невозможен в принципе**: это stored-поле, а не
  атрибут, попытка даёт `stored fields can't be used in expressions`.
  Поэтому `message:/а|б/` применяется после выборки, а по атрибутам
  (`attrs.route:/…/`) считается самим хранилищем. Разница видна на большом
  окне: выражение по тексту стоит сузить сервисом или уровнем.

Сломанное регулярное выражение отвергается на разборе. Это не придирка:
Manticore на нерабочем выражении не сообщает об ошибке, а молча отдаёт
пусто — человек решит, что ничего не нашлось.

## Логи и трейсы вместе

Связь «лог ↔ трейс» точная, по `trace_id` (П1). На ней держатся три вещи,
которых не даст ни одно хранилище по отдельности.

### Единая лента

```bash
curl -H "Authorization: Bearer $TOKEN"   "$WG/api/v1/timeline/9260289364e4347ceab1f3226f2ab51f?format=text"
```

```
трейс 9260289364e4347c · 327 мс · сервисы: checkout, kitchen-display,
orders-api, payment-worker · спанов 7, строк 8
────────────────────────────────────────────────────────────────────────
    +0мс  │ [INFO] checkout order accepted from point p-38
    +0мс  ┌ checkout POST /orders (32.0 мс)
   +32мс  │ [INFO] orders-api order validated, positions: 1
   +33мс  ┌ orders-api validate (6.0 мс)
   +33мс  └ POST /orders
   +38мс  │ [INFO] payment-worker payment requested via acquirer acq-3
   +39мс  ┌ payment-worker acquire (162.0 мс)
  +200мс  │ [INFO] payment-worker payment confirmed by acquirer acq-0
  +201мс  ┌ payment-worker confirm (93.0 мс)
```

Спаны и строки логов на одной шкале, с отступом по вложенности и смещением
от начала. Отдельно считаются **паузы** между соседними событиями: разрыв
в трейсе почти всегда и есть ответ на вопрос «где стояло».

### Поиск процессов, а не строк

Обычный поиск отвечает «вот строки». Этот — «вот процессы, внутри которых
такое было», и сразу целиком:

```bash
curl -G -H "Authorization: Bearer $TOKEN" "$WG/api/v1/traces/search"   --data-urlencode 'q=level:ERROR AND service:payment-worker'   --data-urlencode 'min_ms=250'
```

```
9260289364e4347c  326 мс  checkout, kitchen-display, orders-api, payment-worker
   шаги: order.created → order.validated → payment.requested → payment.confirmed
         → order.paid → kitchen.accepted → order.completed
   спанов 7, заказ 800777, сумма 8031.04 ₽
```

Найдено по одной строке — показан весь процесс: сколько шёл, через какие
сервисы прошёл, какие шаги сделал, чем закончился, на какую сумму.
Именно так формулируется большинство вопросов дежурного: не «покажи строки»,
а «покажи заказы, где сломалось».

### Выгрузка одним файлом

Смотреть и выгружать — разные задачи. На экране лента одного процесса;
в выгрузке — сотни процессов целиком, чтобы унести в блокнот, приложить
к задаче или прогнать своим скриптом.

```bash
# по условию: всё, что подошло, — процессами целиком
curl -G -H "Authorization: Bearer $TOKEN" "$WG/api/v1/export"   --data-urlencode 'q=level:ERROR AND service:payment-worker'   --data-urlencode 'window=6h' -o разбор.ndjson

# конкретные процессы, таблицей
curl -G -H "Authorization: Bearer $TOKEN" "$WG/api/v1/export"   --data-urlencode 'trace_id=9260289364e4,7f31a02b18cc'   --data-urlencode 'format=csv' -o разбор.csv
```

```json
{"trace_id":"ca02b43a…","offset":"+45мс","kind":"log","service":"payment-worker",
 "level":"INFO","message":"payment requested via acquirer acq-2","fp":"6cac8be89a6b",
 "event":"payment.requested","attrs":{"order_id":"801833","amount_cents":"303721",…}}
{"trace_id":"ca02b43a…","offset":"+45мс","kind":"span","service":"payment-worker",
 "span":"acquire","span_id":"4330acd985c9b653","duration_ms":162,"status":"Ok"}
```

⚠️ **Логи и спаны идут одним потоком**, вперемешку по времени, а не двумя
файлами. Смысл именно в этом: склеивать выгрузки по `trace_id` вручную —
ровно та работа, ради избавления от которой всё и делалось. Бизнес-ключи
(`order_id`, `amount_cents`, …) кладутся в `attrs`: без них «покажи заказы,
где деньги списались дважды» превращается в бесполезный текст.

Выгружаются **процессы целиком**, а не подошедшие строки — иначе получится
набор обрывков, за остальными строками того же заказа придётся возвращаться
в систему. Форматы: `ndjson` (для `jq` и скриптов) и `csv` (для таблиц);
оба пишутся потоком, выгрузка на сотни тысяч строк не собирается в памяти.

### В UI и в MCP

На экране «Поиск» переключатель **строки / процессы**, справка по языку
с живым списком полей (берётся с сервера, а не дублируется во фронте),
кнопки выгрузки в ndjson и csv, и **живой хвост** — новые строки по тому же
условию по мере поступления. Из любой строки можно провалиться в ленту
процесса, оттуда — выгрузить его целиком.

У ИИ те же возможности — инструменты `search_logs`, `timeline`, `find_traces`
и `query_help`.

## Детекторы

Работают **без ИИ**: обычный код и SQL по расписанию.

| Детектор | Частота | Что ловит | Зачем нужен |
|---|---|---|---|
| `new_fp` | 30 сек | **ошибка**, которой не было N дней | появление новой ошибки |
| `spike` | 60 сек | частота выше baseline в K раз | деградация |
| `invariant` | по правилу | нарушение бизнес-утверждения | **тихая порча данных** |
| `path_break` | 60 сек | обрыв процесса, пропуск шага | **молчаливые провалы** |
| `predictive` | 5 мин | тренд к исчерпанию ресурса | **до поломки** |
| `slo_burn` | 60 сек | скорость сжигания бюджета ошибок | деградация качества |

⚠️ **`new_fp` смотрит только на ошибки** — `detectors.new_fp_levels`,
по умолчанию `ERROR`, `FATAL`, `CRITICAL`.

Новый паттерн сам по себе не событие: событием его делает то, что это
ошибка. Каждый релиз приносит десятки новых штатных сообщений — «order
completed», «payment confirmed», — и формально все они новые паттерны.
Без фильтра детектор поднимает по инциденту на каждое, с вызовом ИИ
и записью в ленту, а настоящая поломка теряется между ними. Проверено
на стенде: из шести инцидентов подряд четыре оказались обычными INFO
с сотнями тысяч повторов, и реальный `deadlock detected` лежал среди них.

Фильтр стоит в SQL, а не в коде: выборка ограничена пятью сотнями строк,
и отсеивай мы после неё — этот лимит забился бы штатным INFO, а ошибки
в него просто не попали бы.

### Главный — path_break

```
fingerprint  ловит  ПОЯВЛЕНИЕ ошибки
путь         ловит  ОТСУТСТВИЕ ожидаемого события  ← этого не ловит ничто
```

Критерий не «ошибка или нет», а «достигнуто терминальное состояние или повисло».
Отказ платежа по недостатку средств — нормальный путь. `payment.succeeded` без
`order.paid` — повисший процесс, даже если ошибок в логах нет.

**Локализация бесплатна:** точка обрыва **и есть** ответ на вопрос «где».

⚠️ Детектор требует разметки процессов — таблица `process_entry`:

```bash
curl -X POST localhost:8080/api/v1/paths/entry \
  -H 'Content-Type: application/json' \
  -d '{"first_step":"order.created","process_name":"purchase","timeout_ms":120000}'
```

Без этого он честно ничего не делает, а не выдаёт мусор.

### Привратник (gate)

Обычная функция, никакого ИИ внутри. Отвечает на два разных вопроса.

**Фильтр шума** — здесь ИИ действительно не зовут:

| # | Проверка | Не прошло → |
|---|---|---|
| 1 | порог зрелости: ≥ N повторов за M минут **или** ≥ X трейсов | `skip` |
| 2 | дедупликация: уже открыт инцидент с этим fp | `skip` |
| 3 | лимит эскалаций: легло 40 сервисов — уходит один вебхук | `digest` |
| 4 | окно после релиза: новые fp собираются в один разбор | `digest` |

**Насыщенность контекста** — ИИ вызывается во всех трёх случаях:

| Уровень | Условие | Что кладём в вебхук | Работа ИИ |
|---|---|---|---|
| `known` | лучшая ветка набрала `confidence ≥ 0.7` | **все подошедшие гипотезы** со статистикой | сверить и выбрать, **1–2 шага** |
| `partial` | 0.4 – 0.7 | гипотезы + похожие инциденты | разобраться с опорой, 4–6 шагов |
| `unknown` | ни одна ветка не подошла | playbook + полный инструментарий | полное расследование, 12–15 шагов |

> **`known` — не приказ, а гипотеза.** ИИ обязана проверить, тот ли это случай,
> и вправе сказать «похоже, но в этот раз причина другая». Отвергнуть все версии —
> нормальный ответ.

Каждое решение пишется в `gate_decisions` с причиной и номером правила.
По распределению уровней видно главное — **растёт ли доля `known`**.

## Память причин

⚠️ **Симптом ≠ причина.** Один fingerprint `502 from upstream` может значить:

```
fp "502 from upstream"
   ├─ OOM в поде         → поднять лимиты
   ├─ плохой деплой      → откат
   ├─ перегрузка БД      → убить тяжёлые запросы
   └─ сетевой сбой       → звать людей
```

Память устроена **деревом** (`known_causes`), а не словарём. Ветка выбирается
по `distinguishing` — набору признаков, которые проверяются по живым данным:

```json
{
  "all_of": [
    {"type": "metric", "name": "container_memory_usage_bytes", "op": ">", "value": 0.9},
    {"type": "co_fp",  "fp": "b721e0aa1c30", "within_sec": 60},
    {"type": "deploy", "within_min": 30, "service": "same"},
    {"type": "attr",   "key": "host", "op": "matches", "value": "^worker-"},
    {"type": "path",   "process": "order", "broken_at": "payment.confirmed"}
  ],
  "none_of": [{"type": "co_fp", "fp": "c9f102ab7712", "within_sec": 60}],
  "min_match": 3
}
```

Не подошла ни одна ветка → `unknown`, полное расследование, даже если fp знаком
годами. Недоступная метрика считается несовпадением: честное «не знаю» важнее
красивого «похоже».

### Записи знания

> **Runbook — не программа и не плагин. Это запись в базе знаний:**
> «при такой проблеме помогает такое действие, помогло N раз из M».

Из коробки их **ноль** — база наполняется эксплуатацией. Создаёт их ИИ через
`propose_runbook` или человек.

`verify` обязателен: без него неизвестно, помогла ли запись, и статистика
не копится. Статистика ведётся по паре **(решение × проблема)** — одно решение
может помогать при проблеме A в 12 случаях из 12, а при B — в 2 из 9.

Строка «12 из 12» нигде не хранится: она рендерится в момент показа из двух чисел.

## Инварианты

Правила предметной области система вывести из ничего не может. Источника два,
и **оба — не человек**:

1. **ИИ по каталогу событий** — хватает семантики имён, статистика не нужна.
   Работает с первых дней.
2. **Статистический майнинг** — еженедельный SQL по накопленным данным
   («`payment.succeeded` уникален по `order_id` в 99.997% случаев»).

ИИ получает ~50 кандидатов, отсеивает мусор и формулирует SQL. Человек только
**утверждает**: пять минут в неделю пробежать список.

```
предложено ~50  →  человек смотрит  →  включено ~5
enabled = false по умолчанию
```

⚠️ Автоутверждения нет и не будет: из статистики выводятся сотни закономерностей,
но настоящих правил среди них единицы. Автоутверждение завалит систему ложными
срабатываниями — прямой путь к alert fatigue.

## Интерфейс и мини-приложение

**Один адаптивный SPA, один деплой.** В браузере это обычная страница;
внутри мессенджера — то же самое, открытое как Mini App. Собранная статика
вшита в бинарник через `embed.FS`, отдельного фронтового сервиса нет.

| Экран | Что там |
|---|---|
| Инциденты | лента с тем, **что** сломалось, разбор от ИИ, фиксация исхода |
| Паттерны | каталог fingerprint'ов, версии, разметка «шум / внимание / критично» |
| Знание | записи решений и статистика «помогло N из M» |
| Инварианты | правила о деньгах и утверждение кандидатов |
| Пути | эталонные последовательности, точки обрыва |
| Поиск | язык запросов, живой хвост, выгрузка, переход в ленту процесса |
| Привратник | распределение уровней и решение по каждому событию с причиной |
| Обзор | дашборд: набор графиков, открывается первым в мессенджере |
| Трассировки | замеры операций и самые долгие процессы, отдельно от логов |
| Метрики | несколько рядов на одной картинке, каталог с описаниями |
| История | чем закончился каждый разбор, доля успеха, листание по времени |
| Токены | выпуск и отзыв токенов доступа, роли |

Меню строится по правам предъявленного токена: роль `digest` видит только
«Историю», роль `admin` — ещё и «Токены». Это вежливость, а не преграда —
защищает сервер, который отвечает 403 независимо от того, что нарисовал
браузер.

Тренды, графики и дашборды — в Grafana: тащить их сюда значило бы делать
хуже то, что уже сделано. Здесь то, чего в Grafana нет и не будет.

### Распределение найденного по времени

Под строкой поиска — гистограмма: сколько записей попало в каждый интервал.

⚠️ Это не украшение, а половина работы с поиском. Список отвечает «что
нашлось», но не отвечает «когда». Всплеск в 03:40 и ровный фон за сутки
дают одинаковую страницу результатов, а означают разное: первое — авария,
второе — привычный шум.

Клик по столбику сужает **и картинку, и выдачу**: увидел всплеск —
провалился в него. Сужение снимается кнопкой «сбросить».

Пустые интервалы рисуются нулями, а не пропускаются: три всплеска подряд
и три всплеска с часовыми паузами между ними — разные вещи, и пауза это
тоже наблюдение.

Шаг подбирается из круглых значений (5 с, 30 с, минута, 5 минут, час…),
а не делением окна на число столбиков. Шкала с шагом «3 минуты 17 секунд»
технически верна и нечитаема: границы должны попадать на круглое время,
чтобы всплеск можно было соотнести с релизом или ночной выгрузкой.

Если запрос разложился на несколько веток (`текст ИЛИ атрибут`), столбики
помечаются как приблизительные: строку, попавшую в обе ветки, список
покажет один раз, а счётчик посчитает дважды. Это сказано прямо, а не
нарисовано молча.

### Дашборды

⚠️ **Своё, а не «идите в Grafana».**

Grafana лучше рисует и останется главным местом для трендов. Но она —
отдельная система со своим входом, и открыть её с телефона ночью, когда
пришло уведомление, значит вводить второй пароль в четыре утра. Здесь
дашборд нужен для одного: увидеть за пять секунд, живо ли всё, не выходя
из того же приложения, где пришло событие.

Панель — это одно или несколько выражений на одной картинке, график или
одно число крупно. Ширина в треть, две трети или всю строку; на узком
экране колонки схлопываются в одну, потому что три графика по сто двадцать
точек нечитаемы.

Один дашборд помечается главным — **в мессенджере он открывается первым**.
Туда заходят с телефона по уведомлению, и первый вопрос «всё ли живо
прямо сейчас», а не «какие были инциденты».

Живое обновление — раз в пятнадцать секунд, а не раз в секунду: каждый
тик это запрос на панель, а вкладку оставляют открытой на сутки.

#### Папки: дерево, а не один уровень

⚠️ **Папка — сущность со своим родителем, а не текстовое поле у дашборда.**

Полем это делать нельзя по двум причинам, и обе всплывают на второй
неделе. Первая: опечатка в названии заводит вторую почти такую же папку,
и дашборды расползаются по «Платежи» и «Платижи». Вторая: одного уровня
не хватает никому — появляется «Продакшн», внутри «Бэкенд», внутри
«Платежи», и плоский список превращается в перечисление
`Продакшн / Бэкенд / Платежи`, набранное руками у каждого дашборда.

Папки заводятся на верхнем уровне или внутри любой другой, глубина
не ограничена. Дашборд при создании выбирает папку из списка **или
остаётся на верхнем уровне** — так лежат те, за которыми ходят каждый
день, и прятать их в папку значит добавлять клик к самому частому пути.

⚠️ **Папка показывает всё, что под ней, а не только свой уровень.**
Наверху дерева своих дашбордов обычно нет — там одни папки, и надпись
«пусто» у ветки с тремя дашбордами внутри просто отучает её открывать.
Считается вся ветка целиком, с пометкой «включая вложенные».

Разворачивает ветку **вся подпись**, а не значок рядом: целиться
в треугольник размером с букву — работа, которую никто не подряжался
делать, а рука тянется к названию.

⚠️ **Удаление папки не удаляет дашборды.** Вложенные папки уходят вместе
с ней, а дашборды из них всплывают на верхний уровень — и система
сообщает, сколько именно всплыло. Удалить полку и потерять всё, что
на ней стояло, — не то, чего ждут от кнопки «удалить папку».

Петля («папка внутри собственного потомка») запрещена на сервере
запросом по дереву. Интерфейс всё равно считает узлы посещёнными:
если петля когда-нибудь появится, вкладка обязана показать кривое
дерево, а не зависнуть в вечной рекурсии.

#### Легенда: наведение подсвечивает ряд

На графике из двадцати линий подпись отвечает на вопрос «что это»,
но не на вопрос «которая из них». Наведение на подпись гасит остальные
линии и утолщает нужную. ⚠️ Именно гасит: одна чуть более толстая линия
среди девятнадцати одинаковых глазом не находится.

Легенда длиннее десяти рядов сворачивается — у `pg_stat_activity_count`
их бывает несколько десятков, и подписи выдавливают сам график за нижний
край экрана.

⚠️ **В подпись идут только те метки, которыми ряды различаются.**
Список «показываем service, instance, job» не работает: у одной метрики
ряды отличаются по `datname`, у другой по `state`, у третьей по коду
ответа — заранее этого не знает никто. `pg_stat_activity_count` давал
двадцать четыре строки
`pg_stat_activity_count{instance=postgres-exporter:9187, job=infra}`,
одинаковые до символа: легенда есть, а прочесть по ней ряд нельзя.
Теперь постоянные метки отбрасываются, и остаётся то, ради чего легенду
и читают: `{datname=postgres, state=idle}`. Отсутствие метки у части
рядов тоже считается различием — иначе ряд без `state` и ряд с ним
получили бы одну подпись.

Цветов в палитре восемь, а рядов бывает сорок, поэтому со второго
десятка добавляется штрих: пунктир, точки, штрихпунктир. Образец
в легенде рисуется той же линией, что и на графике, — по кружку одного
цвета сплошную линию от пунктирной не отличить.

### Закрытие инцидента

Часть инцидентов решается вручную: перезапуском сервиса, откатом
выкладки, изменением настройки. Автоматически система об этом не узнает —
детекторы видят, что проблема прекратилась, но не видят, что именно
сделал дежурный. Без записи при следующем таком же инциденте разбор
начнётся с нуля.

При закрытии заполняются три поля.

**Вид решения** — выбор из списка: перезапуск, откат, настройка,
ресурсы, данные, внешнее, прошло само, другое. Список закрытый, потому
что по нему считается статистика: «этот шаблон 12 раз решён
перезапуском». По свободному тексту такую статистику не собрать —
«перезапустил воркер», «рестартанул под» и `restart payment-worker`
для счётчика разные значения. Неизвестное значение сервер отклоняет
с кодом 400.

**Подробности** — свободный текст для того, кто будет читать эту запись
позже.

**Признак обхода** — отмечается, если устранён симптом, а не причина.
Перезапуск контейнера обычно относится к обходам. Без этого признака
система накопит статистику «перезапуск помогает» и будет предлагать его
при каждом повторении, а исходная причина останется неразобранной.
Отмеченные обходы образуют список проблем, к которым стоит вернуться;
для них есть отдельный индекс в базе.

Автор закрытия записывается именем из токена доступа.

Все три поля передаются ИИ вместе со списком похожих инцидентов
(инструмент `similar_incidents` в MCP): при разборе новой проблемы
модель видит не только «перезапустил воркер», но и что это был обход.

### Хранение данных и удаление старых

Система пишет данные в четыре хранилища. У каждого свой формат, свой
способ удаления старого и своя скорость роста.

| Хранилище | Что хранит | Как удаляется старое |
|---|---|---|
| Manticore | логи | удаление посуточных индексов целиком |
| ClickHouse | трассировки и логи старше 30 суток | удаление помесячных партиций |
| VictoriaMetrics | метрики | по сроку `-retentionPeriod` + удаление неактивных рядов |
| PostgreSQL | инциденты, решения, статистика, настройки | построчное удаление служебных таблиц |

#### Общий бюджет и доли

`retention.disk_budget` задаёт объём, который система занимает суммарно —
всеми четырьмя хранилищами вместе, а не только логами.

```yaml
retention:
  disk_budget: 200GB
  shares:
    database: 0.15    # 30 ГБ — инциденты, решения, статистика
    metrics: 0.25     # 50 ГБ — метрики
    traces: 0.25      # 50 ГБ — трассировки и холодные логи
    logs: 0.35        # 70 ГБ — логи
```

Доли задаются числами от 0 до 1. Если сумма не равна единице, значения
пересчитываются пропорционально, а в отчёт добавляется предупреждение:
конфигурация с суммой 0.95 не помешает запуску, но 5% места остались бы
неиспользованными.

Каждое хранилище получает свой лимит: `бюджет × доля`. Дальше каждое
живёт независимо — превышение логов не влияет на метрики.

#### Порог, с которого начинается удаление

Пока хранилище занимает меньше 85% своего лимита (`budget_soft_ratio`),
не удаляется ничего, даже если данным много месяцев. Место выделено —
значит, глубина истории максимальна.

При достижении порога включается удаление: убирается ровно столько,
чтобы вернуться под 85%, начиная с самых старых и наименее ценных данных.

Проверка выполняется по расписанию `detectors.retention_schedule`
(по умолчанию раз в час, в 25 минут).

#### Логи (Manticore)

**Как логи разложены.** Строки попадают в отдельный индекс на каждые
сутки и каждый уровень. За 8 августа существуют четыре индекса:

```
logs_err_20260808     logs_warn_20260808
logs_info_20260808    logs_dbg_20260808
```

Это способ хранения, а не расписание удаления. Индексы за текущие
и следующие сутки создаются заранее, поиск идёт по сводной
distributed-таблице, которая перечисляет их все.

**Единица удаления — один такой индекс**, то есть сутки логов одного
уровня. Удалить половину суток или отдельные строки нельзя, поэтому
глубина хранения всегда кратна суткам. Удаление индекса — операция над
файлами: выполняется мгновенно и не нагружает диск.

**Когда выполняется проверка.** Раз в час, в 25 минут
(`detectors.retention_schedule`), а не раз в сутки. За один прогон
удаляется не больше `max_drops_per_run` индексов (по умолчанию 3).

**Два независимых основания для удаления.**

*Первое — предельный срок.* Индекс старше срока для своего уровня
удаляется всегда, независимо от того, сколько места свободно:

```yaml
retention:
  error: 2160h   # 90 суток
  warn: 720h     # 30 суток
  info: 336h     # 14 суток
  debug: 24h     # 1 сутки
```

При этих значениях `logs_dbg` за вчера удаляется на следующий день —
именно он и выглядит как «удаление за прошлый день». Для `info` то же
происходит через 14 суток, для `warn` через 30, для `error` через 90.

*Второе — бюджет.* Если логи заняли больше 85% своей доли, удаляются
дополнительные индексы, даже если их срок ещё не вышел. Порядок
определяется приоритетом:

```
приоритет = возраст_в_сутках / предельный_срок_в_сутках + вес_уровня
вес: debug 3.0, info 2.0, warn 1.0, error 0.0
```

Удаляется индекс с наибольшим приоритетом. Веса устроены так, что
`debug` уходит раньше `info`, `info` раньше `warn`, а `error`
удаляются последними — даже если они старше остальных.

**Пример.** Сейчас на стенде лежат:

```
logs_err_20260805 … logs_err_20260809     (5 суток ошибок)
logs_warn_20260805 … logs_warn_20260809   (5 суток предупреждений)
logs_info_20260805 … logs_info_20260809   (5 суток info)
logs_dbg_20260805 … logs_dbg_20260809     (5 суток debug)
```

Все уровни лежат за одни и те же сутки: сроков по уровням нет,
а бюджет заполнен на 50% — удалять пока незачем. Когда доля дойдёт
до 85%, уйдут сутки 5 августа целиком, всеми четырьмя индексами сразу.

⚠️ **Индексы за сегодня и завтра не удаляются никогда.** В них идёт
запись. Их удаление привело бы к циклу: индекс удалён — создан
заново — место не освободилось. Их объём при этом учитывается
в занятом месте.

⚠️ **Перед удалением индекс исключается из сводной таблицы.** Поиск
идёт через distributed-таблицу, перечисляющую посуточные индексы.
Если удалить индекс, не перестроив её, каждый поисковый запрос будет
завершаться ошибкой `unknown local table` до следующей перестройки.

Если бюджет превышен, а удалять нечего — весь объём в индексах
за сегодня, — в журнал выводится предупреждение и выставляется метрика
`watchgoose_retention_stuck`.

#### Трассировки (ClickHouse)

Трассировки хранятся в таблице `otel_traces` с помесячными партициями,
логи старше 30 суток переливаются в `logs_cold` в том же ClickHouse.
Обе таблицы делят долю «трассировки», потому что лежат на одном диске.

Срок хранения задаётся в конфигурации коллектора (`deploy/otel.yaml`,
`ttl: 2160h` — 90 суток). Дополнительно система следит за долей: при
превышении 85% удаляются самые старые партиции.

⚠️ **Удаляются партиции, а не строки.** `DELETE` в ClickHouse — это
мутация: она перезаписывает куски данных целиком и требует места
и дисковых операций пропорционально их объёму. При нехватке места это
приведёт к отказу. `ALTER TABLE ... DROP PARTITION` изменяет только
метаданные, место освобождается сразу.

⚠️ **Самая свежая партиция не удаляется.** В неё идёт запись; её
удаление привело бы к тому же циклу, что и с сегодняшним индексом логов.

За один прогон удаляется не больше `max_drops_per_run` партиций.

#### Метрики (VictoriaMetrics)

У метрик два независимых механизма удаления: срок хранения и удаление
неактивных рядов.

**Срок хранения** задан флагом `-retentionPeriod` при запуске
VictoriaMetrics (`deploy/docker-compose.yml`, по умолчанию 12 месяцев).
Данные старше срока VictoriaMetrics удаляет сама, автоматически.
Изменить срок на работающей системе нельзя — только перезапуском
с другим значением флага.

**Удаление неактивных рядов** выполняет watchgoose, когда метрики
заняли больше 85% своей доли.

⚠️ Объём хранилища метрик определяется не длиной истории, а числом
рядов. Ряд — это уникальное сочетание имени метрики и значений всех
её меток. Сервис выключили, переименовали или изменили набор меток —
старые ряды остаются на диске до конца срока хранения, хотя новых
точек в них уже нет. В установке на тысячу сервисов таких рядов
со временем накапливается больше, чем действующих.

Порядок работы:

1. У VictoriaMetrics запрашивается статистика `/api/v1/status/tsdb`:
   50 метрик с наибольшим числом рядов. Именно они занимают место;
   перебирать все имена подряд не требуется.
2. Для каждой проверяется, приходили ли данные за последние
   `retention.metrics_stale` (по умолчанию 30 суток). Проверяется
   наличие хотя бы одной точки за весь период, а не последней точки:
   метрика может приходить редко — например, раз в сутки от ночного
   задания.
3. Метрики без данных за этот период удаляются через
   `/api/v1/admin/tsdb/delete_series`. За один прогон — не больше
   `max_drops_per_run` метрик.
4. Запускается `/internal/force_merge`.

⚠️ **`delete_series` удаляет всю историю метрики, а не старую часть.**
Диапазон времени этот API не принимает. Поэтому удаляются только
метрики, в которые действительно давно не пишут: для них «вся история»
и «старая часть» — одно и то же.

⚠️ **Без `force_merge` место не освобождается.** VictoriaMetrics
помечает ряды удалёнными и возвращает место при очередном слиянии
кусков, которое произойдёт неизвестно когда.

⚠️ **Метрики самой системы не удаляются.** Имена с префиксами `vm_`,
`vmagent_` и `watchgoose_` исключены из отбора: `vm_data_size_bytes` —
единственный источник данных об объёме хранилища метрик, а по
`watchgoose_*` видно состояние самой системы.

⚠️ **Имя метрики проверяется перед подстановкой в запрос.** Селектор
для `delete_series` собирается строкой, и кавычка внутри имени
позволила бы расширить его до всех метрик сразу.

Если все крупные метрики активны, а доля исчерпана, удалять нечего:
объём занят данными, которые пишутся прямо сейчас. В журнал выводится
предупреждение с вариантами: увеличить долю метрик, сократить
`-retentionPeriod` или уменьшить число меток на источниках.

Объём хранилища читается из метрики `vm_data_size_bytes`, которую
VictoriaMetrics публикует о себе. Для этого она должна собирать
собственные метрики — цель `victoria:8428` в `deploy/scrape.yml`.
Без неё определить объём невозможно: каталог с данными находится
внутри контейнера.

#### База данных (PostgreSQL)

⚠️ **База очищается автоматически.** При нехватке места PostgreSQL
прекращает приём записи, и вместе с ним останавливается вся система:
приём телеметрии, детекторы, работа с инцидентами. Место заканчивается
быстрее всего во время аварии, когда детекторы срабатывают чаще
обычного, — то есть тогда, когда система нужна больше всего.

⚠️ **Результаты разборов не удаляются.** В базе лежат данные двух видов,
и очистка затрагивает только первый.

**Служебные записи** — история решений об отборе событий
(`gate_decisions`), отправленные уведомления (`outbox`), пункты сводок
(`digest_items`), отклонённые
кандидаты в инварианты, исходные события закрытых инцидентов
(поле `incidents.raw`). Эти данные занимают большую часть объёма:
`gate_decisions` получает строку на каждое срабатывание детектора,
то есть миллионы строк в месяц. На подбор решений они не влияют.

**Результаты разборов** — причины инцидентов, применённые решения,
их исходы, вид решения, признак обхода, статистика «помогло 12 раз
из 12», учебные случаи, инварианты, эталонные последовательности,
каталог шаблонов сообщений. По этим данным система подбирает решение
для новых инцидентов. Восстановить их нельзя: они появляются только
по мере работы. Объём небольшой — разбор закрытого инцидента занимает
сотни байт против десятков килобайт исходного события.

**Ступени очистки.** За один прогон выполняется одна ступень: если
первая освободила строки, остальные в этот раз не запускаются.
Следующий прогон начинается снова с первой.

| № | Ступень | Что удаляется | Последствия |
|---|---|---|---|
| 1 | `служебные записи старше срока` | история отбора событий, отправленные уведомления, пункты сводок, истёкшие токены, отклонённые кандидаты — старше `db_noise` (30 суток) | нет |
| 2 | `исходные события закрытых инцидентов` | поле `raw` у инцидентов, закрытых более `db_raw` назад (90 суток), и подробности проверки решений | по закрытому инциденту нельзя посмотреть исходное событие; разбор остаётся |
| 3 | `служебные записи полностью` | то же, что на первой ступени, но без ограничения по дате | разбор недавних аварий станет менее подробным |
| 4 | `профили частот неактивных шаблонов` | `fp_baseline` для шаблонов, которых не было в логах 30 суток | детектор всплесков несколько часов работает по неполным данным, затем профили пересчитываются |

⚠️ **Пятой ступени нет.** Если после четвёртой места не хватает, значит
объём занят результатами разборов. Система выводит ошибку в журнал,
выставляет `watchgoose_db_cleanup_stuck = 1` и останавливается.
Дальнейшее решение принимает администратор: увеличить `disk_budget`
или долю `shares.database`.

**Удаление порциями.** За прогон удаляется не больше `db_rows_per_run`
строк (по умолчанию 20 000) из каждой таблицы. `DELETE` без ограничения
на таблице в миллионы строк держит долгую блокировку и записывает
в журнал упреждающей записи (WAL) больше, чем освобождает на диске, —
то есть при нехватке места ухудшает ситуацию.

⚠️ **После удаления выполняется `VACUUM`.** Без него удаление строк
не освобождает место: PostgreSQL помечает строки удалёнными, но файл
таблицы сохраняет прежний размер, и `pg_database_size` не уменьшается.
Очистка отработала бы вхолостую — строки удалены, счётчики растут,
место продолжает заканчиваться.

⚠️ **Используется `VACUUM`, а не `VACUUM FULL`.** `VACUUM FULL`
перезаписывает таблицу в новый файл: нужно место под копию таблицы
и исключительная блокировка на всё время работы. При нехватке места
это приведёт к отказу. Обычный `VACUUM` размер файла не уменьшает,
но помечает место внутри него свободным — новые строки пишутся туда,
и база перестаёт расти. Уменьшить файл на диске может только
`VACUUM FULL`; его запускает администратор вручную.

Из этого следует, что **размер базы после очистки не уменьшается**.
Проверка «хватило ли места» смотрит на число удалённых строк, а не
на `pg_database_size`: иначе цикл прошёл бы все ступени подряд
за один прогон.

#### Что происходит при резкой нехватке места

Пример: выкладка утроила поток логов, бюджет 200 ГБ.

1. **В течение часа.** Очередной прогон видит, что логи заняли больше
   85% своей доли. Удаляются до трёх самых старых индексов, начиная
   с `debug`. Занятое место возвращается под порог.
2. **Следующие часы.** Приток остаётся высоким, порог достигается
   снова. Каждый час уходит ещё до трёх индексов: сначала `debug`,
   затем `info`, затем `warn`. Ошибки остаются.
3. **Параллельно.** Детекторы срабатывают чаще, `gate_decisions` растёт.
   Когда база подходит к 85% своей доли, запускается первая ступень
   очистки и удаляет служебные записи старше 30 суток.
4. **Если этого мало.** База переходит ко второй, третьей и четвёртой
   ступеням. Инциденты, причины и решения остаются нетронутыми.
5. **Итог.** Глубина хранения логов сокращается — например, с 14 суток
   до 4 по `info`. Система продолжает работать: принимает телеметрию,
   находит инциденты и подбирает решения по накопленной статистике.

Текущее состояние видно на стартовом экране в блоке «Распределение
места» и по адресу `GET /api/v1/storage/budget`. Метрики для
оповещений: `watchgoose_retention_used_bytes`,
`watchgoose_retention_stuck`, `watchgoose_db_used_bytes`,
`watchgoose_db_cleanup_stuck`, `watchgoose_db_cleanup_rows_total`.

### Трассировка, логи которой уже удалены

Трассировки хранятся дольше логов, поэтому для процесса месячной
давности спаны обычно есть, а записей логов уже нет.

Пустой список логов при наличии спанов не означает, что сервис ничего
не записал. Без пояснения это читалось бы именно так, и вывод о работе
сервиса был бы неверным.

Ошибкой такая ситуация не считается: данные удалены по сроку хранения.
Страница открывается, спаны отображаются, а над лентой выводится
пояснение: логи этих суток удалены, в поиске доступны последние N суток
начиная с такой-то даты.

Граница определяется по началу самых старых суток, доступных в поиске.
Индекс за 4 августа содержит записи с 00:00 этого дня, поэтому событие
в 03:00 4 августа находится в пределах глубины хранения — его отсутствие
объясняется другой причиной, и пояснение не выводится.

### Метрики: сначала сервис, потом метрика

⚠️ **В установке на тысячу источников имя метрики почти ничего не сужает.**

`http_requests_total` есть у всех, и список из пяти сотен имён — это
список чужих метрик, в котором свою не найти. Поэтому работа начинается
с выбора сервиса, а каталог показывает только его метрики. Клик по строке
добавляет её на график **сразу с фильтром** `{service="..."}` — иначе
пришлось бы знать синтаксис PromQL, чтобы посмотреть свою метрику.

Источник помечен по-разному в зависимости от того, как метрика пришла:
экспортёры Prometheus ставят `job`, OTLP-коллектор `service_name`, наши
агрегаты `service`. Спрашивая про одну метку, система показала бы треть,
поэтому спрашивает про три.

### Логи: свои колонки и запись целиком

Набор колонок выбирает человек. ⚠️ Фиксированные «время · уровень ·
сервис · сообщение» годятся, пока ищут глазами; как только начинают
разбирать — нужны `order_id`, `region`, точка, сумма, и без них каждую
строку приходится открывать по одной, чтобы увидеть то, что могло бы
стоять колонкой. Выбор хранится в браузере: он относится к человеку
и его задаче, а не к запросу.

Клик по строке разворачивает **запись целиком**, включая поля, которых
нет в колонках. Оттуда любое поле добавляется колонкой или превращается
в условие поиска одним нажатием. Разбор почти всегда упирается в поле,
которое заранее не выбрали.

### Трассировки отдельно от логов

Склейка с логами отвечает на вопрос «что случилось в этом запросе».
Но у трассировок есть своя работа, которую склейка не делает: измерить,
сколько занимают операции, и найти самые медленные. Для этого не нужен
ни конкретный запрос, ни логи — нужна выборка по всем сразу.

**Замеры операций.** ⚠️ Три числа вместо среднего, и это не педантизм:
среднее по задержкам врёт систематически. Половина запросов по 10 мс
и половина по 2 секундам дают «в среднем секунду», чего не переживал
никто.

| | |
|---|---|
| **обычно** | медиана — как у большинства |
| **у неудачливых** | 95-й процентиль — как у худших пяти процентов |
| **худшее** | максимум — что вообще бывает |

На живом стенде это выглядит так:

```
сервис           операция        вызовов   обычно  у неудачливых   худшее
payment-worker   acquire         151 270    105 мс      172 мс     180 мс
payment-worker   confirm         151 670     70 мс      116 мс   3 499 мс
checkout         POST /orders    151 570     24 мс       39 мс      40 мс
orders-api       validate        151 270     14 мс       24 мс      25 мс
```

Вторая строка и объясняет, зачем три числа: `confirm` обычно быстрее
`acquire`, но иногда занимает три с половиной секунды. Среднее этот
хвост размазало бы, медиана одна — спрятала.

**Самые долгие процессы** — список трейсов, отсортированный по времени,
с кликом внутрь. Вход в разбор «почему медленно».

⚠️ И то и другое считается **группировкой в ClickHouse**, а не выборкой
спанов в память. Чтобы найти двадцать самых долгих процессов за час,
пришлось бы иначе перекачать все спаны этого часа — сотни тысяч строк
ради двадцати.

### Графики метрик

Отдельный экран: несколько выражений PromQL сразу, по одному в строке,
каждое своим цветом с легендой и последним значением.

⚠️ Смысл именно в «нескольких». Одна метрика на графике — это то, что
и так умеет Grafana. Ценность в том, чтобы положить рядом задержку
и ошибки одного сервиса: по отдельности это два наблюдения, вместе —
одно объяснение.

Ось Y общая для всех рядов, и это осознанно: две оси на одной картинке
позволяют подогнать любые два ряда под похожую форму и увидеть связь там,
где её нет. Если величины несопоставимы, честнее показать это разницей
масштаба, чем спрятать.

**Каталог метрик** отвечает на вопрос, с которого начинается работа
в незнакомой установке. ⚠️ Список имён без пояснений почти бесполезен:
`watchgoose_ingest_flush_rows_total` ничего не говорит тому, кто не писал
этот код, а имён в установке пять с половиной сотен. Человек открывал
экран, видел пустое поле и уходил в Grafana — то есть экран не работал.

Метрики разложены по группам с пояснением к каждой:

| Группа | Что это |
|---|---|
| бизнес | метрики ваших сервисов — то, ради чего всё и стоит |
| watchgoose | приём, очереди, детекторы, привратник |
| трассировки | задержки по спанам, посчитанные коллектором |
| postgresql · узел · среда выполнения | состояние базы, машины, процессов |

Описания собственных метрик берутся **из реестра Prometheus**, где они
объявлены рядом со счётчиками. Отдельный словарь был бы вторым источником
правды: метрику переименуют, а пояснение останется и будет врать.

Клик по строке добавляет метрику на график. Фильтр ищет и по имени,
и по описанию — можно искать «очередь», не зная, как она называется.

Ошибка в одном выражении не роняет весь график: остальные линии
рисуются, а про сломанное сказано отдельной строкой. Человек подбирает
запрос на ходу, и терять из-за опечатки уже нарисованное — худшее, что
можно сделать.

### Граф движения запроса

На карточке трейса — картинка «куда пошёл запрос»: сервисы слева направо
по глубине вызова, стрелки с числом вызовов, временем и ошибками.

⚠️ Лента отвечает «когда», граф — «куда пошло и где встало». На ленте
видно порядок событий, но не устройство: тридцать строк подряд не
показывают, что checkout сходил в inventory дважды, а в payments один раз
и получил отказ. Человек восстанавливает это в голове по отступам, и на
трейсе из сотни спанов перестаёт восстанавливать вовсе.

В узле два числа, и второе важнее:

- **всего** — длительность спанов сервиса вместе с ожиданием;
- **своих** — время, которое сервис работал САМ, без ожидания тех, кого
  позвал.

Именно собственного времени не хватает, когда смотрят на длительность
спана: внешний спан длится столько же, сколько всё поддерево под ним,
поэтому «медленный» шлюз обычно не медленный — он ждёт. На живом трейсе
из стенда это видно сразу:

```
гл.0  checkout          вызовов 1  своих   0,0 мс  всего  33,0 мс
гл.1  payment-worker    вызовов 2  своих 141,0 мс  всего 173,0 мс
гл.1  orders-api        вызовов 3  своих  44,0 мс  всего  44,0 мс
гл.1  kitchen-display   вызовов 1  своих  13,0 мс  всего  13,0 мс

checkout → payment-worker   1×  141 мс
checkout → orders-api       3×   44 мс
checkout → kitchen-display  1×   13 мс
```

Раскладка по уровням вызова, а не пружинная симуляция: одна и та же
система должна выглядеть одинаково при каждом просмотре, иначе глазу
не на что опереться.

Сервисы, приславшие логи, но не спаны, тоже попадают на картинку —
выкинуть их значило бы нарисовать неполную схему и не сказать об этом.
Про оборванные связи система пишет прямо: «сервис, который их звал,
трейсы не отправляет».

### Стенд Mini App

Страница `/miniapp.html` открывает интерфейс в рамке телефона
с подставленным окружением мессенджера.

⚠️ Нужна потому, что Mini App нельзя проверить «просто открыв страницу».
Внутри мессенджера меняется почти всё: узкий экран, чужая палитра,
системная кнопка «назад», вибрация вместо всплывающих окон. Половина
этих отличий проявляется только там, и узнавать о них от дежурного
в четыре утра — плохой план.

Что даёт стенд:

- экран 390×844 — распространённый размер, на котором вёрстка ломается первой;
- палитры мессенджера: тёмная, светлая и **неполная** — разные версии
  присылают разный набор цветов, и недостающие должны оставаться своими,
  иначе текст становится невидимым на своём же фоне;
- журнал вызовов: всё, что интерфейс просит у мессенджера — вибрация,
  кнопка «назад», окна подтверждения;
- системная кнопка «назад» отдельно от браузерной.

⚠️ Вход по подписи `initData` здесь подделать нельзя — она проверяется
секретом бота на сервере. Стенд кладёт обычный токен доступа, а окружение
мессенджера подставляет ради вёрстки и поведения. Если бы подпись
подделывалась, это была бы дыра, а не стенд.

### История разборов

⚠️ **Счётчик инцидентов не говорит ничего.**

Сто инцидентов, из которых девяносто решены известным способом, и сто,
из которых ни один не решён, — это две разные системы с одинаковым
счётчиком. Поэтому каждая отработанная схема — и удачная, и нет —
попадает в отдельную таблицу истории и остаётся там неизменной.

Четыре исхода:

| Исход | Что значит |
|---|---|
| `helped` | решение применили, метрика подтвердила |
| `not_helped` | применили, метрика не подтвердила — разбор продолжается |
| `unresolved` | инцидент закрыт без решения |
| `open` | ещё разбирается |

Доля успеха считается **от закрытых** разборов: включать в знаменатель то,
что ещё разбирается, значит занижать её просто потому, что сейчас
что-то открыто.

Почему отдельная таблица, а не выборка из инцидентов. Инциденты живут
своей жизнью: их закрывают, удаляют вместе с истёкшими паттернами,
переоткрывают. История же обязана быть неизменной — это ответ на вопрос
«как система отработала за квартал», и он не может меняться задним числом.

Листается **курсором**, а не номером страницы. Смещение на глубоких
страницах заставляет базу пройти и выбросить все предыдущие строки, но
хуже другое: пока человек листает, приходят новые записи, всё съезжает,
и часть строк он увидит дважды, а часть не увидит вовсе.

Запись идёт в две точки. При открытии — там, где одновременно известны
заголовок события, уровень, с которым позвали ИИ, и посчитанное влияние;
дальше событие уходит в вебхук, и в коде его больше нет. При закрытии —
внутри самой операции закрытия, а не у каждого, кто закрывает: закрытий
четыре (автоматическая проверка, человек через `/outcome`, человек через
`/close`, ИИ через MCP), и разложив запись по всем четырём, мы получили бы
историю с дырами ровно в тех местах, про которые забыли.

Раз в десять минут история сверяется с инцидентами. ⚠️ Без этого разовый
сбой ломал бы её навсегда: между закрытием инцидента и записью итога база
может моргнуть, а повторить закрытие нельзя — оно отвергается как уже
сделанное, и второй попытки записать итог просто не наступает. Инциденты
здесь источник правды, история — производная от них. Той же сверкой
в историю попадают инциденты, закрытые до появления таблицы.

Роль `digest` видит этот экран и не видит логов: в логах бизнес-ключи
и суммы, а здесь — только то, как отработала система.

### Внутри мессенджера

Mini App — та же страница, но живёт по чужим правилам, и все они учтены:

- **Вход по подписи.** `initData` мессенджера проверяется HMAC-подписью
  по токену бота (`MINI_APP_SECRET`) с проверкой свежести. Токен вводить
  не нужно и негде: у человека с телефона нет доступа к переменным сервера.
- **Тема хозяина.** Берётся `themeParams` целиком, а не только светлая/тёмная,
  и перечитывается по событию `themeChanged`. Недостающие цвета остаются
  своими — иначе при неполной палитре получится нечитаемый текст.
- **Высота хозяина.** Своя `100dvh` в его webview врёт, и низ списка уезжает
  под клавиатуру; берётся `viewportStableHeight`.
- **Своя кнопка «назад».** На подробных экранах показывается системная
  кнопка мессенджера — рисовать рядом вторую незачем.
- ⚠️ **Вертикальный свайп отключён.** Иначе, листая ленту инцидентов,
  пользователь случайно закрывает приложение: этим же жестом мессенджер
  закрывает окно.
- ⚠️ **Диалоги свои, а не `alert()`/`prompt()`.** Внутри webview системные
  окна либо блокируются, либо выглядят чужеродно — а подтверждение исхода
  это главный сценарий Mini App.
- **Отклик на действие.** Кнопка без вибро-отклика на телефоне ощущается
  как несработавшая.
- **Меньше экранов.** Показываются инциденты, поиск и знание; сводка
  и широкие таблицы скрыты — «аналитику в Mini App не тащить» (§10.4 плана).

Объект хозяина ищется и как `window.Telegram.WebApp`, и как `window.WebApp`:
интерфейс Mini App сложился общий, и свой мессенджер может положить его короче.

## Поведение под нагрузкой

Раздел про то, что происходит, когда в узел пишут тысячи источников
одновременно. Все числа получены на прогонах, а не оценены.

### Ограничения памяти

Пять независимых пределов; срабатывает тот, который наступит раньше.
Первые два стоят ДО разбора, остальные — после.

| Предел | По умолчанию | Что ограничивает |
|---|---|---|
| `server.memory_limit` | лимит контейнера | цель сборщика мусора для всей кучи |
| `server.inflight_bytes` | 256 МБ | объём тел запросов, разбираемых одновременно |
| `ingest.queue_bytes` | 512 МБ | объём принятого, но ещё не записанного |
| `ingest.batch_bytes` | 32 МБ | объём одной пачки в памяти воркера |
| `ingest.queue_depth` | 200 000 | число записей в очереди |

⚠️ Предел по числу записей сам по себе бесполезен, когда сообщения бывают
по мегабайту: пять тысяч записей в пачке — это до пяти гигабайт в памяти
одного воркера, а воркеров столько же, сколько ядер. Поэтому объём считается
отдельно, и при его исчерпании источник получает `ErrQueueFull`, а не молчаливую
потерю: коллектор повторит из своей дисковой очереди.

**Почему одной границы очереди мало.** Очередь ограничивает уже
РАЗОБРАННОЕ. К моменту, когда она отвечает «полно», тело запроса уже
прочитано целиком и развёрнуто в объекты — то есть пик приходится
на стадию, которую очередь не видит. Сколько запросов разбирается
одновременно, не ограничивал никто: `net/http` и gRPC поднимают горутину
на соединение и не считают, сколько памяти те держат.

Замер: 200 одновременных запросов с телами по 1.5 МБ (296 МБ в сумме)
подняли кучу с 67 МБ до **1122–1312 МБ** по трём прогонам — вчетверо
больше объёма тел. Ничего в конфиге на это не влияло: пиковую память
задавало то, сколько источников совпало по времени.

⚠️ Стоит сказать и то, чего в этом замере НЕ было. Приём отработал
штатно: из двухсот запросов 109–115 приняты полностью, 7–11 частично,
остальные получили **503 с `Retry-After`** и внятным телом
(`rejectedLogRecords`, «очередь ingest переполнена»).
Ни одного оборванного соединения, ни одной молчаливой потери — это
и есть правильное поведение при перегрузке.

Проблема, значит, не в отказах, а в том, что **пик памяти ничем
не ограничен сверху**. На машине с 31 ГБ это просто цифра в метрике.
В контейнере с `limits.memory` тот же наплыв кончается OOM-killer,
и вот он теряет данные уже молча.

Поэтому приём берёт разрешение ДО чтения тела, а бюджет считается
в байтах, а не в числе запросов (запросы отличаются по размеру на три
порядка). Кому не хватило — ждёт две секунды и получает 503 с
`Retry-After`; для коллектора это штатный ответ, он повторит из дисковой
очереди.

**Почему без `memory_limit` этого всё равно мало.** Сборщик мусора Go
работает от GOGC: следующая уборка назначается, когда куча вырастет вдвое
относительно живых данных. Про лимит контейнера он не знает — такова
договорённость, лимит задаёт тот, кто запускает.

На том же замере, в один и тот же момент под нагрузкой: `heap_alloc`
636 МБ, а живых объектов по профилю кучи — 350 МБ. Почти половина
занятого — мусор, который сборщик не спешил забирать, потому что причины
спешить ему никто не назвал. В контейнере с лимитом
это заканчивается OOM-killer, и это худший из возможных исходов: очередь
принятого теряется целиком, хотя источники уже получили «ок», а сегменты
WAL остаются помеченными «в работе» — доливщик их не подхватит, и записи
не переиграются никогда.

`server.memory_limit` пуст по умолчанию и означает «взять из cgroup».
Процесс читает `/sys/fs/cgroup/memory.max` (или путь v1) и назначает себе
90% от него — остаток идёт на то, что в GOMEMLIMIT не входит: стеки,
буферы сокетов, сам код. Вне контейнера предел не назначается: выдуманное
число ограничило бы процесс на ровном месте.

Тот же замер с пределом 512 МБ и бюджетом приёма 256 МБ, по три прогона
на каждую настройку:

| | Пик кучи | Память процесса | Принято | Время |
|---|---|---|---|---|
| Без пределов | 1122–1312 МБ | 1284–1527 МБ | 109–115 | 2.8–3.2 с |
| С пределами | 756–826 МБ | 895–1030 МБ | 116–121 | 5.6–6.7 с |

⚠️ Читать эту таблицу надо целиком, включая последний столбец.
`GOMEMLIMIT` — это ЦЕЛЬ для сборщика, а не жёсткая стена: куча выходит
за 512 МБ и на пике доходит до 800, потому что предел заставляет убирать
чаще, а не запрещает выделять. Отсюда и время: при перегрузке процесс
тратит на уборку вдвое больше и работает медленнее. Это не побочный
эффект, а сама суть размена — притормозить и выжить вместо того, чтобы
разогнаться и быть убитым ядром. Принятых записей при этом не меньше,
а больше.

⚠️ Предел и ограничение приёма работают только в паре. Предел заставляет
сборщик убирать чаще; ограничение приёма не даёт мусору появляться
быстрее, чем его успевают забирать. Один предел без ограничения приёма
под нагрузкой сверх возможностей уводит процесс в непрерывную уборку
вместо работы.

Что смотреть: `watchgoose_ingest_queue_bytes`,
`watchgoose_ingest_inflight_bytes`, `go_memstats_heap_alloc_bytes`,
`go_gc_gomemlimit_bytes` и `watchgoose_ingest_dropped_total` с
`reason=inflight_bytes`.

### Размер сообщения

Не ограничен (`ingest.max_message_bytes: 0`). Стектрейс на мегабайт, дамп
запроса, ответ чужого API — хранятся целиком. Проверено сквозным прогоном
на 1, 4 и 9 МБ; отдельно проверена запись в Manticore на 16 МБ.

В разбор паттерна уходит только начало сообщения — `ingest.fingerprint_bytes`,
по умолчанию 4 КБ. Причин две: форма стектрейса определяется его головой,
а токенизация мегабайта на каждой записи съела бы процессор раньше,
чем закончилась бы очередь. Резать при этом надо по границе символа — иначе
многобайтный символ рвётся пополам и получается битый UTF-8.

### Кардинальность метрик

⚠️ Метка со значением из данных — прямой путь к неограниченному росту памяти.
`CounterVec` помнит каждое встреченное сочетание меток и не забывает его
никогда. Тысяча сервисов с именами подов вместо имён сервисов — это десятки
тысяч рядов; `/metrics` раздувается до мегабайтов, сборщик перестаёт успевать,
процесс уходит в OOM. Падает при этом именно та система, которая должна
показывать, что происходит с остальными.

Значения меток проходят через реестр с потолком (500 сервисов, 200 маршрутов).
Сверх потолка всё сходится в одно значение `прочее`, а факт срабатывания
потолка виден в `watchgoose_label_cardinality_capped_total` — это повод
посмотреть, что именно пишется в `service`.

⚠️ Этой метрики НЕ БУДЕТ в `/metrics`, пока потолок ни разу не сработал:
у счётчика с метками ряды появляются только после первого значения.
Ноль здесь выглядит как «метрики нет» — это норма, а не поломка,
и алерт на неё надо писать через `absent_over_time` или сравнение
с нулём по умолчанию.

Отдельно: метка маршрута считается ДО проверки доступа, на любом пути, включая
несуществующие. Идентификаторы в пути схлопываются в шаблон (`{id}`, `{fp}`,
`{trace}`), а итог всё равно проходит через тот же реестр — иначе перебор
адресов снаружи наращивал бы память процесса без всякой аутентификации.

### Живой хвост

Каждая подписка — запрос в Manticore раз в две секунды, пока открыта вкладка.
Ограничения: не больше 24 одновременных подписок (сверх — `429`), не дольше
30 минут одна подписка, и отдельный пятисекундный срок на запрос — иначе
два десятка подписок с медленными запросами выели бы пул соединений,
общий с приёмом, и остановили запись логов.

### Выгрузка

Процессы забираются партиями по 50: оба хранилища принимают несколько
идентификаторов одним запросом. Поштучный обход на двухстах процессах давал бы
около 400 запросов вместо 6 — замерено. Потолок одной выгрузки — 500 000 строк,
при его достижении в конец файла пишется явная отметка об обрезке.

### Замеренное

Все замеры — ноутбук, хранилища в Docker на той же машине. Это заведомо
худший случай: приём, Manticore и PostgreSQL делят одни ядра и один диск.

**Однородная нагрузка** (несколько отправителей, обычные логи):

| Что | Значение |
|---|---|
| Пропускная способность приёма | 124 000 записей/с (пик), 52 000 устойчиво |
| Задержка экспорта пачки в 500 записей | p50 32 мс, p95 65 мс, p99 95 мс |

**Флот из 1000 сервисов** (`wgsim --mode=fleet --services=1000 --conns=250`,
250 отдельных соединений, у каждого сервиса своё имя, свои формы сообщений
и свои бизнес-ключи; каждый двадцатый шумит втрое сильнее остальных).

⚠️ Замеры разведены намеренно. Смешивать обычные логи с мегабайтными
стектрейсами в одном числе нельзя: получится не «записей в секунду»,
а «мегабайт в секунду» под видом записей, и такое число несравнимо
ни с чем.

| | Обычные логи | Каждый 37-й сервис шлёт стектрейс на 1 МБ |
|---|---|---|
| Принято | **35 000 – 40 000 записей/с** | 15 018 записей/с |
| Объём текста | 420 МБ за 60 с | 8.7 ГБ за 100 с |
| Задержка пачки (50 записей) | p50 247 мс, p95 841 мс, p99 1.27 с | p50 67 мс, p95 290 мс, p99 436 мс |

Во втором столбце система упирается в пропускную способность по БАЙТАМ,
а не по записям: 87 МБ/с текста — это и есть предел записи в одиночный
контейнер Manticore на этой машине.

| Ресурс | Значение |
|---|---|
| Горутины | 599 в покое при 250 соединениях, пик 1206, после нагрузки 37 |
| Куча | пик 1110 МБ, через 70 с покоя 374 МБ живых и 779 МБ возвращено системе |
| Очередь | держалась на 310–357 МБ при потолке 512 МБ |
| Рядов в `/metrics` | 1824 (150 КБ) при тысяче сервисов — потолок реестра меток работает |

**Про отклонённые записи.** Генератор в этих прогонах предлагает около
100 000 записей/с — намеренно втрое больше, чем хранилище физически способно
записать. Разница уходит в отказы, и это проверяемое поведение, а не сбой:
источник получает `Unavailable`, повторяет из своей дисковой очереди,
а узел не растёт в памяти и не теряет данные молча. Именно это и проверялось.

Величина, которую стоит смотреть в эксплуатации, — не «сколько отклонено»,
а `watchgoose_ingest_queue_bytes`: если она подолгу стоит у потолка, приём
не успевает за источниками и роль `ingest` надо масштабировать.

**Огромные сообщения** (сквозной прогон OTLP → Manticore → поиск):

| Размер | Результат |
|---|---|
| 1.2 / 4.9 / 9.9 МБ | сохранены байт в байт, один fingerprint на все три |
| 16 / 32 / 48 МБ | сохранены целиком (17.1 / 34.3 / 51.4 МБ в хранилище), ошибок записи нет |

Верхняя граница — `server.max_body_bytes` (64 МБ по умолчанию): это потолок
на весь OTLP-запрос, а не на сообщение.

**Прочее:**

| Что | Значение |
|---|---|
| Тысяча сервисов × 20 записей | дерево паттернов 1 кластер, +3.9 МБ (тест `TestThousandServicesIngest`) |
| Выгрузка 200 процессов | 6 запросов к Manticore, 167 мс |
| Горутины после 4 всплесков по 24 подписки | 33, не растут |

### Где узкое место

Замер сделан профилировщиком и по процессорному времени процессов, а не
на глаз. Установившаяся нагрузка, тысяча сервисов, обычные логи:

| Потребитель | Процессор | Доля машины (12 ядер) |
|---|---|---|
| Manticore | 4.9 ядра | 41% |
| watchgoose | 3.3 ядра | 27% |
| PostgreSQL | 0.7 ядра | 6% |
| генератор нагрузки | 1.6 ядра | 13% |

Машина насыщена на ~87%, и самый крупный потребитель — **Manticore**,
а не наш код. Пока это так, дальнейшее ускорение приёма упирается
не в код: масштабируется разделением, роль `ingest` горизонтальна.

Профиль самого сервиса под этой нагрузкой, снятый **в контейнере**:

| Что | Доля процессора процесса |
|---|---|
| разбор protobuf | 23% |
| сборка мусора | 20% |
| системные вызовы | 11% |
| запись в хранилища (драйвер MySQL, JSON для WAL) | ~7% |
| собственная логика приёма | остальное |

Своего кода в верхушке профиля нет вовсе: сверху разбор входящего
формата и сборка мусора, которую этот же разбор и порождает. Дальнейшее
ускорение здесь означало бы отказ от protobuf, а не оптимизацию нашей
логики.

⚠️ Тот же профиль на бинарнике под Windows выглядел иначе: 38% занимали
системные вызовы через `stdcall` вместо 11%. Это разница платформ,
а не версий кода, — ещё одна причина мерить в контейнере.

**Что было исправлено по результатам профилирования:**

*Обновление каталога паттернов* стоило 1147 мс на пачку — дороже самой
записи логов. В пачке с тысячи сервисов сотни разных паттернов, и на каждый
шёл отдельный `INSERT ... ON CONFLICT`; восемь воркеров делали это
одновременно по пересекающимся строкам, добавляя ожидание на блокировках.
Переписано на один оператор с массивами и `ORDER BY fp`: **1147 → 255 мс**.

*Нормализация токенов* занимала 12% процессорного времени всего процесса —
больше, чем разбор protobuf. Причина: тринадцать регулярных выражений
прогонялись подряд на каждом токене каждой записи, а подавляющее
большинство токенов — обычные слова, где ни одно из них совпасть не может.
Добавлен отсев одним проходом по строке: **нормализация в 2.5 раза быстрее,
фингерпринтинг целиком в 2.8 раза**, регулярки ушли из верхушки профиля
(1.3% вместо 12.2%).

⚠️ Эта оптимизация проверяется не бенчмарком, а **эквивалентностью**:
нормализация определяет шаблон, шаблон определяет fingerprint, а fingerprint —
ключ ко всему накопленному знанию. Изменить её вывод хоть на одном токене
значит отвязать причины, статистику решений и историю инцидентов
от паттернов. Поэтому прежняя реализация сохранена в тестах как эталон,
и обе сверяются на корпусе из 200 000 токенов — включая граничные случаи
вокруг каждого правила.

### Ключевой факт: считать надо в мегабайтах, а не в записях

Пропускная способность узла определяется **объёмом текста**, а не числом
записей. Одна запись по 10 КБ стоит примерно как восемьдесят записей
по 120 байт. Поэтому «сколько записей в секунду выдержит» — вопрос,
на который нет ответа без размера сообщения.

Замеры на **контейнерном стеке** (`docker compose`, один узел, 12 ядер,
всё на одной машине вместе с генератором нагрузки — заведомо худший
случай; 1000 сервисов, 250 соединений, генератор шлёт на максимуме):

| Средний размер сообщения | Записей/с | МБ/с | Ядер на приём | Ядер на Manticore |
|---|---|---|---|---|
| 120 байт (обычный лог) | 25 300 | 3.0 | 3.2 | 5.4 |
| 10 КБ (лог с контекстом) | 3 350 | 34.3 | 2.0 | 3.2 |
| 64 КБ (дампы, трейсбеки) | 172 | 11.3 | 2.9 | 0.5 |

**Как читать эту таблицу.** Ни одно из чисел не является пределом,
заложенным в код: все три прогона упираются в процессор машины, где
приём, Manticore, PostgreSQL и сам генератор делят двенадцать ядер.

Видно и другое: узкое место переезжает вместе с размером сообщения.
На коротких логах больше всех работает Manticore (5.4 ядра против 3.2
у приёма) — платим за число документов. На десятикилобайтных, наоборот,
хватает двух ядер приёма и трёх Manticore, а пропускная способность
в мегабайтах вырастает вдесятеро. На шестидесятичетырёхкилобайтных
Manticore почти не при делах (0.5 ядра), зато приём занят разбором.

Величина, которая переносится на другое железо, — **стоимость на ядро**:
около 8 000 коротких записей в секунду на ядро приёма, или около
17 МБ/с на ядро при крупных сообщениях.

⚠️ Прежняя версия этой таблицы была снята с бинарника под Windows
и давала совсем другую картину: 1 430 записей/с на десяти килобайтах
вместо 3 350. Разница не в системе, а в платформе — под Windows 43%
процессорного времени уходило на системные вызовы. Мерьте в контейнере.

**Как этим пользоваться.** Возьмите свой поток в мегабайтах в секунду
(число сервисов × записей в секунду × средний размер) и разделите на
пропускную способность одного узла из таблицы. Это и есть число подов
роли `ingest`.

Пример: 1000 сервисов, по 5 записей в секунду, средний размер 10 КБ →
5000 записей/с × 10 КБ = **50 МБ/с**. По таблице один узел даёт 34 МБ/с,
значит нужно **2 узла** приёма плюс запас — берите 3.

⚠️ Числа получены на одной машине, где приём и хранилища делят ядра
и диск. На раздельном железе с SSD под Manticore они заметно выше;
таблицу стоит перемерить у себя тем же генератором:

```bash
./bin/wgsim --mode=fleet --endpoint=localhost:14317     --services=1000 --conns=250 --batch=50 --msg-size=10240 --duration=60s
```

### Пример расчёта: 1000 сервисов, 200 млн записей в сутки

Разбор конкретной цели по шагам — числа взяты из прогона на контейнерном
стеке (1000 сервисов, флот, всё на одной машине).

**Поток.** 200 000 000 / 86 400 = **2 315 записей/с в среднем**. Среднее
обманчиво: рабочий день даёт пик втрое-вчетверо выше среднесуточного,
то есть считать надо на **7 000–9 000 записей/с**.

**Процессор и память.** Замер на боевой сборке — весь стек поднят через
`docker compose`, watchgoose работает в контейнере с лимитом 2 ГБ,
поток ровно 2 315 записей/с от тысячи сервисов:

| Контейнер | Процессор | Память |
|---|---|---|
| **watchgoose** | **0.14 ядра** | **176 МБ** из 2 ГБ |
| manticore | 0.07 ядра | 524 МБ |
| postgres | 0.12 ядра | 91 МБ |
| clickhouse | 0.08 ядра | 415 МБ |
| остальное (victoria, vmagent, коллектор, grafana) | 0.02 ядра | 220 МБ |

Заявленный поток для узла — не нагрузка, а фон: **запас по процессору
больше чем двадцатикратный**. Предел памяти сборщик взял из лимита
контейнера сам, очередь держалась на 1 МБ, потерь ноль.

Пик втрое-вчетверо выше среднего остаётся столь же спокойным. Отдельный
прогон «сколько вообще выдержит» — с генератором, который шлёт настолько
быстро, насколько может, — дал 8 000–15 000 записей/с на одном узле.

⚠️ Числа сняты в контейнере под Linux, и это принципиально. Те же
замеры на бинарнике под Windows давали в разы худшую картину: по профилю
там 43% процессорного времени уходило на системные вызовы (`stdcall`),
которых в Linux-сборке нет. Если будете мерить у себя — мерьте
в контейнере, иначе получите характеристики платформы, а не системы.

**Вывод по железу.** Одного узла приёма достаточно с большим запасом.
Второй под роли `ingest` нужен не ради производительности, а ради
переживания перезапуска.

**Место на диске.** Замер по индексам стенда: **113–286 байт на запись**
после сжатия Manticore, в среднем **227 байт**. Разброс — от размера
сообщений; берите свой, разделив `disk_bytes` на `indexed_documents`
в `SHOW TABLE ... STATUS` после первых суток работы.

| Средний размер записи | В сутки | Бюджет на 30 суток | Бюджет на 90 суток |
|---|---|---|---|
| 113 Б (компактные логи) | 23 ГБ | 680 ГБ | 2.0 ТБ |
| 227 Б (замер стенда) | 45 ГБ | 1.4 ТБ | 4.1 ТБ |
| 500 Б (JSON с контекстом) | 100 ГБ | 3.0 ТБ | 9.0 ТБ |

⚠️ Считать надо не «сколько влезет», а наоборот: сколько места есть —
столько и задать в `retention.disk_budget`. Система сама выстроит под
него глубину и покажет прогноз (`storage_status`, экран «Хранение»).
При 200 млн записей в сутки и бюджете 1 ТБ глубина составит около
трёх недель по всем уровням — при том, что `dbg` уйдёт первым, а `err`
доживёт до предельного возраста.

**Память.** При заявленном потоке — 176 МБ из 2 ГБ лимита контейнера,
куча 132 МБ, очередь 1 МБ, потерь ноль. Ориентир для узла: **2 ГБ**
при сотне соединений, **4 ГБ** при двухстах и крупных сообщениях.

⚠️ Лимит контейнера задать ОБЯЗАТЕЛЬНО. Сборщик мусора Go про cgroup
не знает и без лимита растит кучу, пока процесс не убьёт ядро. С лимитом
watchgoose читает его сам и назначает себе предел в 90% от него —
в журнале это видно строкой «предел памяти взят из лимита контейнера».
Подробности — в разделе «Ограничения памяти».

### Аналитика во время приёма

Отдельный вопрос, и на центральном узле — главный: **не встаёт ли поиск,
пока идёт запись**. Хранилище у них общее, ядра общие, пул соединений
общий, и типичный способ узнать об этом — когда во время всплеска логов
перестаёт открываться интерфейс.

Замер на контейнерном стеке: тысяча сервисов пишет 2 315 записей/с,
одновременно четыре клиента непрерывно дёргают экраны интерфейса
и инструменты MCP.

| Что спрашиваем | Медиана | p99 |
|---|---|---|
| Проверка здоровья | 3–4 мс | 5–22 мс |
| Список инцидентов | 3–5 мс | 10–11 мс |
| Состояние хранения | 7–21 мс | 14–49 мс |
| MCP: паттерны ошибок | 28–165 мс | 56–366 мс |
| MCP: что сломалось | 30–381 мс | 55–571 мс |
| Поиск по логам | 104–865 мс | 164–1116 мс |
| Поиск по тексту | 150–1022 мс | 332–1430 мс |

⚠️ Разброс в таблице настоящий, и его стоит объяснить — вместе
с признанием ошибки в прежнем объяснении.

Сначала было написано, что запрос без полнотекстовой части исполняется
полным сканом и потому дорог. **Это неверно.** Числа были сняты через
`docker compose exec` с запуском mysql-клиента, а он один стоит 450 мс —
столько же показывал и `SELECT 1`. То есть измерялась обёртка, а не
запрос.

Настоящие времена (`SHOW META`, 6 млн записей в базе):

| Запрос | Время |
|---|---|
| `order_id='...'` — точное совпадение | 3 мс |
| `MATCH('несуществующее слово')` | 1 мс |
| `MATCH('обработан')` — миллионы совпадений | 21 мс |
| `level='ERROR'` | 24 мс |

Атрибуты индексируются колоночным движком (`engine = columnar`),
текст — инвертированным индексом. Скана нет ни там ни там.

**Что действительно стоило денег — `max_matches`.**

`max_matches` у Manticore — это размер очереди сортировщика: он собирает
столько строк ЦЕЛИКОМ, со всеми колонками, включая `message` и `attrs`,
и только потом отдаёт запрошенные пятьдесят. Стоимость выходит
пропорциональна не объёму данных и не числу совпадений, а этому числу,
помноженному на ширину строки.

Замер на 284 тысячах совпадений (`level='ERROR'`), 19 колонок, `LIMIT 50`:

| | |
|---|---|
| `max_matches=50` | 9 мс |
| `max_matches=1000` | 133 мс |
| `max_matches=5000` | 687 мс |
| `max_matches=5000`, но `SELECT id` | 27 мс |

Последняя строка показывает, что платится именно за материализацию строк,
а не за поиск.

⚠️ **И здесь была ошибка, которая делала поиск медленным.** В каждый
запрос уходил потолок из конфига — пять тысяч, — независимо от того,
сколько строк просил клиент. На пятидесяти запрошенных строках Manticore
собирал пять тысяч и 4950 выбрасывал.

Теперь `max_matches` считается из запроса: `limit + offset` с небольшим
запасом, ограниченный потолком из конфига. Выдача **побайтово та же** —
проверено сравнением всех пятидесяти строк при `max_matches` от 50
до 20000. Через API на живом стенде:

| Запрос | Было | Стало |
|---|---|---|
| `level:ERROR`, 50 строк | 768 мс | **39 мс** |
| `level:ERROR`, 200 строк | 793 мс | **72 мс** |
| `service:service-0427` | 156 мс | **27 мс** |
| `level:ERROR AND connection` | 7 мс | 9 мс |
| `order_id:779190` | 14 мс | 13 мс |

Точечные запросы и так были быстрыми — они просили мало строк. Страдали
именно широкие фильтры, то есть самый частый способ начать разбор.

Занижать `max_matches` ниже `limit + offset` нельзя: Manticore вернёт
**пусто**, а не «неточно» — проверено, `limit=50 offset=200` при
`max_matches=100` даёт ноль строк. Ровно поэтому значение считается
из запроса, а не задаётся руками. Настройка в конфиге осталась и работает
как потолок глубины пагинации: уйти на сотую страницу и заставить базу
собрать полмиллиона строк нельзя.

Сузить запрос по-прежнему полезно, но уже не ради `max_matches`:

- окно времени: час вместо суток;
- уровень: `level:ERROR` уходит в свою корзину, а это в разы меньше
  документов;
- любое избирательное поле: `order_id`, `trace_id`, `event`.

Второй источник разброса — конкуренция. Под приёмом на полной скорости
поиск замедляется в разы: Manticore пишет и читает одними и теми же
ядрами.

**Кириллица в поиске работает** — и по тексту, и в значениях атрибутов
(`service:мой-сервис`, `order_id:ЗАКАЗ-1024`). Это стоит сказать прямо,
потому что при проверке через оболочку Windows кириллица в аргументах
уходит не в UTF-8, запрос доезжает битым, и выглядит это как «поиск
не находит русское».

### Готовый профиль под тысячу сервисов

Умолчания рассчитаны на десятки сервисов. На тысяче часть из них мала,
причём мала ТИХО: система работает и ошибок не пишет, а качество разбора
и запас по памяти уходят незаметно.

Готовый набор с объяснением каждого значения — `deploy/watchgoose-1000.yaml`.
Оттуда стоит взять целиком, а не выборочно; самое важное:

| Настройка | Умолчание | В профиле | Что будет иначе |
|---|---|---|---|
| `server.memory_limit` | не задан | из лимита контейнера | без него процесс растёт до OOM |
| `server.inflight_bytes` | 256 МБ | 512 МБ | пик памяти приёма не ограничен |
| `ingest.fingerprint.max_clusters` | 5 000 | 50 000 | инциденты перестают склеиваться |
| `ingest.workers` | 4 | 8 | запись отстаёт от приёма |
| `postgres.max_conns` | 16 | 48 | запросы ждут соединения |
| `manticore.max_conns` | 16 | 48 | поиск ждёт за спиной записи |
| `retention.disk_budget` | не задан | 1 ТБ | глубина хранения не планируется |

⚠️ Отдельно про `ingest.fingerprint.max_clusters` — это самая незаметная
из них. Дерево шаблонов ограничено сверху нарочно, иначе мусорные
сообщения раздували бы его без предела. Но когда потолок ВЫБРАН, новые
шаблоны перестают обобщаться: отпечаток остаётся устойчивым, а шаблоном
становится само сообщение целиком.

Ломается при этом не приём, а всё, что стоит после: каждое непохожее
сообщение становится отдельным «паттерном», инциденты не склеиваются,
накопленное знание к новым отпечаткам не привязывается. Со стороны это
выглядит как «система вдруг стала шуметь» — без единой ошибки в журнале.

Следите за парой `watchgoose_fingerprint_clusters` и
`watchgoose_fingerprint_clusters_max`: запас должен быть двукратным.

### Настройки под ваш профиль

| Профиль | `batch_bytes` | `queue_bytes` | `max_message_bytes` | `fingerprint.max_tokens` |
|---|---|---|---|---|
| Обычные логи (до 1 КБ) | 4 МБ | 512 МБ | 0 | 80 |
| Логи с контекстом (5–50 КБ) | 1–4 МБ | 512 МБ – 1 ГБ | 0 | 80 |
| Дампы и трейсбеки (сотни КБ) | 1 МБ | 1–2 ГБ | 0 | 40 |

⚠️ **Больше `batch_bytes` — не лучше.** Пачка материализуется в памяти
трижды: срез записей, текст `INSERT` и копия, которую строит драйвер при
экранировании значений. На замерах с сообщениями по 10 КБ пачка в 1–4 МБ
давала на треть больше пропускной способности, чем в 32 МБ, при втрое
меньшей куче. Умолчание — 4 МБ.

Память узла приёма считается так:

```
пик ≈ queue_bytes + workers × batch_bytes × 3 + запас на соединения
```

Для умолчаний (512 МБ + 8 × 4 МБ × 3 + запас) это около 1 ГБ. Ставьте
лимит пода вдвое выше расчётного: пики при всплесках реальны.

### Что смотреть в эксплуатации и что делать

| Метрика | Что означает | Что делать |
|---|---|---|
| `watchgoose_ingest_queue_bytes` подолгу у `queue_bytes` | приём не успевает за источниками | добавить подов роли `ingest`; если не помогло — узкое место в Manticore |
| `watchgoose_ingest_dropped_total{reason="queue_full"}` растёт | источники получают отказ и повторяют | то же самое; само по себе не потеря данных, но задержка растёт |
| `watchgoose_ingest_dropped_total{reason="queue_bytes"}` растёт | упёрлись в память, а не в число записей | сообщения крупные: уменьшить `batch_bytes`, увеличить `queue_bytes` |
| `watchgoose_label_cardinality_capped_total` растёт | в `service` попадает не имя сервиса | почти всегда имя пода вместо имени сервиса; чинить на стороне источника |
| `watchgoose_wal_bytes` растёт | Manticore недоступен, пачки копятся на диске | проверить Manticore; при `on_full=drop_oldest` данные начнут теряться |
| `watchgoose_ingest_flush_duration_seconds` растёт | Manticore пишет медленнее | диск под Manticore, либо пора делить индексы |
| `go_goroutines` растёт монотонно | утечка | снять профиль: `/api/v1/debug/pprof/goroutine` |

### Ротация и удаление старых данных

Логи лежат в **посуточных индексах** по корзинам уровня: `logs_err_20260805`,
`logs_info_20260805` и так далее. Поверх них стоят distributed-зонтики
(`logs`, `logs_err`, …) — через них идёт поиск.

| Задача | Расписание по умолчанию | Что делает |
|---|---|---|
| `rotation` | `5 0 * * *` | создаёт индексы на сегодня и завтра |
| `retention` | `25 * * * *` | удаляет просроченные, при нехватке диска — ещё и по приоритету |
| `archive_upload` | `0 2 * * *` | выгружает завершившиеся сутки в S3 |
| `archive_retention` | `0 2 * * *` | удаляет из архива батчи старше срока |
| `archive_slots` | `@every 1m` | закрывает дни, которые перестали смотреть |

Завтрашний индекс создаётся заранее: перекос часов на источнике не должен
упираться в отсутствующую таблицу. Если запись всё же пришла в день,
для которого индекса нет, приём создаёт его на месте и повторяет вставку.

⚠️ **Сроков по уровням нет, есть один общий бюджет.** Пока доля логов
занята меньше чем на 85%, не удаляется ничего. Выше — уходят самые старые
сутки, целиком, со всеми уровнями сразу. Сегодняшние и завтрашние сутки
не удаляются никогда.

Раньше здесь были сроки по уровням (90/30/14 дней и сутки для DEBUG),
ватерлиния `disk_high_watermark` и веса сервисов. Всё это убрано: подробно
о том, почему, — в разделе «Хранение».

⚠️ **Порядок операций при удалении принципиален.** Зонтик — это
distributed-таблица, перечисляющая локальные индексы поимённо, и Manticore
не умеет переопределять её иначе как через `DROP` + `CREATE` (`ALTER`
её не берёт). Поэтому:

1. зонтик пересобирается БЕЗ обречённых индексов;
2. только потом они удаляются с диска.

Обратный порядок оставляет зонтик со ссылками на удалённые таблицы, и всё
это время **каждый поиск падает** с `unknown local table`. На удалении
пятнадцати индексов это секунды полной неработоспособности поиска, а не
миллисекунды. Проверено под нагрузкой: до исправления один запрос из 228
падал, после — 332 запроса подряд без единого сбоя при удалении 28 индексов.

Остаточное окно — сама пересборка зонтика (`DROP` и `CREATE` идут не
атомарно). Оно миллисекундное, и запрос, попавший в него, повторяется
автоматически; счётчик повторов — `watchgoose_manticore_umbrella_retries_total`.

Проверка ротации под нагрузкой (200 сервисов, ~8 000 записей/с, удаление
28 просроченных индексов одновременно с приёмом):

| Что | Результат |
|---|---|
| Поиск во время удаления | 332 запроса, 0 сбоев |
| Приём | не прерывался, 8 000 записей/с |
| Повторов из-за пересборки зонтика | 0 |
| Индексов удалено | 28 из 36 |

### Бюджет хранения

Главный рычаг управления местом. Вместо «храни логи 14 дней» вы говорите
системе, **сколько места ей выделено**, а глубину хранения она выстраивает
сама.

```yaml
retention:
  disk_budget: "200GB"       # сколько места система себе позволяет
  budget_soft_ratio: 0.85    # с какой занятости начинать уборку
  max_drops_per_run: 3       # сколько индексов убирать за прогон
```

Логика обратна привычной. Обычная политика отвечает на вопрос «когда пора
удалять» и удаляет по расписанию, даже когда места вдоволь. Бюджет отвечает
на другой вопрос — «сколько мы можем себе позволить»:

| Занято | Что делает система |
|---|---|
| меньше 85% бюджета | **не удаляет ничего**: место выделено, пусть хранит как можно глубже |
| выше 85% | убирает самое старое и наименее ценное, ровно столько, чтобы вернуться под порог |
| выше 100% | то же самое, но в журнале появляется предупреждение |

Порядок удаления: `dbg` → `info` → `warn` → `err`, внутри уровня — от
самого старого. Ошибки держатся до последнего.

**Изменение бюджета на живой системе.** Уменьшили с терабайта до ста
гигабайт — лишнее уйдёт постепенно, по `max_drops_per_run` индексов
за прогон уборки. ⚠️ Плавность здесь не косметика: обвальное удаление
половины истории необратимо, а постепенное даёт время передумать
и вернуть бюджет обратно. Увеличили бюджет — удаление прекращается
немедленно.

⚠️ **Считается СВОЙ объём, а не свободное место раздела.** Раздел может
делиться с чужими данными: ориентируясь на него, система либо удаляла бы
своё из-за чужого роста, либо не удаляла вовсе, пока сосед не заполнит диск.

⚠️ **Сегодняшний и завтрашний индексы не удаляются никогда** — в них идёт
запись. Их объём в бюджете учитывается, но тронуть их нельзя. Если весь
объём лежит именно в них, система физически не может вернуться под бюджет
и честно об этом говорит: в журнале появляется предупреждение, а метрика
`watchgoose_retention_stuck` встаёт в единицу. Лечится либо увеличением
бюджета, либо уменьшением притока.

Предельные сроки (`retention.error` и остальные) при этом продолжают
работать как **верхняя граница возраста**: они нужны там, где хранить
дольше нельзя по регламенту. Хотите, чтобы глубиной управлял только
бюджет, — поставьте их в ноль.

**Где это видно.** Состояние хранения доступно всем, кто принимает
решения по истории:

| Кому | Как |
|---|---|
| человеку | плашка на экране инцидентов — и в браузере, и в мини-приложении |
| ИИ | инструмент MCP `storage_status` |
| мониторингу | `watchgoose_retention_budget_bytes`, `..._used_bytes`, `..._forecast_days`, `..._days_kept{bucket}`, `..._stuck` |
| скриптам | `GET /api/v1/storage` |

⚠️ Модели это нужно не «для полноты картины». Она строит выводы по истории:
сравнивает всплеск с базовой линией, ищет похожие случаи, смотрит, было ли
такое раньше. Если глубина хранения — трое суток, а она рассуждает о «том же
самом месяц назад», вывод будет уверенным и неверным.

Пример ответа:

```json
{
  "budget_human": "186.3 ГиБ",
  "used_human":   "70.1 ГиБ",
  "budget_ratio": 0.376,
  "per_day_human": "5.4 ГиБ",
  "forecast_days": 34.2,
  "days_kept": {"err": 90, "warn": 30, "info": 13, "dbg": 1}
}
```

### Опечатки в конфиге

Неизвестный ключ в конфиге — **ошибка запуска**, а не предупреждение.

⚠️ Молчаливое игнорирование настройки хуже явной ошибки. Человек пишет
`retention: {default: 2h}`, уверен, что старое удаляется через два часа,
а работают умолчания — и узнаёт об этом, когда кончится диск. Проверено
на себе: при первом прогоне ротации конфиг был написан несуществующими
ключами и молча не применился, а `ingest.wal_dir` (правильно
`ingest.wal.dir`) тихо не работал во всех тестовых конфигах подряд.

Допустимые ключи берутся из самой структуры конфига, поэтому список
не может разойтись с кодом.

### Профилирование

Профилировщик доступен под тем же токеном, что и остальной API:

```bash
curl -H "Authorization: Bearer $TOKEN"   "$WG/api/v1/debug/pprof/profile?seconds=30" -o cpu.prof
go tool pprof -top cpu.prof
```

⚠️ Открытым его оставлять нельзя: профиль содержит имена функций, адреса
и куски данных из памяти процесса, а сам сбор притормаживает процесс.

Профили блокировок и ожиданий по умолчанию **выключены**: их сбор не
бесплатен — каждая операция с замком дополнительно учитывается. Включаются
явно, когда есть подозрение на конкуренцию за замки:

```yaml
server:
  profile_mutex_fraction: 5    # учитывать каждое 5-е событие блокировки
  profile_block_rate: 10000    # ожидания дольше 10 мкс
```

```bash
curl -H "Authorization: Bearer $TOKEN" "$WG/api/v1/debug/pprof/mutex" -o mutex.prof
go tool pprof -top mutex.prof
```

Именованные профили (`heap`, `goroutine`, `allocs`, `mutex`, `block`,
`threadcreate`) доступны каждый по своему пути.

⚠️ Изначально они были недоступны: стандартный `pprof.Index` определяет
имя профиля, отрезая от пути префикс `/debug/pprof/`, и с префиксом
`/api/v1` ничего не находил — все шесть путей отдавали одну и ту же
страницу оглавления на 2597 байт. Ошибки при этом не было, поэтому
заметить можно было только сравнив ответы. Каждый профиль теперь
зарегистрирован отдельным обработчиком.

### Где предел и почему

Разбор профиля под нагрузкой — в разделе «Поведение под нагрузкой».
Коротко: сверху разбор входящего protobuf (23%) и сборка мусора (20%),
которую этот же разбор и порождает. Собственной логики приёма
в верхушке профиля нет.

Отсюда и потолок: дальнейшее ускорение упирается не в наш код,
а в стоимость разбора формата. Масштабируется это не оптимизацией,
а разделением — роль `ingest` горизонтальна.

## Подключение своих сервисов

Раздел для тех, кто пишет сервисы, а не эксплуатирует Watchgoose.
Он отвечает на три вопроса: куда слать, что слать и как это сделать
за пять минут.

### Куда слать

Все три сигнала идут по одному адресу — в коллектор. Отдельных адресов
для логов, трассировок и метрик нет; адрес зависит только от того,
откуда шлёт приложение.

| Откуда шлёт приложение | gRPC | HTTP |
|---|---|---|
| С другой машины | `ДОМЕН:4317` | `https://ДОМЕН:4318` |
| С самого сервера Watchgoose | `localhost:14317` | `http://localhost:14318` |
| Из контейнера в сети стека | `otel-collector:4317` | `http://otel-collector:4318` |

Снаружи порты `4317` и `4318` держит Caddy и проксирует их в коллектор.
Обращаться нужно именно по тому имени, под которым установлен стек
(`ДОМЕН`): запрос на IP-адрес сервера в эти блоки не попадёт.

⚠️ Caddy поднимается в профиле `tls`. Если при установке выбран режим
без сертификата, наружу не открыт ни один порт — ни приёма, ни
интерфейса; слать можно только с самого сервера.

Аутентификация — заголовок `Authorization: Bearer <INGEST_TOKEN>`.
Проверяется на входе в коллектор, до разделения по сигналам, поэтому
нужна одинаково всем трём.

Принятое коллектор раскладывает сам:

| Что | Где оседает |
|---|---|
| **Логи** | Watchgoose → Manticore |
| **Трассировки** | ClickHouse |
| **Метрики** | VictoriaMetrics |

⚠️ **Метрики тоже идут в коллектор, по OTLP.** `vmagent` чужие сервисы
не обнаруживает: в `deploy/scrape.yml` перечислены вручную только цели
самого стека. За `/metrics` вашего сервиса никто не придёт, пока вы
не впишете его туда сами — см. «Метрики» ниже.

⚠️ **Трассировки и метрики принимает только коллектор.** Watchgoose
берёт логи и ничего больше: отправленные ему напрямую трассировки
встречают отказ с названной причиной.

```
Unimplemented: watchgoose принимает только логи;
               трейсы сюда слать не нужно — коллектор пишет их прямо в ClickHouse
```

Прямой приём логов в Watchgoose существует, но пользоваться им обычно
незачем:

- порты `4317`/`4318` самого Watchgoose на хост не публикуются — адрес
  `watchgoose:4318` виден только контейнеру, подключённому к сети стека;
- в обход коллектора теряется его дисковая очередь: пока Watchgoose
  перезапускается, коллектор держит логи на диске и досылает их потом.

Таблица описывает поставку через `docker compose`. В установке через Helm
у приёмника свой сервис `<release>-watchgoose-ingest` с портами
`4317`/`4318`: внутри кластера логи можно слать прямо в него, наружу
Ingress отдаёт только API.

### Обязательный набор атрибутов

Watchgoose опирается на девять атрибутов. Шесть задаются один раз при
подключении, седьмой — на каждой записи, два подставляются
из трассировки.

| Атрибут OTLP | Что определяет | Из окружения | Поиск |
|---|---|---|---|
| `service.name` | имя сервиса | — | `service:payments` |
| `service.version` | версия сборки | `WATCHGOOSE_SERVICE_VERSION`, `SERVICE_VERSION`, `OTEL_SERVICE_VERSION` | `service_version:1.4.2` |
| `service.instance.id` | экземпляр: под, контейнер, процесс | `WATCHGOOSE_INSTANCE_ID`, `POD_NAME`, `HOSTNAME` | `service_instance_id:…` |
| `service.kind` | категория: `application`, `infrastructure`, `integration`, `job` | `WATCHGOOSE_SERVICE_KIND` | `service_kind:application` |
| `deployment.environment` | контур | `WATCHGOOSE_ENV` | `env:prod` |
| `host.name` | узел | имя машины | `host:worker-3` |
| `component` | часть сервиса: `http`, `db`, `cache`, `queue`, `client`, `domain`, `scheduler`, `startup` | — | `component:db` |
| `trace_id`, `span_id` | цепочка вызова | активный спан | `trace_id:…` |

Клиентские библиотеки подставляют, что могут, из окружения
и перечисляют недостающее через `OnError` при запуске.

Приёмник проверяет набор сам: `ingest.require.mode` принимает `off`,
`warn` (по умолчанию) и `reject`. В режиме `reject` записи с неполным
набором не принимаются; в `partialSuccess` ответа OTLP возвращается
их число и перечень недостающих атрибутов. Записи из `partialSuccess`
отправитель не повторяет — так определено протоколом.

⚠️ Переключать на `reject` только после того, как показатель
`watchgoose_ingest_invalid_total` перестал расти: он разложен
по сервисам и атрибутам, видно поимённо, кто ещё не обновил телеметрию.

⚠️ Когда между сервисом и приёмником стоит коллектор, ответ приёмника
до сервиса не доходит: коллектор отвечает сразу, приняв пачку в очередь.
Отбраковка видна в журнале коллектора (`Partial success response`)
и в показателе. Для проверки нового сервиса пошлите пачку приёмнику
напрямую — из контейнера в сети стека на `http://watchgoose:4318/v1/logs`,
в установке через Helm на `<release>-watchgoose-ingest:4318`. С хоста
такого адреса нет: порты приёмника наружу не публикуются.

⚠️ Две ловушки .NET, на которых спотыкаются почти все.

**Первая:** имена `ActivitySource` и `Meter` надо перечислить в настройках
явно. OpenTelemetry собирает только названные источники — не названный
не собирается. Ошибки при этом нет: телеметрия «подключена», а трейсов
и метрик нет.

**Вторая:** хост надо ЗАПУСТИТЬ (`app.Run()` или `app.StartAsync()`).
OpenTelemetry поднимает провайдеры фоновой службой хоста; без запуска
`StartActivity` возвращает `null`, а значит нет ни спанов, ни `trace_id`
в логах. Тоже молча.

Обе поймались на живом прогоне при написании этой документации.

⚠️ И третья, общая: подключайтесь через `AddWatchgooseTelemetry`
(или `AddWatchgoose`, если нужны только логи), а не через
`AddProvider(new WatchgooseLoggerProvider(...))`. Контейнер .NET
освобождает только те объекты, которые создал сам: провайдер, отданный
готовым экземпляром, никогда не будет закрыт — и накопленная пачка
не отправится. Пропадут последние записи перед остановкой, то есть ровно
те, ради которых в лог потом и полезут.

Дальше — обычный код:

```python
from opentelemetry import metrics, trace

meter = metrics.get_meter("orders")
orders_total = meter.create_counter("orders_total")

with trace.get_tracer("orders").start_as_current_span("обработка заказа"):
    # trace_id подставится САМ из активного спана
    logging.getLogger("orders").error(
        "оплата не прошла: банк вернул отказ",
        extra={"component": watchgoose.Components.CLIENT,
               "event": "payment.failed",
               "order_id": order_id,
               "amount_cents": amount})

orders_total.add(1, {"result": "failed"})
```

Исходящий вызов — через `outgoing()`, он и заголовки отдаёт,
и оставляет след вызова в трейсе:

```python
with watchgoose.outgoing("POST payments") as headers:
    requests.post(url, headers=headers)
```

Замеры (контейнер, против настоящего Watchgoose): вызов `log.info()`
обходится сервису в **13.6 мкс**, из которых 6.9 — сам стандартный
`logging`. Сквозная доставка с шестнадцати потоков — **10 500 записей/с**
без потерь. Подробнее — README репозитория
[`watchgoose-client-python`](https://git.smorodi.ru/infrastructure-public/watchgoose-client-python).

⚠️ Три ловушки Python, все молчаливые.

**Первая, и самая опасная: gunicorn форкает воркеров, а фоновый поток
форк не переживает.** Если клиент создан до форка — а в Flask-приложении
так и бывает, на уровне модуля, — в дочернем процессе останется очередь
без того, кто её разбирает. Логи будут «отправляться» и копиться
в памяти, пока не упрутся в потолок, и ни одной ошибки при этом.
Модуль поднимает отправщика заново через `os.register_at_fork`, но знать
про это стоит: своя телеметрия в чужом коде страдает тем же.

**Вторая: перезагрузчик Flask запускает процесс дважды.** С `debug=True`
или `use_reloader=True` телеметрия поднимется в двух процессах — две
очереди, два набора метрик, путаница в трейсах. В проде перезагрузчика
нет, но на стенде это сбивает с толку.

**Третья: заголовки HTTP регистронезависимы, а словарь — нет.** Werkzeug
отдаёт `Traceparent` с большой буквы, а извлекатель OpenTelemetry ищет
точное `traceparent` и молча ничего не находит. Выглядит как
«трассировка работает, только сервисы почему-то в разных трейсах».
Модуль приводит ключи к нижнему регистру сам; поймано на первом же
прогоне примера.

#### Полные примеры

Куски выше показывают устройство, но копировать лучше готовое:

| Язык | Пример |
|---|---|
| Go | `watchgoose-client-go/example` — `go run . -collector=localhost:14317` |
| C# | `watchgoose-client-csharp/Example` — `dotnet run -- --collector http://localhost:14317` |
| Python | `watchgoose-client-python/example` — `python app.py --collector localhost:14317` |

Адреса — для запуска на самом сервере Watchgoose. Из контейнера в сети
стека это `otel-collector:4317`, с другой машины — `ДОМЕН:4317` и токен
в `Authorization`.

Это работающие программы, не выдержки. В каждой поднимаются два
обработчика — «заказы» и «оплата», — и заказы ходят в оплату по HTTP.
Так видно то, ради чего трассировка и нужна: она проходит НАСКВОЗЬ через
сетевой вызов.

Что получается на выходе — проверено на живом стенде, все три языка:

```
POST /orders (Server)              ← запрос пришёл в заказы
└─ оплата заказа (Internal)        ← бизнес-шаг
   └─ POST payments (Client)       ← заказы зовут оплату
      └─ POST /pay (Server)        ← оплата приняла ТУ ЖЕ цепочку
```

Все логи обоих обработчиков — с одним `trace_id`, метрики с разбивкой
по результату: `orders_total{result="ok"} = 4`, `{result="failed"} = 2`.

#### Прокидывание трассировки: что именно надо сделать

Связь между сервисами держится на заголовке `traceparent`. Вызывающий
кладёт в него свою цепочку, вызываемый достаёт и продолжает.

⚠️ Это самая частая причина, по которой «трассировка есть, а толку нет».
Каждый сервис по отдельности создаёт свои спаны, а связи между ними
не возникает: цепочка обрывается на каждом сетевом вызове, и вместо
одной картины получается набор огрызков.

Руками делать ничего не нужно — в обеих библиотеках это готово:

**Go** — заверните сервер и клиента:

```go
// входящие запросы: достать цепочку и продолжить
http.ListenAndServe(":8080", watchgoose.Middleware(mux))

// исходящие вызовы: положить цепочку в заголовок
client := &http.Client{Transport: watchgoose.Transport(nil)}
```

⚠️ Запрос обязан создаваться через `http.NewRequestWithContext` с тем
самым `ctx`, в котором живёт спан. Обычный `http.NewRequest` контекста
не несёт, и цепочка оборвётся молча: запрос уйдёт, ответ придёт,
а связи в трейсе не будет.

**C#** — включается настройкой, дальше само:

```csharp
o.InstrumentAspNetCore = true;   // входящие запросы
o.InstrumentHttpClient = true;   // исходящие вызовы
```

⚠️ Для исходящих берите клиента из `IHttpClientFactory`
(`builder.Services.AddHttpClient()`). Созданный через `new HttpClient()`
инструментацией не оборачивается, и заголовок не уйдёт.

#### Что делают обе библиотеки

Не блокируют ваш код · копят пачками · повторяют только то, что стоит
повторять (429 и 5xx — да, 401 — нет) · дописывают накопленное при
остановке · раскладывают бизнес-ключи по колонкам · подставляют
`trace_id` сами.

Проверено не только тестами, но и прогоном против стека, поднятого через
`docker compose`: логи с `trace_id` дошли до Watchgoose, спаны —
до ClickHouse, счётчики и гистограммы — до VictoriaMetrics. Оба языка.

### Что слать: поля, которые дают отдачу

Watchgoose раскладывает часть атрибутов по отдельным колонкам. По ним
можно искать, группировать и связывать записи между сервисами; всё
остальное тоже сохраняется и ищется, но колонкой не становится.

| Атрибут | Зачем |
|---|---|
| `service.name` | имя сервиса. **Не имя пода** |
| `deployment.environment` | prod / stage / dev |
| `host.name` | узел; сюда и кладите имя пода |
| `service.version` | привязка ошибки к релизу |
| `trace_id`, `span_id` | связь лога с трассировкой |
| `event` | короткое имя события: `order.created` |
| `order_id`, `payment_id`, `user_id` | история одной сущности через все сервисы |
| `amount_cents` | сумма **в копейках, целым числом** |
| `region`, `point_id`, `point_type`, `tariff` | разрезы для группировки |

Три правила, которые окупаются больше всего:

1. **Имя сервиса стабильное.** `orders` — да, `orders-7d9f8b-x2k1` — нет.
   Имя пода меняется при каждом рестарте: разбивка по сервисам
   превратится в мусор, а реестр меток на приёмнике переполнится
   и начнёт схлопывать источники в «прочее».

2. **`event` без идентификаторов.** `payment.failed` — да,
   `payment.PAY-77.failed` — нет. Из стабильных имён событий система
   строит пути бизнес-процессов и ловит обрывы: «заказ создан, оплата
   ушла, подтверждения нет». Идентификаторы для этого есть в своих полях.

3. **`trace_id` везде, где он есть.** Без него инцидент разбирается
   по времени и наитию; с ним видна вся цепочка вызовов вокруг ошибки,
   включая соседние сервисы. Обе библиотеки подхватывают его сами —
   Go из контекста (`watchgoose.WithTrace`), C# из `Activity.Current`.

⚠️ Длину сообщения ограничивать не надо. Стектрейс на мегабайт — обычное
дело, и обычно именно он и нужен при разборе. Watchgoose такие сообщения
принимает целиком (проверено на 48 МБ), а паттерн определяет по началу,
так что длинный хвост ничего не стоит.

### Метрики

Штатный путь — **OTLP в коллектор**, тем же клиентом и по тому же адресу,
что логи и трассировки. Коллектор кладёт метрики в VictoriaMetrics.

Второй путь — свой `/metrics` в формате Prometheus. ⚠️ Сам по себе он
не работает: `vmagent` ничего не обнаруживает, в `deploy/scrape.yml`
только `static_configs` с вручную перечисленными целями самого стека.
Сервис надо вписать туда руками и перезапустить `vmagent`, а цель должна
быть доступна ему по внутренней сети стека.

```yaml
scrape_configs:
  - job_name: orders
    static_configs:
      - targets: ["orders:8080"]
```

⚠️ Метка со значением из данных — самый частый способ уронить хранилище
метрик. Идентификатор заказа, `trace_id`, имя пода в метке означают,
что число рядов растёт вместе с трафиком и не уменьшается никогда.
Идентификаторам место в логах и трейсах, где они и ищутся; в метках —
только то, что имеет конечный набор значений: сервис, метод, код ответа.

### Трассировки

Стандартный OpenTelemetry SDK для вашего языка, экспортёр OTLP на тот же
коллектор. Ничего специфичного для Watchgoose здесь нет — он читает
трейсы из ClickHouse, куда их кладёт коллектор.

Важно другое: **связь между трейсом и логом делаете вы**. Если в записи
лога есть `trace_id`, Watchgoose показывает лог и трейс вместе — от этого
и зависит, будет разбор инцидента занимать минуты или часы. Обе наши
библиотеки эту связь ставят автоматически, если трассировка в сервисе
включена.

### Проверка, что всё дошло

```bash
# Записи от вашего сервиса за последний час
curl -H "Authorization: Bearer $TOKEN" \
     "$WG/api/v1/search?q=service:orders&limit=5"

# Поля разложились по колонкам, если в ответе заполнены
# order_id, event, trace_id — а не только message и attrs
```

Если записи есть, но бизнес-ключи лежат в `attrs`, а не в своих
колонках — значит имена атрибутов не совпали с таблицей выше. Ищите
опечатку: `orderId` вместо `order_id`, `amount` вместо `amount_cents`.

## Роли и масштабирование

Один образ, один репозиторий, роль выбирается флагом:

```bash
watchgoose --role=all         # всё в одном процессе (dev, малый прод)
watchgoose --role=ingest      # приём и запись
watchgoose --role=detectors   # детекторы + gate + вебхуки
watchgoose --role=api         # REST + MCP + Web UI
```

**Четыре роли, не шесть.** Ролей `brain` и `executor` нет: ИИ внешняя,
исполнение внешнее.

| Роль | Реплики | Почему |
|---|---|---|
| `ingest` | **N, автоскейл** | stateless по логике, у каждого пода свой WAL |
| `api` | **N, автоскейл** | stateless, сюда же MCP |
| `detectors` | **N подов, 1 активный** | ⚠️ иначе один инцидент создастся N раз |

Лидерство берётся через `pg_advisory_lock`: работает одинаково в docker-compose
и в кластере, RBAC не требует, отпускается само при падении процесса.

```bash
helm upgrade --install watchgoose deploy/helm/watchgoose \
  -n observability --create-namespace \
  -f deploy/helm/watchgoose/values-prod.yaml
```

## Надёжность

**Три рубежа при отказе хранилищ:**

```
1. Буфер OTel Collector (file_storage)   минуты  — рестарт, деплой
2. WAL в ingest-плече                    часы    — падение Manticore
3. Backpressure к источникам             —       — исчерпание диска
```

Путь пачки: **приём → сегмент на диск (fsync) → батч в Manticore → удаление
сегмента**. Сегмент = одна пачка, поэтому «наполовину записанных» не бывает.

| Ситуация | Поведение |
|---|---|
| Manticore недоступен | пишем в WAL, после восстановления доливаем |
| WAL переполнен | по `on_full`: `drop_oldest` или `backpressure` |
| ClickHouse недоступен | коллектор ретраит из своей очереди, логи не затронуты |
| PostgreSQL недоступен | ingest **продолжает писать логи**, каталог обновится позже |
| Получатель вебхуков лежит | события копятся в `outbox` и уходят с ретраями |

⚠️ Отказ PostgreSQL не останавливает приём: каталог паттернов — производная,
его можно восстановить; поток данных — нет.

## Хранение

Посуточные RT-индексы Manticore под distributed-зонтиком. TTL в Manticore нет —
удалением управляем сами.

```
logs_err_YYYYMMDD    ERROR, FATAL
logs_warn_YYYYMMDD   WARN
logs_info_YYYYMMDD   INFO
logs_dbg_YYYYMMDD    DEBUG, TRACE
```

Разные индексы — это разделение ПОИСКА, а не хранения: запрос по ошибкам
не читает объёмный INFO. Срок хранения у всех уровней один.

### Удаляются целые сутки, и только когда кончается место

```
занято < 85% бюджета   → не удаляется ничего
занято ≥ 85% бюджета   → уходят самые старые сутки, целиком
сегодня и завтра       → не удаляются никогда
```

⚠️ **Никаких сроков по уровням.** Раньше DEBUG жил сутки, INFO — две недели,
ERROR — 90 дней. На разборе это означало ровно одно: происшествие трёхдневной
давности показывало голые ошибки без единой строки контекста вокруг них,
то есть ровно то, ради чего в логи и заходят.

Логи нужны, чтобы человек — дежурный, разработчик, ИИ — открыл и понял, что
происходило. Понять это по одним ERROR нельзя. Поэтому уровни хранятся
одинаково, а место освобождается удалением самых старых суток целиком.

⚠️ **Весов сервисов тоже нет.** Была настройка `retention.service_weights`:
логи «неважных» сервисов выкидывались первыми. Проблема в том, что неважных
сервисов не бывает — важность выясняется в момент происшествия, а не при
настройке. Сервис, который полгода никого не волновал, в день аварии
оказывается единственным, чьи логи нужны.

### Бюджет делится между четырьмя долями

```
WATCHGOOSE_RETENTION_DISK_BUDGET=200GB     сколько система себе позволяет ВСЕГО

  база знаний    15%   ← не ротируется никогда: знание не восстанавливается
  метрики        25%
  трассировки    25%
  логи           35%
```

Доля базы резервируется и не трогается уборкой. Там инциденты, накопленные
решения и статистика — то, чего нет больше нигде.

⚠️ **Вероятностного сэмплирования нет.** По сэмплу нельзя считать агрегаты,
а аналитика по трейсам — равноправный первичный сценарий. Отсев на входе
касается только заведомого мусора: health-checks и keep-alive.

### Метрики: единственное хранилище со сроком по календарю

VictoriaMetrics не умеет ограничивать себя по объёму и не позволяет удалять
отдельные сутки: только по возрасту целиком (`-retentionPeriod`) или ряд
со всей его историей. Поэтому здесь срок задан календарём — по умолчанию
полгода, — а система считает, влезает ли этот срок в свою долю при текущем
притоке, и предупреждает заранее.

```
VICTORIA_RETENTION_MONTHS=6     то же число в двух местах: у контейнера и у нас
```

### Логи инцидента хранятся отдельно и вечно

Когда инцидент открывается, куски логов вокруг него КОПИРУЮТСЯ в базу и живут
там столько же, сколько сам инцидент. Ротация до них не дотягивается: сутки,
из которых они собраны, могут уйти хоть завтра.

```
WATCHGOOSE_GATE_EVIDENCE_LINES=500      сколько строк сохранять
WATCHGOOSE_GATE_EVIDENCE_SAMPLES=10     сколько оставлять от одного шаблона
```

Если строк подошло больше предела, они прореживаются: от каждого повторяющегося
шаблона остаётся несколько образцов, приоритет отдаётся ERROR, затем WARN,
INFO и DEBUG. **Рядом всегда записывается пометка**, сколько строк подходило,
сколько осталось и по какому правилу — иначе по сотне строк из пятисот тысяч
делались бы выводы, не зная, что это сотая часть.

Автоматического удаления логов инцидента нет вовсе. Они уходят только вместе
с инцидентом, если его удалили осознанно.

```
после отсева мусора       →  ~45–60 ГБ
в Manticore               →  12–18 ГБ/день
```

## Архив в S3

Ротация освобождает место, удаляя старые сутки. Архив делает так, чтобы
удалённое не пропадало насовсем: каждую ночь завершившиеся сутки уезжают
в хранилище объектов одним файлом.

⚠️ **Выгрузка и удаление — разные механизмы.** Сутки уезжают в архив сразу
после того, как закончились, а из местного хранилища уходят тогда, когда
кончается место. Между этими событиями могут пройти недели.

### Что лежит в архиве

Одни сутки — один объект:

```
prod/2026/08/2026-08-11.tar
├── manifest.json          день, счётчики, размеры, контрольные суммы
├── logs.ndjson.zst
├── traces.ndjson.zst
└── metrics.ndjson.zst
```

Контейнер `tar` не сжат, а сжаты его части по отдельности: можно прочитать
только метрики, не распаковывая логи. `manifest.json` читается диапазонным
запросом, без скачивания всего объекта — на нём и строится список доступных
суток.

Контрольные суммы считаются от ИСХОДНЫХ данных, а не от сжатых: библиотеки
сжатия меняются от версии к версии, а данные — нет. Битая часть отказывает
с внятной причиной, а не отдаёт половину молча.

### Шифрование

```
ARCHIVE_ENCRYPTION=             key | none | пусто (режим по наличию ключа)
ARCHIVE_ENCRYPTION_KEY=...      парольная фраза, из неё выводится ключ
```

Части шифруются AES-256-GCM перед укладкой в контейнер. Ключ выводится из
парольной фразы **argon2id** — со случайной солью, один раз на батч. Просто
взять SHA-256 от строки было бы негодно: один проход хеша перебирается на
видеокарте миллиардами вариантов в секунду, и архив, закрытый такой
«защитой», вскрывается по словарю за вечер.

Каждая часть привязана к версии формата, дню и своему имени (это уходит
в дополнительные аутентифицируемые данные GCM). Подставить часть из другого
дня или подсунуть `traces` вместо `logs` не выйдет: расшифровка откажет.

Манифест остаётся открытым: список суток секретом не является, и требовать
ключ, чтобы просто увидеть, за какие дни есть архив, — лишнее. В нём же
лежат соль, параметры вывода ключа и `key_id` — короткая метка ключа.
По ней архив, закрытый другим ключом, распознаётся сразу и говорит об этом
прямо («архив зашифрован другим ключом (key_id X, настроен Y)»), а не падает
на середине восстановления с «неверный ключ?». Ротация ключа возможна:
старые батчи читаются старым ключом, новые собираются новым.

⚠️ **Парольную фразу потеряете — архив не прочитать ничем.** Сам ключ
не хранится нигде: по `key_id` его не восстановить.

⚠️ **Работа без шифрования — осознанный выбор, а не умолчание.** Пустой
ключ при включённом архиве даёт заметное предупреждение при старте, а
в строке журнала про подключённый архив пишется признак шифрования. Чтобы
предупреждение снять, напишите `ARCHIVE_ENCRYPTION=none` — тогда решение
записано.

### Срок хранения

```
ARCHIVE_RETENTION_DAYS=180
ARCHIVE_RETENTION_DRY_RUN=true    ← по умолчанию только считает, ничего не удаляя
```

Удаление в S3 необратимо, поэтому пробный режим включён с самого начала:
первый месяц разумно смотреть в журнал «что удалилось бы», а не проверять
срок хранения на своих данных.

⚠️ **Логов инцидентов срок хранения НЕ касается — но лежат они не здесь.**

Куски логов вокруг инцидента копируются в базу в момент его открытия
и живут там столько же, сколько сам инцидент. Доля базы уборкой не
урезается, ротация до этих строк не дотягивается: инцидент годовой
давности остаётся читаемым, даже когда сутки, из которых он собран,
из архива давно ушли.

Второй копии в S3 нет намеренно: две записи одного и того же надо было бы
держать согласованными, а вечное хранение уже обеспечено базой.

### Просмотр истории

⚠️ **Отдельно ходить никуда не нужно.** В поиске выбирается любой период —
пресетом до полугода или парой дат. Если он старше того, что осталось
на диске, поиск сам говорит об этом и предлагает открыть нужный день:

```
За 2026-04-18 логов на диске уже нет.
Они сохранены в архиве. Открыть этот день?     [ Открыть 2026-04-18 ]
```

Так и задумано: человек не думает «разверну сутки». Он выбирает период
и ждёт, что система найдёт данные, где бы они ни лежали. Если дня нет
и в архиве — так и написано, а кнопки нет: система тогда ещё не работала
или архив был выключен.

Открытие занимает несколько минут: день разворачивается в ОТДЕЛЬНЫЕ
экземпляры хранилищ — `manticore-archive`, `clickhouse-archive`,
`victoria-archive`. Почему не в живые: сутки полугодовой давности сломали бы
посуточную раскладку, попали бы под ротацию и вытеснили свежие данные — то
есть просмотр истории ломал бы работу системы. Почему те же хранилища,
а не новый вид: тогда весь код поиска, трассировок и графиков пришлось бы
учить второму источнику.

Пока день открыт, вверху висит полоса «История за такое-то число», и все
экраны данных — поиск, трассировки, графики, выгрузка файлов — показывают
его, а не сегодняшний. В API это параметр `archive_day=2026-04-18`.

Живой хвост в этом режиме выключен: сутки закончились, новым строкам
взяться неоткуда.

Раздел «Данные → История» остаётся для управления: какие дни открыты,
кто их смотрит и когда закроются.

### Сколько дней можно держать открытыми

Открытый день занимает местный диск рядом с живыми данными, поэтому их
число ограничено:

```
ARCHIVE_MAX_USERS=4          человек одновременно
ARCHIVE_DAYS_PER_USER=2      дней на каждого
                             → 8 дней на установку
ARCHIVE_SLOT_TTL=4h          через сколько день закроется сам
ARCHIVE_RESTORE_BYTES=4GB    предел на размер одних суток
```

Один и тот же день, нужный двоим, разворачивается ОДИН раз — смотрящих
у него двое. День закрывается, когда его перестали смотреть: либо нажали
«Закрыть», либо истёк срок. Забытая вкладка не держит его сутки.

Размер распакованных суток известен из манифеста ДО скачивания: отказ по месту
случается сразу, а не после того, как гигабайты уже приехали.

### У ИИ доступа к архиву нет

Возможность `archive:read` есть у ролей `admin` и `viewer`, но не у `ai`.
Ячеек на установку восемь, а разборов бывает десятки в сутки: агент, дошедший
до архива по любому поводу, занял бы их все за час и оставил без истории
живых людей — ровно тогда, когда она нужна. Логи инцидента у агента и так
есть: они лежат в самом инциденте.

### Включение

```bash
# в .env
ARCHIVE_ENABLED=true
ARCHIVE_ENCRYPTION=key
ARCHIVE_ENCRYPTION_KEY=$(openssl rand -hex 32)
S3_ENDPOINT=https://s3.example.com     # своё хранилище
S3_BUCKET=watchgoose
S3_ACCESS_KEY=...
S3_SECRET_KEY=...

# со своим хранилищем — профиль нужен только ради архивных экземпляров
docker compose --profile archive up -d
```

Профиль `archive` поднимает MinIO и три архивных экземпляра. MinIO здесь —
для проверки и небольших установок: на боевой машине задайте `S3_ENDPOINT`
внешнего хранилища, потому что смысл архива в том, что данные лежат ОТДЕЛЬНО
от машины, которая может умереть вместе со своим диском.

Бакет создаётся отдельным разовым контейнером, а не самим watchgoose: право
создавать бакеты — это право менять раскладку всего хранилища, и системе,
которая только пишет туда суточные архивы, оно не нужно.

## Цели по качеству

Цель — доля успешных обращений, ниже которой опускаться нельзя. Система
считает, с какой скоростью расходуется остаток допустимых сбоев, и поднимает
инцидент заранее — до того как порог пробит.

```
Разбор → Цели по качеству → Новая цель
```

```
идентификатор   payments-latency          латиница: попадает в тексты инцидентов
сервис          payments
название        Ответ платежей быстрее секунды
цель            99.5                      можно долей (0.995) или процентом
окно            30 суток
успешные        sum(rate(http_requests_total{code!~"5.."}[5m]))
все             sum(rate(http_requests_total[5m]))
```

### Что цель показывает

На экране у каждой цели три числа, и они отвечают на единственный вопрос,
ради которого её и заводили: выполняется ли она прямо сейчас.

```
выполнение                 99,87%    какая доля обращений успешна за окно
осталось права на ошибку   ▓▓▓░░░    полосой, чтобы читалось при десятке целей
состояние                  под угрозой
```

⚠️ **«Остаток права на ошибку» — это НЕ «сколько ошибок было».**

Цель 99,5% за 30 суток означает, что 0,5% обращений разрешено завершиться
неуспехом. Израсходовано 0,4% — осталась пятая часть, и это повод
действовать сегодня. Сама по себе цифра «0,4% ошибок» выглядит малой
и ни о чём не говорит; именно поэтому показывается остаток, а не доля.

Состояний четыре: **выполняется**, **под угрозой** (право израсходовано
больше чем наполовину — к концу окна запаса не останется), **нарушена**
и **нет данных** с объяснением, какое из выражений промолчало.

⚠️ **Ноль обращений — не нарушение цели.** Ночью у сервиса может не быть
ни одного запроса; посчитав выполнение как ноль, экран показал бы аварию
там, где просто никто не приходил.

Цель можно изменить, выключить и включить обратно. Идентификатор при
правке заблокирован: он попадает в тексты инцидентов, и сменив его,
вы не переименуете цель, а заведёте вторую, потеряв накопленное
по первой. У выключенной цели состояние не считается — она ни за чем
не следит, и «выполнение» у неё было бы числом ни о чём.

Оба выражения проверяются НА ХРАНИЛИЩЕ МЕТРИК при сохранении. Синтаксически
верное выражение может ссылаться на метрику, которой нет, — и цель молча
считалась бы всегда идеальной. Проверка при сохранении это единственный
момент, когда человек ещё смотрит на форму и может исправить.

## Дисциплина логирования

Две вещи, без которых половина системы не работает. Заложить **сразу**:
ретроспективно не добавить.

**П1. Сквозной `trace_id`** через всю цепочку: веб → очередь → воркеры →
внешние агенты. Без него не работают path-детектор, корреляция и половина
диагностики. Самая окупаемая вещь во всём проекте.

**П2. Бизнес-ключи — отдельными атрибутами, не в тексте:**

```
❌ message = "payment 4412 for order 8891 succeeded"

✅ message      = "payment succeeded"
   event        = "payment.succeeded"
   order_id     = "8891"
   payment_id   = "4412"
   amount_cents = 199000        ← деньги ТОЛЬКО целыми
```

Только так инварианты считаются по логам, без доступа к боевой БД.

> ⚠️ **Деньги — только целые в минимальных единицах.** `float` даёт накопленную
> погрешность, и первым сломается инвариант «сумма списаний == сумме движений» —
> ровно самая чувствительная проверка.

⚠️ **Измерения для резки** (`region`, `point_id`, `point_type`, `tariff`) —
из той же категории. Поля нет в момент записи → разрезать данные по нему задним
числом невозможно. Список согласовать с аналитиками **до первой записи**
(`manticore.extra_dimensions`).

Вебхук из CI после каждого деплоя — недооценённый повод: новый fingerprint сразу

```bash

  "commit_sha": "a91f3ce", "changed_files": ["OrderRepository.php"]

```

Через 30 минут система соберёт новые паттерны этого сервиса и отдаст ИИ одним
батч-вызовом. Потом по `fp_version_map` ловятся регрессии:

```
fp #a3f9c1 "serialization failure"
```

### Тесты

Ключевое покрыто там, где ошибка дорого стоит:

- **золотой корпус фингерпринтинга** — «сообщение → ожидаемый шаблон».
  Тюнинг нормализации обязателен первые месяцы, и без корпуса каждая правка —
  выстрел вслепую;
- формула `confidence` и пороги уровней — они продублированы в плане в двух
  местах, тест ловит расхождение;
- выбор ветки причины по `distinguishing`, включая `none_of` и недобор условий;
- WAL: долив после падения, битый хвост сегмента, обе политики переполнения;
- контракт исходящего события и подпись HMAC;
- протокол MCP, права групп и **отсутствие инструментов действия**;
- сроки хранения и приоритет удаления индексов;
- **разграничение доступа**: каждая пара «роль — возможность» перечислена
  явно, поэтому новая возможность ломает тест до тех пор, пока про неё
  не решат осознанно; отдельно — что токен приёма не открывает логи;
- **что ни один маршрут не остался без охраны**: проверка читает исходник
  маршрутизатора и требует, чтобы каждый путь под `/api/v1` был закрыт
  явно. Пройти запросом по всем маршрутам нельзя — `http.ServeMux`
  не отдаёт список зарегистрированного, а значит забытый маршрут именно
  поэтому и не заметят;
- **что приём, собранный без проверяющего, отвергает запросы** — ловушка,
  на которой этот код один раз уже сломался: внутренние функции вели себя
  как задумано, а приёмник целиком принимал всех;
- доступ к API: токен, подпись Mini App, кэш проверки и его потолок;
- каждый дефект, найденный на живом прогоне (см. раздел выше).

## Безопасность

Список секретов короткий — и это прямое следствие того, что ИИ внешняя:

| Роль | Есть | Нет |
|---|---|---|
| `ingest` | запись в Manticore, чтение/запись Postgres | всё остальное |
| `detectors` | read-only ко всем хранилищам, секрет подписи | **ключей моделей нет** |
| `api` | read-only ко всем хранилищам, токены доступа | **ключей моделей нет** |

Доступ к REST и Web UI закрыт по умолчанию. Токены живут в базе, у каждого
своя роль — подробности ниже. Внутри мессенджера вход идёт по подписи
`initData`, которая проверяется секретом бота и протухает через сутки;
роль такого входа задаётся отдельно и по умолчанию `viewer`.

### Роли и токены

⚠️ **Общего токена «на всех» нет, и это не косметика.**

Пока токен был один, сервис, который просто шлёт логи, получал ровно тот же
доступ, что дежурный инженер: мог читать логи с бизнес-ключами и суммами
и утверждать инварианты. Отозвать его у одного было нельзя, не сломав всех
разом, а по журналу нельзя было понять, кто что сделал.

Теперь токенов сколько угодно, у каждого своя роль, и права описаны
**списком возможностей**, а не проверкой роли по месту. Разница
принципиальна: `если роль == admin`, разбросанное по коду, означает,
что шестая роль потребует найти все такие места и не забыть ни одного,
а забытое место — это либо отказ там, где доступ положен, либо доступ там,
где не положен. Второе не заметит никто, пока не станет поздно.

| Роль | Для кого | Что даёт |
|---|---|---|
| `ingest` | сервисы и коллектор | **только запись телеметрии** |
| `viewer` | дежурные, разработчики | логи, метрики, трейсы, инциденты, паттерны — на чтение |
| `digest` | руководители, смежники | только история разборов и сводки, без доступа к логам |
| `ai` | внешний агент через MCP | чтение данных и запись результата разбора |
| `admin` | тот, кто разворачивал | всё, включая выпуск токенов и профилировщик |

Про роль `ingest` стоит сказать отдельно. Её токен лежит в **каждом**
сервисе, который шлёт логи: в образах, в переменных окружения, в конфигах
разработчиков — то есть в самом ненадёжном месте периметра. Поэтому он
не даёт ничего, кроме записи: утечка такого токена означает мусор в логах,
а не доступ к ним.

Роль `ai` не может ни менять настройки, ни выпускать токены, ни писать
в приём. Первые два — потому что модель ошибается, и цена ошибки в настройках
несоизмерима с пользой от возможности их менять. Третье тоньше: право писать
телеметрию позволило бы агенту подделать собственные улики.

**Как это работает.**

```bash
# первый токен создаётся сам, если таблица пуста, и печатается ОДИН раз
docker compose -f deploy/docker-compose.yml logs watchgoose | grep "ПЕРВЫЙ ТОКЕН"

# дальше — этим токеном
curl -X POST localhost:8080/api/v1/tokens      -H "Authorization: Bearer $ADMIN"      -d '{"name":"otel-collector","role":"ingest"}'

# или из командной строки, не поднимая сервис
./bin/watchgoose --issue-token="дежурная смена" --token-role=viewer

# кто я и что мне можно
curl -H "Authorization: Bearer $TOKEN" localhost:8080/api/v1/whoami
```

Значение токена видно **один раз** — в момент выпуска. В базе лежит
SHA-256 от него: дамп базы не должен означать утечку доступа. Восстановить
нельзя, можно только выпустить новый.

Отзыв через `DELETE /api/v1/tokens/{id}` действует немедленно — с точностью
до времени жизни кэша (`api.token_cache_ttl`, по умолчанию 30 секунд).
Кэш здесь не оптимизация, а условие работоспособности: проверка идёт
на каждом запросе, включая приём, и без него десять тысяч записей в секунду
означали бы десять тысяч обращений в PostgreSQL за одной и той же строкой.
Отрицательный ответ кэшируется тоже — иначе подбор токенов бьёт прямо в базу.

Отдать последний живой администраторский токен система не даст: `DELETE`
на него отвечает отказом. Иначе одно неверное нажатие оставляет систему
без единого способа войти.

Отказ по правам приходит кодом **403**, а не 401, и разница не косметическая:
на 401 клиент идёт обновлять токен, чего делать не надо. В теле — какая роль
предъявлена и какого права не хватило.

Интерфейс строит меню по ответу `/whoami`: роль `digest` видит только
«Историю», роль `admin` — ещё и «Токены». Это вежливость, а не преграда:
защищает сервер, который отвечает 403 независимо от того, что нарисовал
браузер.

⚠️ **Система больше не выпускает секретов сама.** Разовые токены на инцидент
убраны: они уезжали наружу в теле события и оседали в журналах принимающей
стороны — по новому секрету на каждое происшествие. Все токены теперь выпускает
человек. В базе лежит SHA-256 от токена, а не сам токен.

Что даёт токен роли `ai`: **чтение по всей системе и запись результата
разбора**. Разобрать сбой, не глядя на соседние сервисы, нельзя, поэтому
чтение не ограничено рамками одного инцидента. Номер инцидента для записи
агент называет доводом вызова; без номера запись отвергается, а не уходит
в какой-нибудь подвернувшийся.

### Приём телеметрии

Приём OTLP по gRPC и HTTP требует токен роли `ingest`. ⚠️ **Раньше пустой
токен означал «пускать всех», и это было ошибкой:** система, поднятая
по умолчанию, принимала записи от кого угодно, а человек об этом не знал.
Теперь нет проверяющего — значит не пускать; открыть приём можно только
явным `api.allow_anonymous`, то есть решением, а не упущением.

Почему это важнее, чем кажется. Кто дотянулся до порта приёма, тот не просто
насыпет мусора в логи: поддельные записи создают fingerprint'ы, поднимают
инциденты и портят бизнес-ключи, по которым считаются инварианты про деньги.
Отравить память системы не лучше, чем прочитать её.

Токен приёма — единственный, значение которого можно задать снаружи
(`INGEST_TOKEN`): он и так будет лежать в переменных окружения каждого
сервиса, который шлёт логи, и прятать его от собственного конфига незачем.
Если переменная пуста, токен генерируется при первом запуске и печатается
в журнал — его надо прописать коллектору.

### Контейнеры

В compose и в Helm процесс не root (uid 10001), `no-new-privileges`,
все capability сброшены, корень только для чтения, seccomp `RuntimeDefault`.
Под запись остаются только том WAL и `/tmp`.

| 3 | движок инвариантов, статистический майнинг кандидатов | бизнес-ключи из этапа 0 |
| 4 | MCP, привратник, playbook'и, таблицы знания | всё перечисленное выше |

### Ожидаемая динамика

Число обращений к ИИ **не падает** — она разбирает все инциденты всегда.
Падает их **стоимость**:

```
              обращений/день   из них known    средняя цена разбора
Неделя 1          5–15              0%          высокая (всё новое)
Месяц 2          15–25             45%          ↓ в 3 раза
Месяц 6          15–25             75%          ↓ в 10–20 раз
```

## Эксплуатационный риск: поток ложных срабатываний

Основная причина, по которой такие системы выключают, — не ошибки в коде,
а объём уведомлений. Детекторы первые недели работают по неоткалиброванным
базовым линиям и на неразмеченном каталоге паттернов; если весь этот поток
идёт наружу, его перестают читать, а вместе с ним перестают читать и полезное.

Что заложено в код против этого:

1. **Детекторы включаются по одному** (`detectors.enabled`). Порядок имеет
   значение: `new_fp` и `spike` дают шум, пока каталог не размечен, а
   `invariant` и `path_break` осмысленны почти сразу.
2. **Порог зрелости.** Паттерн не считается событием, пока не повторился
   заданное число раз за окно и не встретился в нескольких трейсах.
3. **Дедупликация и бюджет эскалаций.** Повтор клеится к уже открытому
   инциденту; сверх часового бюджета всё уходит в сводку, а не наружу.
4. **Уровни контекста.** Событие с известной причиной и высокой уверенностью
   идёт с готовой гипотезой; неизвестное — с полным контекстом; заведомый
   шум не идёт вообще.
5. **Доля ложных срабатываний** считается по каждому детектору и по каждому
   правилу инвариантов (`invariants.stats`).

Все решения привратника записываются с причиной и номером сработавшего
правила — это позволяет калибровать пороги по факту, а не на глаз.

Отдельно: система не выполняет действий над сервисами и не имеет для этого
учётных данных. Это сознательное ограничение — цена ошибки автоматического
действия в проде несоизмерима с выигрышем от него.

### Что нашлось при проверке и исправлено

Шесть дефектов, которые не видны в коде и вылезли только на живом прогоне:

1. **`trace_id` бился на OTLP/JSON.** Спецификация OTLP кодирует его hex-строкой,
   а стандартный protojson читает `bytes` как base64 — и молча раскодировал hex
   в мусор. Ломался П1, а с ним связка «лог ↔ трейс» и весь path-детектор.
2. **Коллектор не мог доставить ни одной пачки.** Штатный экспортёр `otlphttp`
   сжимает тело gzip'ом по умолчанию; приёмник этого не разжимал и отвечал 400.
   Приём выглядел рабочим, а логи не доходили вообще.
3. **Дедлоки в каталоге паттернов.** Воркеры батчера брали строки в произвольном
   порядке — Postgres снимал транзакции, и 20% обновлений каталога терялось.
   Исправлено сортировкой по `fp` плюс одна повторная попытка.
4. **WAL переигрывал живые сегменты.** Доливщик не отличал пачку, которая прямо
   сейчас пишется, от оставшейся после падения — 5 000 дублей на 2 млн строк.
5. **Manticore не агрегирует строковые атрибуты.** `max(service)` в `GROUP BY`
   валил `error_patterns` и `event_catalog` — два ключевых MCP-инструмента.
6. **Predictive молчал ровно тогда, когда нужен.** Шаг выборки был фиксированным
   (короткое окно вырождалось в одну точку), а при уже пройденном пороге детектор
   не сообщал ничего вместо «ресурс исчерпан».

Плюс закрыта дыра, которую живой прогон и выявил: **REST и Web UI работали
без аутентификации вообще.** Теперь роль `api` без токена не стартует.

На каждый дефект написан тест.

### Отдельный аудит: что нашлось при сплошной проверке

Прогон уже собранной системы целиком — статический анализ, чтение всех мест,
где строится SQL и проверяется доступ, плюс проверка каждого вывода на живом
стенде. Восемь находок, все закрыты и покрыты тестами:

1. **Инъекция в имя поля языка запросов.** Имя колонки параметром не задать,
   оно уходит в SQL текстом. Проверка `SafeColumn()` была написана, но
   к именам полей не применялась: запрос `a;DROP:1` компилировался в
   `attrs.a;DROP = ?`. Теперь неизвестное имя проверяется до подстановки.
2. **Приём телеметрии был открыт всем.** Теперь требует токен роли `ingest`,
   а отсутствие проверяющего означает «не пускать», а не «пускать» — см. выше.
3. **Cookie принималась как токен доступа.** Браузер прикладывает её сам,
   в том числе к запросу, затеянному чужим сайтом, а под `/api/v1` восемь
   POST-обработчиков утверждают инварианты и закрывают инциденты. Интерфейс
   и так носит токен заголовком, поэтому cookie больше не принимается вовсе —
   это дешевле и надёжнее, чем защита от CSRF.
4. **`/readyz` рассказывал лишнее анониму.** Эндпоинт открыт для проверок
   живости, а в текст ошибки попадали внутренние адреса и имена пользователей
   хранилищ. Теперь наружу уходит только состояние; подробности — по
   `?verbose=true` и только с токеном.
5. **Scoped-токен оставался в очереди исходящих.** Событие живёт в БД 14 дней,
   и всё это время в нём лежал действующий ключ. Теперь при отметке о доставке
   он затирается в самом JSON.
6. **Запись в чужой инцидент подменялась молча.** Просьба «запиши разбор в #38»
   с токеном от #40 писала в #40 и отвечала «готово». Изоляция соблюдалась,
   но модель считала, что разобрала один инцидент, а разбор ложился в другой.
   Теперь это отказ с внятным текстом.
7. **Падение поиска без Manticore.** Роль `api` намеренно поднимается без него,
   но обработчики разыменовывали нулевой клиент — паника вместо ответа.
   Теперь честная 503.
8. **Лишний запрос на каждое открытие ленты.** `Timeline` ходил в Manticore
   за шагами процесса и выбрасывал ответ: второй поход к базе впустую, плюс
   его ошибка роняла весь запрос.

Заодно исправлено то, что всплыло рядом: конфиг коллектора не предъявлял
ingest-токен (с закрытым приёмом логи перестали бы доходить), симулятор
не умел предъявлять ни один из токенов, а предупреждение на старте обещало,
что события «копятся в БД», хотя без вебхука они сразу помечаются
доставленными.

Что проверено и оказалось в порядке: подстановка значений в SQL везде идёт
параметрами (четыре хранилища), идентификаторы проверяются в 20 местах,
подстановки в HTML экранируются, у HTTP-клиентов есть таймауты, лимиты
на размер тела и на выборки стоят, токены в логи не попадают, MCP закрыт
и по `tools/list`, и по `tools/call`, истёкший и отозванный токены
отвергаются, обход каталога в веб-раздаче не проходит.

### Второй заход: интерфейс, мини-приложение и полнота поиска

Отдельная сверка с планом по трём вопросам — есть ли Mini App, удобен ли
интерфейс, полноценен ли поиск. Интерфейс прогонялся в настоящем браузере
(десктоп и телефон в режиме мессенджера), а не читался глазами по коду.

Чего не хватало и сделано:

1. **Выгрузки не было вообще.** Совместный просмотр логов и спанов был,
   а унести их одним файлом было нельзя. Добавлен `GET /api/v1/export`:
   ndjson и csv, процессами целиком, потоком, с бизнес-ключами.
2. **`message:/рег.выр/` молча искал не то.** `REGEX()` по `message`
   в Manticore невозможен — это stored-поле. Выражение уходило
   в полнотекстовый поиск слова `deadlock|timeout` и находило пусто.
   Теперь применяется после выборки.
3. **`-term` работал только после явного `AND`.** `timeout -level:DEBUG` —
   самая частая форма записи — падала с «недопустимое имя поля `-level`»,
   хотя именно она и была в подсказках системы.
4. **В языке не было** исключающих `{a TO b}` и смешанных `[a TO b}`
   диапазонов, открытых границ `[100 TO *]`, регулярных выражений,
   проверки наличия поля `поле:*` / `_exists_:`, близости слов `"а б"~3`.
5. **Mini App был из трёх строк:** читался `initData`, вызывались `ready()`
   и `expand()`. Не было темы мессенджера, его высоты, его кнопки «назад»,
   отклика на действие; вертикальный свайп закрывал приложение прямо
   при прокрутке ленты; подтверждение исхода — главный сценарий Mini App —
   шло через `alert()` и `prompt()`, которые в webview не работают;
   при неудачном входе пользователю предлагали ввести серверный токен,
   которого у него нет.
6. **Лента инцидентов не давала триажа.** Карточка показывала
   `#15 new_fp e0ea976c897e` — набор символов, по которому не отличить
   отвалившийся эквайринг от перезапуска пода. Теперь в списке шаблон
   паттерна («acquirer timeout after &lt;DUR&gt;, order &lt;N&gt;»), число повторов
   и статус по-русски.
7. **Живой хвост и справка по полям были в API, но не в интерфейсе.**
   Подключены; хвост понимает тот же язык запросов, что и поиск, а справка
   берёт список полей с сервера, чтобы он не разошёлся с разбором.

### Третий заход: параллелизм, память, масштаб

Прогон под детектором гонок и под нагрузкой, которую задаёт назначение узла —
тысячи источников. Гонок не нашлось ни одной, но нашлось семь других дефектов,
каждый из которых виден только на объёме или на многопоточности.

1. **Остановка приёма теряла принятые записи.** Батчер выходил по отмене
   контекста, а приёмник останавливался ПОСЛЕ неё. Всё, что источник успел
   прислать в этом окне, получало «ок» и оставалось в очереди, которую больше
   некому читать. Под нагрузкой — тысячи записей, потерянных молча, при том
   что главная гарантия приёма ровно обратная. Теперь батчер выходит только
   по `Stop()` и перед выходом дочерпывает очередь до дна.
2. **`Stop()` сам по себе висел вечно.** Батчер не слушал канал, который
   закрывает `Stop`, — остальные горутины слушали. Работало только потому,
   что в `main` порядок остановки случайно оказался верным.
3. **Паника в записи пачки роняла процесс и теряла данные навсегда.**
   Паника происходила в горутине батчера, где её некому перехватить: падал
   весь узел, а сегмент WAL оставался помеченным «в работе» — доливщик его
   уже не трогал. Теперь паника ловится, сегмент честно помечается упавшим
   и переиграется, воркер живёт дальше.
4. **Метка `service` в счётчике приёма** — неограниченный рост памяти
   на узле с тысячами источников. Закрыто реестром с потолком; заодно
   выяснилось, что `trace_id` в пути не схлопывался в шаблон, а неизвестные
   пути от сканера создавали ряды метрик без всякой аутентификации.
5. **Обрезка сообщений рвала UTF-8 пополам** и вылезала за собственный
   потолок на три байта. На любом не-ASCII тексте результат — битый UTF-8,
   который `json.Marshal` молча подменяет на U+FFFD.
6. **Медленный детектор копил заблокированные горутины.** Задач восемнадцать,
   часть ходит раз в минуту; вставшая задача держала общий замок, и каждая
   следующая метка расписания вешала на него ещё одну горутину с живым
   контекстом. Теперь наложившийся прогон пропускается с записью в лог
   и в счётчик.
7. **Выгрузка ходила в хранилища по разу на процесс** — около 400 запросов
   на двухстах процессах вместо 6. Переписана на партии.

6. **Нормализация токенов съедала 12% процессора всего процесса** — больше,
   чем разбор protobuf. Тринадцать регулярных выражений прогонялись подряд
   на каждом токене каждой записи, хотя подавляющее большинство токенов —
   обычные слова, где ни одно из них совпасть не может. Добавлен отсев
   одним проходом по строке: нормализация в 2.5 раза быстрее, фингерпринтинг
   целиком в 2.8 раза. Проверено не бенчмарком, а эквивалентностью прежней
   реализации на корпусе из 200 000 токенов — иначе изменился бы шаблон,
   а с ним и все fingerprint'ы.
7. **Профилировщика не было вообще.** «Стало медленно» на центральном узле
   разбирается гаданием, а гадание на живой системе стоит дороже профиля.
   Подключён `pprof` под тем же токеном, что и остальной API: профиль
   содержит имена функций и куски данных из памяти, а сам сбор притормаживает
   процесс — открытым его оставлять нельзя.

Плюс снято ограничение на длину сообщения: раньше всё резалось на 16 КБ,
теперь сообщения любого размера хранятся целиком, а память защищена пределами
на объём пачки и очереди.

Что проверено и оказалось в порядке: гонок нет (детектор гонок на всех
пакетах, включая тесты, где 20 отправителей, 6 воркеров батчера и параллельная
доливка WAL работают одновременно); горутины не текут (четыре всплеска
по 24 подписки подряд — счётчик держится в коридоре 31–36, рост дают только
соединения пула драйвера); память возвращается (после 60 секунд нагрузки живых
159 МБ, 383 МБ отдано системе, за 45 секунд покоя роста нет); курсоры и тела
ответов закрываются везде; таймеры останавливаются; пулы соединений ограничены;
у всех запросов есть сроки.

Отдельно проверено на кириллице: значения в атрибутах ищутся корректно,
включая имена сервисов и бизнес-ключи. Первоначальный «отрицательный»
результат оказался артефактом оболочки, коверкавшей UTF-8 в аргументах curl,
а не дефектом системы.

### Четвёртый заход: прогон флотом из тысячи сервисов

Отдельный прогон по сети: тысяча сервисов, 250 соединений, у каждого своё имя,
свои формы сообщений и свои бизнес-ключи; каждый пятидесятый шлёт стектрейс
на мегабайт, каждый двадцатый шумит втрое сильнее остальных. Это проверка
не пропускной способности, а того, как узел переживает РАЗНООБРАЗИЕ — именно
на нём ломаются центральные системы: метки метрик, дерево паттернов, каталог
и пул соединений растут не от объёма, а от числа разных значений.

Найдено и исправлено:

1. **Обновление каталога паттернов стоило дороже записи логов** — 1147 мс
   на пачку. В пачке с тысячи сервисов сотни разных паттернов, и на каждый
   шёл отдельный `INSERT ... ON CONFLICT`; восемь воркеров делали это
   одновременно по пересекающимся строкам, добавляя ожидание на блокировках.
   Переписано на один оператор с массивами: **1147 → 255 мс**, общая
   пропускная способность **10 300 → 15 000 записей/с**.
2. **Пачка держала ссылки на сообщения после записи.** `batch[:0]` сохраняет
   ёмкость, и массив под срезом продолжает ссылаться на строки: сборщик их
   не заберёт, пока слот не перезапишут. На обычных логах незаметно,
   на стектрейсах по мегабайту так зависают сотни мегабайт — и на тихой
   системе висят вечно. Добавлено обнуление элементов перед усечением.
3. **Образец сообщения в каталоге хранился целиком.** Каталог паттернов
   читают все экраны и все инструменты модели; класть туда мегабайтные
   стектрейсы значит раздувать самую горячую таблицу. Обрезается до 2 КБ
   по границе символа — полный текст и так лежит в Manticore.
4. **Счётчик срабатывания потолка меток мог не сработать вовсе.** После
   заполнения реестра быстрый путь возвращает «прочее», не заходя под замок,
   и разовая отметка не ставилась. Теперь считается каждое обезличивание:
   оператору нужна скорость, отвечающая на вопрос «сколько источников
   мы перестали различать».
5. **Буфер SQL-запроса рассчитывался по числу записей**, а не по объёму
   текста. Прикидка «256 байт на запись» промахивается на два порядка
   на стектрейсах: буфер на 50 МБ, выросший из килобайта, — это около
   двух десятков перевыделений с копированием всего накопленного.

Что проверено и оказалось в порядке: горутины возвращаются (599 в покое
при 250 соединениях, пик 1206 под нагрузкой, 37 после); память возвращается
(пик 1110 МБ, через 70 секунд покоя 374 МБ живых и 779 МБ отдано системе);
очередь ни разу не превысила потолок (310–357 МБ при 512 МБ); отказ при
переполнении честный (`Unavailable`, источник повторяет из своей очереди);
дерево паттернов ограничено сверху (5000 кластеров); `/metrics` остался
150 КБ и 1824 ряда при тысяче источников; сообщения до 48 МБ проходят
сквозь всю цепочку целиком; гонок нет.

### Пятый заход: профилирование под разными размерами сообщений

Отдельная серия замеров по размеру сообщения — потому что «записей
в секунду» без указания размера ничего не значит. Каждый прогон
на чистых хранилищах: Manticore с накопленными данными пишет медленнее,
и без сброса цифры между размерами несравнимы.

На сообщениях в 10 КБ вскрылось, что узкое место переехало из Manticore
в собственный код: 793 записи/с при 7.1 ядра на приём против 1.9 ядра
на Manticore. Профилировщик показал три причины, и все три в разборе
паттернов.

1. **`strings.Fields` разбирал сообщение целиком.** На записи в 10 КБ это
   около полутора тысяч кусков и большой срез под них — при том что
   в разбор идут только первые восемьдесят токенов. 13% процессорного
   времени всего процесса. Заменено на разбор с ранней остановкой.
2. **`splitPunct` конвертировал строку в руны и обратно** — три аллокации
   на каждый токен, 12% процессорного времени. Переписано по байтам:
   отсекаемые символы ASCII, а в UTF-8 продолжающие байты всегда ≥ 0x80,
   поэтому границы символов не рвутся.
3. **Разбор паттерна не был ограничен по числу токенов.** Ограничение
   было по байтам (4 КБ), то есть на 10 КБ сообщении разбирались все
   шестьсот токенов из этих четырёх килобайт. Паттерн определяется
   началом сообщения — «какое исключение и где»; хвост стектрейса это
   одинаковые кадры вызовов. Добавлен `fingerprint.max_tokens` (80).

Итог на 10 КБ: **793 → 1431 записи/с, 8.9 → 3.3 мс процессора на запись**,
нагрузка на приём и на Manticore выровнялась (4.8 против 3.0 ядра).

Отдельно проверено, что `batch_bytes` по умолчанию был выбран неудачно.
Пачка материализуется в памяти трижды — срез записей, текст `INSERT`
и копия драйвера при экранировании. Пачка в 1–4 МБ давала на треть больше
пропускной способности, чем в 32 МБ, при втрое меньшей куче; умолчание
изменено на 4 МБ.

⚠️ Все три оптимизации разбора проверяются не бенчмарком, а
**эквивалентностью**: прежняя реализация сохранена в тестах как эталон,
и обе сверяются на корпусе из 200 000 токенов. Иначе изменился бы шаблон,
а с ним и все fingerprint'ы — накопленное знание отвязалось бы от паттернов.
Тест уже отработал по назначению: поймал ошибку в условии для
шестнадцатеричных чисел, допущенную при первой попытке ускорения.

Здесь же добавлен профилировщик (`/api/v1/debug/pprof/`, под тем же
токеном): «стало медленно» на центральном узле разбирается гаданием,
а гадание на живой системе стоит дороже профиля.

### Шестой заход: ротация и удаление под нагрузкой

Проверка того, что до этого не проверялось ни разу: как ведут себя ротация
посуточных индексов и удаление старых данных, когда они происходят
одновременно с приёмом и поиском. Стенд с ротацией и удалением раз
в 20 секунд, 36 индексов за прошлые дни, 200 сервисов пишут, поиск идёт
непрерывно.

1. **Удаление ломало поиск целиком.** Индексы удалялись ПЕРЕД пересборкой
   зонтика, и всё это время зонтик ссылался на несуществующие таблицы —
   каждый поиск падал с `unknown local table`. На 28 индексах это секунды
   полной неработоспособности поиска, повторяющиеся при каждой чистке.
   Порядок исправлен: сначала вывод из зонтика, потом удаление с диска.
   Было 1 сбой из 228 запросов, стало 0 из 332.
2. **Зонтик пересобирался при каждой ротации,** даже когда создавать было
   нечего. Пересборка идёт через `DROP` + `CREATE` (Manticore не умеет
   иначе), то есть окно неработоспособности создавалось на ровном месте.
   Теперь только при изменении состава индексов.
3. **Запрос, попавший в окно пересборки, падал.** Окно миллисекундное
   и неустранимо, поэтому запрос повторяется один раз; счётчик повторов
   выведен в метрики.
4. **Задачи обслуживания голодали.** Мгновенный отказ при занятом замке
   (введённый в прошлом заходе против накопления горутин) на частом
   расписании привёл к тому, что 33 прогона из 39 были пропущены,
   а удаление отработало один раз вместо шести. Заменено на ограниченное
   ожидание: короткое пересечение переживается очередью, застрявшая
   задача — пропуском.
5. **Опечатка в конфиге молча игнорировалась.** Найдено на себе:
   конфиг прогона был написан ключами `retention.default` и
   `retention.by_bucket`, которых в схеме нет, — система взяла умолчания
   и ничего не сказала. Тем же способом во всех тестовых конфигах тихо
   не работал `ingest.wal_dir` (правильно `ingest.wal.dir`). Теперь
   неизвестный ключ — ошибка запуска, а список допустимых берётся
   из структуры конфига и не может разойтись с кодом.

Что проверено и оказалось в порядке: индексы на сегодня и завтра создаются
заранее; запись в день без индекса создаёт его на месте и повторяет вставку;
удаление по срокам считает возраст правильно для всех корзин; приём
не прерывается на время чистки; данные удаляются именно те, что просрочены.

### Седьмой заход: сплошная проверка всего, что не проверялось

Прогон по областям, до которых руки не доходили ни разу: одновременный
старт нескольких подов, выборы лидера и подхват при падении, холодный слой,
очередь исходящих при недоступном получателе, все 31 инструмент MCP,
все шесть детекторов, восстановление WAL после жёсткого убийства процесса.

Найдено и исправлено:

1. **Одновременный старт подов ронял миграции.** `CREATE TABLE IF NOT EXISTS`
   в PostgreSQL не атомарен: при запуске пяти процессов четыре падали
   с «duplicate key value violates unique constraint» на системном каталоге,
   а две реплики могли выполнить одну миграцию дважды. В кластере это
   crash-loop подов на каждой раскатке. Вся процедура убрана под
   advisory-блокировку; проверено на восьми одновременных процессах —
   миграции применились по одному разу, ни один не упал.
2. **Холодный слой не создавался вовсе.** В `TTL ts + INTERVAL 12 MONTH`
   колонка `ts` объявлена `DateTime64(3)`, а ClickHouse требует в выражении
   TTL `DateTime` или `Date` и отвергает создание таблицы целиком. Поскольку
   холодный слой выключен по умолчанию, обнаружить это можно было только
   включив его.
3. **Переливка теряла данные.** Она шла постранично через `OFFSET`, а
   Manticore не умеет глубокую постраничную выборку: при смещении больше
   `max_matches` запрос падает с «offset out of bounds». На потолке в 5000
   переливалось ровно 10 000 строк за сутки, остальное молча оставалось
   в горячем хранилище и удалялось по сроку — то есть холодный слой терял
   ровно то, ради чего существует. Переписано на курсор по времени:
   проверено на 12 000 строк, переносятся все.
4. **Переливка не была идемпотентной** — переносила одни и те же сутки при
   каждом прогоне, задваивая данные в слое, предназначенном для аудита
   и аналитики. Добавлена отметка обработанных суток.
5. **Очередь исходящих обещала защиту, которой не было.** `SELECT ... FOR
   UPDATE SKIP LOCKED` выполнялся вне транзакции, поэтому блокировка
   снималась до доставки: две реплики роли `api` забирали одно событие
   и отправляли вебхук дважды — ИИ получала один инцидент два раза.
   Заменено на атомарный захват через `UPDATE ... RETURNING`.
6. **Сырые ошибки хранилищ уходили модели.** `submit_fp_verdict` на
   неизвестный паттерн отвечал текстом PostgreSQL про нарушение внешнего
   ключа, инструменты трейсов — текстом ClickHouse про отсутствующую
   таблицу. Модель дёргает инструменты вслепую по описанию: из такого
   текста она не поймёт ни что сделала не так, ни что делать дальше,
   и будет повторять вызов. Заменено на объяснения.
7. **Поиск отвечал 400 при упавшем хранилище.** Код 400 означает «твой
   запрос неверен»: получив его при верном запросе, интерфейс или модель
   начнут переписывать запрос вместо того, чтобы повторить позже.
   Разделено: ошибка разбора — 400, недоступное хранилище — 503.

   ⚠️ Первая версия этой проверки сверяла подстроки вроде
   `connection refused` — и на живой системе не сработала: Windows отдаёт
   локализованное «target machine actively refused it», где этой подстроки
   нет. Тексты системных ошибок зависят от платформы, языка и версии
   драйвера, поэтому различение построено на ТИПАХ (`net.Error`,
   `driver.ErrBadConn`, `syscall.Errno`, `context.DeadlineExceeded`),
   а текстовая сверка осталась только для собственных кодов драйвера.

### Восьмой заход: блокировки, память, бюджет хранения

Заход под заявленную боевую цель — **1000 сервисов, 200 млн записей логов
в сутки**. Основной вопрос: где процесс упирается не в диск и не в сеть,
а сам в себя.

**Главная находка — конкуренция за замок разбора паттернов.**

Профиль блокировок под нагрузкой показал **26 310 секунд** суммарного
ожидания на замке дерева Drain. Это не время работы, а время, которое
горутины простояли в очереди: при 1000 источников каждая запись проходит
через определение паттерна, а дерево было одно на процесс под одним
`sync.Mutex`. Ядра при этом заняты, но заняты ожиданием.

Переделано в два шага:

1. Дерево разложено на **64 независимых секции**; номер секции считается
   по ключу (сервис + длина сообщения) хешем FNV-1a. Записи разных
   сервисов больше не встречаются на одном замке вовсе.
2. Горячий путь переведён на **чтение**. Раньше любая запись брала замок
   на запись, хотя в устоявшемся режиме подавляющее большинство записей
   попадает в уже существующий паттерн и ничего в дереве не меняет.
   Теперь такая запись берёт замок на чтение, сверяется с готовым
   шаблоном и увеличивает счётчик атомарно. На запись замок берётся,
   только если паттерн новый или шаблон реально меняется.

Результат на том же профиле: **26 310 с → 201 с, в 131 раз меньше.**

Остальное, найденное и исправленное:

1. **Пакет записей удерживал сообщения в памяти.** После отправки пакет
   обрезался как `batch[:0]` — длина ноль, но указатели на сообщения
   в нижележащем массиве остаются, и сборщик мусора их не трогает.
   При мегабайтных сообщениях это сотни мегабайт, висящих без причины
   до следующего заполнения. Добавлена явная очистка перед обрезкой.
2. **Бюджет удалял живые индексы.** Найдено на первом же живом прогоне
   бюджета: сегодняшний индекс — самый крупный и по возрасту самый
   «дешёвый», поэтому под давлением бюджет сносил именно его, ротация
   тут же создавала его заново, занятое место не менялось. В журнале
   это выглядело как «удалено 9 индексов» при неподвижной занятости —
   вечный круг. Индексы, в которые идёт запись, помечены и из кандидатов
   исключены; их объём при этом продолжает учитываться.
3. **Счётчик ограничения кардинальности врал.** Быстрый путь возвращал
   `прочее` не увеличивая счётчик, поэтому по метрикам выходило, что
   ограничение почти не срабатывает, хотя срабатывало постоянно —
   а это единственный признак того, что часть меток схлопнута и разбивка
   по сервисам стала неполной.
4. **Обрезка длинных образцов рвала UTF-8.** `s[:limit]` резал по байтам:
   на границе многобайтного символа в базу уходила битая
   последовательность, а добавленное многоточие вдобавок выводило строку
   за объявленный предел. Переписано по рунам.

Что проверено и оказалось в порядке:

| Бюджет хранения | 10 проверок границ: пока место есть — не удаляет ничего; за прогон сносит не больше потолка; сначала `dbg`, ошибки последними |

### Девятый заход: память, замки, выделения под целевой нагрузкой

Заход под ту же цель — 1000 сервисов, 200 млн записей в сутки — но
с другим вопросом: не «где узкое место», а «что здесь ограничено только
на словах». Проверялось всё, что имеет потолок: очереди, реестры,
пулы соединений, карты, горутины, таймеры.

**Память процесса не была ограничена ничем.**

Это главная находка захода, и она в двух частях.

Первая: очередь ингеста ограничена по байтам, и это легко прочесть как
«память процесса ограничена». Она не ограничена — граница очереди стоит
ПОСЛЕ разбора. К моменту, когда очередь отвечает «полно», тело запроса
уже прочитано целиком и развёрнуто в объекты. Сколько запросов
разбирается одновременно, не ограничивал никто.

Замер: 200 одновременных запросов с телами по 1.5 МБ (296 МБ в сумме)
подняли кучу с 67 МБ до **1122–1312 МБ** по трём прогонам. Ни одна
настройка на это не влияла: пик задавало то, сколько источников совпало
по времени.

⚠️ Сам приём при этом отработал правильно, и это стоит развести:
из двухсот запросов 109–115 приняты полностью, 7–11 частично, остальные
получили 503 с `Retry-After` и разборчивым телом. Оборванных соединений
и молчаливых потерь нет ни одной. Находка не в отказах, а в том, что пик
памяти не ограничен сверху ничем: на машине с 31 ГБ это просто цифра,
а в контейнере с `limits.memory` — OOM-killer.

Вторая, и она оказалась весомее: **сборщик мусора не знал про лимит
контейнера**. `GOMEMLIMIT` не выставлялся нигде — ни в коде, ни в compose,
ни в Helm. Сборщик Go работает от GOGC и назначает следующую уборку,
когда куча вырастет вдвое относительно живых данных; про cgroup он
не знает. Замер в один момент под нагрузкой: `heap_alloc` 636 МБ при
350 МБ живых объектов — почти половина занятого была мусором, который
никто не просил забирать быстрее. В контейнере это заканчивается
OOM-killer, а с ним теряется очередь принятого и подвисают сегменты WAL,
помеченные «в работе».

Сделано:

- `server.inflight_bytes` — разрешение берётся ДО чтения тела, бюджет
  считается в байтах. Не поместившийся ждёт две секунды и получает 503
  с `Retry-After`. Заодно ограничено число потоков на gRPC-соединение:
  по умолчанию gRPC не ограничивает его вовсе.
- `server.memory_limit` — предел для сборщика; пустое значение означает
  «взять из cgroup» и назначить 90%. Вне контейнера предел не
  назначается: выдуманное число ограничило бы процесс на ровном месте.
- Лимит памяти прописан в compose и в `.env.example` — без него настройка
  бесполезна.

Результат на том же замере, по три прогона на настройку: пик кучи
**1122–1312 → 756–826 МБ**, память процесса **1284–1527 → 895–1030 МБ**,
принятых записей не меньше, а больше (109–115 → 116–121). Плата —
время: под перегрузкой процесс тратит на уборку вдвое больше
(2.8–3.2 с → 5.6–6.7 с). Это и есть смысл размена: притормозить и выжить
вместо того, чтобы разогнаться и быть убитым ядром.

**Главным замком в системе оказался счётчик метрики.**

Профиль блокировок под нагрузкой в тысячу сервисов: из всей конкуренции
за замки в процессе **693 секунды — 35%** приходилось на
`prometheus.CounterVec.WithLabelValues`, который вызывался на каждую
принятую запись. Для сравнения, разбор паттернов, через который проходит
та же каждая запись, давал 17 секунд — восьмое шардирование сделало своё
дело, и место главного узкого горла освободилось для следующего.

Дело не в том, что счётчик медленный, а в том, что он общий: каждый вызов
хеширует значения меток и лезет в карту рядов под замок, один на весь
процесс. Записей в пачке сотни, а разных сочетаний «уровень+сервис» —
единицы. Теперь пачка считается на месте, в массиве фиксированного
размера, и в счётчик уходит одно сложение на сочетание.

Конкуренция в приёме: **711.7 → 40.0 секунды, в 17.8 раза меньше.**
Доля приёма во всей конкуренции процесса: 36.25% → 2.15%. То, что
осталось наверху, — целиком внутреннее: вытеснение горутин (61%)
и аллокатор со сборщиком (20%). Своих замков в верхушке профиля больше
нет.

**Выделения на записи сокращены вдвое.**

Профиль выделений разбора паттернов показал, что 65% всего, что там
выделяется, — накладные расходы, не производящие ничего:

- `treeKey` (28.7%) собирал строку-ключ на каждой записи, чтобы дважды
  ею воспользоваться и выбросить. Теперь ключ собирается в буфере
  на стеке; Go умеет искать в `map[string]` по срезу байт без выделения,
  а строка материализуется только при вставке нового кластера — их
  не больше `max_clusters` за всю жизнь процесса.
- `hashFP` (36.5%) склеивал «шаблон\0сервис» в новую строку и просил
  у `hex.EncodeToString` сорок знаков, из которых оставлял двенадцать.
  Срез строки в Go не копирует — значит за каждым отпечатком висел
  сорокабайтный массив ровно столько, сколько живёт запись. Теперь
  склейка идёт в буфер на стеке, а шестнадцатеричная запись собирается
  сразу нужной длины.

|---|---|---|
| Выделений на запись (разбор паттерна) | 9 | 4 |
| Байт на запись | 629 | 403 |
| Наносекунд на запись | 408 | 356 |
| Выделений на запись (весь приём) | 9.8 | 4.8 |

⚠️ Подъём поиска счётчика из цикла заметного выигрыша по времени
не дал: разброс между прогонами (±10%) больше самого эффекта, потому что
приём упирается в разбор паттернов, а не в метрики. Изменение оставлено
ради конкуренции — цифры по ней выше и они не в пределах шума.

Остальное, найденное и исправленное:

1. **Обогащение останавливало приём на время запроса к базе.** Кэш
   версий сервисов обновляется раз в минуту, и обновление держало замок
   на запись всё время похода в PostgreSQL. Через этот кэш проходит
   каждая пачка со всех источников, а `sync.RWMutex` не пускает новых
   читателей, пока ждёт писатель, — значит на время запроса вставал ВЕСЬ
   приём. При здоровой базе это миллисекунды и незаметно; при больной —
   до пяти секунд полной остановки раз в минуту, причём ровно тогда,
   когда логов приходит больше обычного. Теперь под замком только обмен
   готовой картой: пока один обновляет, остальные читают прежнюю.
   Проверено тестом с базой, отвечающей секунду: на старом коде читатели
   простаивали ровно эту секунду.
2. **Потолок реестра меток бил по своим.** Разных значений метки
   `service` разрешалось 500 — при заявленной цели в тысячу источников.
   Половина сервисов схлопнулась бы в «прочее», и разбивка приёма
   по сервисам стала бы бесполезной ровно в той установке, под которую
   всё делается. Причём молча: графики выглядели бы как обычно. Потолок
   поднят до 2000 — двойной запас к рабочему масштабу.
3. **`max_matches` слался константой в каждый запрос.** В Manticore это
   размер очереди сортировщика: он собирает столько строк ЦЕЛИКОМ, со
   всеми колонками, и лишь потом отдаёт запрошенные. Уходил потолок
   из конфига — пять тысяч, — сколько бы строк ни просил клиент. На
   пятидесяти запрошенных собиралось пять тысяч, и 4950 выбрасывались:
   широкий фильтр `level:ERROR` отвечал 768 мс вместо 39. Теперь значение
   считается из `limit + offset`; выдача побайтово та же — проверено
   сравнением всех строк при `max_matches` от 50 до 20000.
4. **Одинаковые логи схлопывались в один.** При объединении веток запроса
   строки различались по содержимому — время, сервис, текст. Но одинаковые
   логи в системе не аномалия, а норма: сотня воркеров одного сервиса пишет
   «connection refused» в одну и ту же миллисекунду, когда отваливается
   база. Такие строки считались одной, и дежурный видел единственное
   упоминание вместо всплеска — то есть терял ровно тот признак, по
   которому отличают сбой одного запроса от сбоя целиком. Проверено на
   стенде: десять записей с общим временем показывались как одна. Теперь
   строки различаются по `(id, ts)`. Одного `id` мало — Manticore нумерует
   записи в каждом посуточном индексе своей чередой, — но записи с общим
   `id` заведомо из разных суток, и `ts` их разводит.
5. **Детектор всплесков строил норму по одной точке вместо ста
   шестидесяти восьми.** Почасовые частоты считались выражением
   `INTEGER(ts / 3600000)`, а `INTEGER()` в Manticore приводит к 32 битам —
   unix-миллисекунды в них не помещаются, и выражение молча возвращало
   НОЛЬ для каждой строки. Ошибка невидимая: запрос отрабатывает,
   группировка выполняется, просто все записи попадают в один и тот же
   час. Для baseline это означало норму, построенную по одной точке,
   и детектор, которому не с чем сравнивать. Найдено при проверке
   гистограммы на живых данных — на юнит-тестах SQL-выражение
   не исполняется. Исправлено на `IDIV(ts, N)`; `BIGINT()` тоже не годится
   — он считает через float и теряет точность, два разных времени дают
   один номер часа.
6. **Генератор слал спаны плоским списком.** Ни один спан не имел
   `parent_span_id`, поэтому проверки шли на данных, каких в бою не бывает:
   ни графа движения запроса, ни собственного времени сервиса по такому
   набору не построить. Теперь шаги заказа связываются в дерево.
7. **Детектор новых паттернов поднимал инциденты на штатных INFO.**
   Он брал любой fingerprint, которого не было раньше, независимо
   от уровня. На стенде это дало ленту, где из шести инцидентов подряд
   четыре — «payment confirmed by acquirer» (243 402 повтора), «order
   completed» (119 432), «payment requested» (122 587), — а настоящий
   `deadlock detected` лежал между ними. В проде каждый релиз с новыми
   сообщениями давал бы то же самое, плюс вызов ИИ на каждое. Ровно тот
   alert fatigue, против которого система и делалась. Добавлен фильтр
   уровней (`detectors.new_fp_levels`, по умолчанию только ошибки);
   проверено с обеих сторон — новые INFO инцидентов не поднимают,
   новый ERROR поднимает.
8. **Замеры по трассировкам считались по смещённой выборке.** Первая
   версия экрана тянула спаны в память и складывала их в Go. Выборка
   спанов при этом ограничена полусотней САМЫХ ДОЛГИХ — то есть «замеры»
   строились по одному хвосту распределения, а на экране выглядели
   правдоподобно: одна операция, медиана три секунды. Переписано
   на группировку в ClickHouse: 7 операций, по 150 тысяч вызовов каждая.
9. **`Latency()` падал на приведении типов.** `max(Duration)` приходит
   UInt64, квантили — Float64, драйвер не приводит: скан в `*float64`
   валит весь ответ. Функция была написана давно и не вызывалась ниоткуда,
   поэтому не падала. Первый же экран, которому она понадобилась, получил
   500.
10. **Чтение тела запроса мусорило втрое.** `io.ReadAll` начинает
   с 512 байт и удваивает буфер, копируя каждый раз всё прочитанное:
   для тела в полтора мегабайта это дюжина перевыделений. На профиле
   кучи чтение тел держало 58 МБ при бюджете приёма в 32 МБ — разница
   и была этим мусором. `Content-Length` штатные экспортёры присылают
   всегда, поэтому буфер выделяется сразу нужного размера.

Что проверено и оказалось в порядке:

| Что | Результат |
|---|---|
| Гонки данных | 34 пакета под детектором, 0 находок |
| Утечки горутин и памяти | под нагрузкой 1075 горутин / 1122 МБ → после 28 горутин / 75 МБ, очередь 0 |
| Границы дерева паттернов | карта секций растёт только вместе с кластерами, потолок `max_clusters` соблюдается |
| Учёт WAL | `pending` и `inflight` очищаются на всех путях, включая упавшую пачку |
| Пулы соединений | PostgreSQL и Manticore ограничены по числу и по времени жизни соединения |
| Таймеры и тикеры | все останавливаются, включая путь ошибки |
| Точность счёта принятого | накопитель сходится знак в знак, чужой уровень не теряется |

### Десятый заход: работа под заявленным потоком

Заход не про предел, а про заявленное: тысяча сервисов, 200 млн записей
логов в сутки, и при этом система обязана оставаться пригодной для
разбора — то есть отвечать на запросы, пока принимает.

**Поиск во время приёма занимал шесть секунд.**

Главная находка. Приём при этом работал безупречно: ноль потерь, куча
199 МБ, очередь 3 МБ. А поиск по логам отвечал 6.5 секунды при медиане
2 мс на пустой системе. Интерфейс в таком состоянии непригоден, и это
ровно тот случай, ради которого узел и ставится: разбираться надо
во время инцидента, а не после.

Причин оказалось две, и обе не в приёме.

1. **Запрос по уровню сканировал все уровни.** Логи разложены
   по посуточным индексам на уровень, но `level:ERROR` уходил в общий
   зонтик и прочитывал заодно все `info` и `dbg`. Запрос без
   полнотекстовой части Manticore исполняет полным сканом — индекса
   по атрибутам у него нет, — так что это буквально лишняя работа:
   434 тысячи нужных записей против 7 миллионов прочитанных. Разрыв
   растёт со временем, потому что `info` копится быстрее всех.
   Теперь набор индексов выбирается по уровню запроса.
2. **`max_matches` умножал стоимость каждого запроса.** Настройка
   выглядит безобидно — «сколько совпадений разрешено рассмотреть», —
   а на деле Manticore материализует до `max_matches` строк ЦЕЛИКОМ,
   со всеми колонками, включая `message` и `attrs`, и только потом
   сортирует и отдаёт запрошенные пятьдесят.

   ⚠️ Поймано на себе: готовя профиль под тысячу сервисов, я поднял
   `max_matches` с 5000 до 20000 — рассуждая, что «совпадений будет
   больше». Замер одного и того же запроса: 1000 → 526 мс,
   5000 → 1772 мс, 20000 → 5400 мс. То есть настройка, добавленная
   для масштаба, замедлила поиск втрое.

Итог: медиана поиска под приёмом **6.5 → 2.1 с**, p99 **9.4 → 5.1 с**.

**Токен по-русски принимался, но работать не мог.**

Найдено случайно, на собственном проверочном прогоне. Заголовок
`Authorization` переносит только печатный ASCII: клиент с кириллическим
токеном не может даже отправить запрос. Сервис при этом стартовал молча,
и со стороны это выглядело как «доступ не работает, токен же правильный».
Вся документация проекта по-русски, так что движение естественное.
Теперь — отказ на старте с объяснением; заодно закрыта подстановка
заголовков через перевод строки в токене.

**Дерево шаблонов упиралось в потолок вслепую.**

`max_clusters` по умолчанию 5000 — расчёт на десятки сервисов. При
исчерпании новые шаблоны перестают обобщаться, и ломается не приём,
а склейка инцидентов и привязка знания. Метрики на это не было вовсе.
Добавлены `watchgoose_fingerprint_clusters`, `..._max` и счётчик
`..._capped_total`; в профиле потолок поднят до 50 000.

**Генератор нагрузки врал про поток.**

Флот слал настолько быстро, насколько мог, — то есть любой замер под ним
был замером ПЕРЕГРУЗКИ, а выдавался за «столько-то записей в сутки».
Добавлен `--rate`; первая версия с общим счётчиком давала верную среднюю
скорость при рваном потоке (залпы по 10 000 зап/с и провалы в ноль),
поэтому переделана на независимый темп каждого отправителя с разбросом —
как у настоящих сервисов.

Что измерено под заявленным потоком:

| Что | Результат |
|---|---|
| Процессор, watchgoose | 0.21 ядра при 2 315 записей/с |
| Процессор, Manticore | 0.24 ядра |
| Память | куча 199 МБ, очередь 3 МБ |
| Потери | ноль |
| Аналитика одновременно с приёмом | 322 запроса, 0 сбоев |
| Предел одного узла | 8 000–15 000 записей/с (4–5 ядер) |
| Гонки данных | 22 пакета, 0 находок |

### Одиннадцатый заход: стек целиком, в контейнерах

Заход начался с законного вопроса: почему все прошлые замеры сняты
с бинарника под Windows, если в прод поедет контейнер. Ответ был плохой —
`docker-compose.yml` существовал, но целиком его никто ни разу
не запускал. Запустили — и он не поднялся.

**Три дефекта, которые видны только при настоящем запуске:**

1. **`docker compose up` падал целиком из-за необязательной части.**
   `node-exporter` монтирует корень хоста, чтобы видеть диски и память
   машины. На Docker Desktop такой монтаж невозможен в принципе:
   контейнеры живут в виртуальной машине. Стек не поднимался вообще
   с сообщением «path / is mounted on / but it is not a shared or slave
   mount». Вынесен в профиль `host-metrics`: на боевом Linux включается
   одним флагом, в остальных местах не мешает.

2. **VictoriaMetrics не стартовала никогда.** В `vm-aggr.yaml` агрегатор
   был записан как `quantiles`, а он требует параметров —
   `quantiles(0.5, 0.9, 0.99)`. VictoriaMetrics не игнорирует такое
   правило, а отказывается запускаться: контейнер перезапускался
   по кругу. Вместе с ним не работал `verify` — проверка, помогло ли
   принятое решение, то есть половина смысла накопления знания.

3. **Дисковая очередь коллектора не работала.** Named volume создаётся
   с владельцем root, а коллектор работает от uid 10001 и не может
   писать в собственную очередь. Проявлялось это не отказом приёма,
   а тем, что коллектор вообще не стартовал. Хуже другое: дисковая
   очередь — это и есть защита от потери логов, пока Watchgoose
   перезапускается. Молча работающий коллектор без неё был бы опаснее
   падающего. Добавлен разовый контейнер, выставляющий владельца.

Заодно порты хоста вынесены в переменные: 8080 занят на машинах чаще,
чем свободен, и упираться в это на первом запуске незачем.

**Замеры пришлось переснять, и они изменились в разы.**

| Что | Бинарник под Windows | Контейнер под Linux |
|---|---|---|
| Поиск по логам, медиана | 2.1 с | **104 мс** |
| Поиск по тексту, медиана | 2.5 с | **150 мс** |
| Худшая p99 по всем запросам | 5.7 с | **332 мс** |
| Запросов обслужено за тот же срок | 322 | **1 587** |
| Процессор watchgoose | 0.21 ядра | **0.14 ядра** |

Разрыв объясняется профилем: под Windows 43% процессорного времени
уходило на системные вызовы (`stdcall`), которых в Linux-сборке нет.
То есть прежние числа описывали платформу, а не систему.

⚠️ Отсюда правило, которое стоит соблюдать и вам: мерить надо в той
сборке, которая поедет в прод. Иначе получите характеристики своего
ноутбука.

Впервые в этом прогоне `/readyz` показал все четыре зависимости
работающими — ClickHouse и VictoriaMetrics в прежних стендах просто
отсутствовали, и вся связанная с ними функциональность (трейсы, холодный
слой, `verify`) не проверялась ни разу.

### Клиентские библиотеки: дефект, найденный на первом же прогоне

Вместе со стеком появились готовые клиенты под Go и C#
(группа `infrastructure-public`). На первом живом прогоне C#-версия
показала ровно ту
поломку, от которой библиотека должна защищать: логи «отправлялись»
без единой ошибки и не доезжали.

Причина — в правиле контейнера зависимостей .NET: он освобождает только
те объекты, которые создал сам. Провайдер, зарегистрированный готовым
экземпляром (`AddProvider(new ...)`), никогда не получает `Dispose`,
значит накопленная пачка не отправляется. Пропадают при этом последние
записи перед остановкой — те самые, ради которых в лог потом и полезут.

Исправлено регистрацией через фабрику; в документации подключение
описано именно тем способом, который работает.

### Двенадцатый заход: клиентские библиотеки под тем же увеличительным стеклом

Библиотеки написаны последними и проверялись меньше всего, поэтому
заход сосредоточен на них. Нашлось две штуки, и обе — повторение уже
известных ошибок, только в новом месте.

**1. Очередь ограничена числом записей, а не байтами.**

Ровно тот же дефект, который однажды чинили на стороне приёмника,
переехал в клиент. Десять тысяч мест в очереди при мегабайтных
стектрейсах — это десять гигабайт, то есть библиотека логирования
уронила бы чужой сервис по памяти раньше, чем это сделало бы то,
что он логирует.

Добавлены `QueueBytes` (64 МБ) и `BatchBytes` (8 МБ) в обеих
библиотеках; проверка по объёму идёт до проверки по числу мест.
Замер: сто записей по полмегабайта при потолке 4 МБ — 97 отброшено,
в очереди 3 МБ.

**2. Два одновременных `FlushAsync` в C# — один зависал навсегда.**

Обещание отправки было одно на всех: два вызова ставили флаг, отправщик
делал один сброс и отпускал семафор ОДИН раз. Второй ждал бесконечно.
Ошибка тихая — видна только когда сервис останавливается и не может
дождаться. Теперь у каждого вызова своё обещание; проверено восемью
одновременными вызовами.

**Разброс задержки поиска: разобрано, почему.**

Между прогонами поиск по логам замедлился со 104 до 865 мс, и это
стоило выяснить, а не списать на шум. Проверены и отвергнуты три
объяснения: фрагментация индексов (принудительное слияние не изменило
ничего), размер окна (пять минут против часа — разница на треть),
число посуточных индексов (один день идёт столько же, сколько зонтик).

Причина в объёме корзины: `logs_err` вырос с почти пустого до 284 тысяч
записей. Прямое следствие полного скана, которым Manticore исполняет
запрос без полнотекстовой части. В README теперь стоит диапазон
с объяснением, а не одно число.

Что проверено и оказалось в порядке:

| Что | Результат |
|---|---|
| Гонки данных | 23 пакета, 0 находок |
| Доступ без токена | 401 на всех путях, включая приём и pprof |
| Секреты в журнале | 0 |
| Контейнер | uid 10001, `no-new-privileges`, все capability сняты |
| Аналитика под нагрузкой | 494 запроса, 0 сбоев |
| Потери при приёме | 0 |
| Статика | gofmt, vet, staticcheck, сборка C# — чисто |

## Отличия реализации от плана

Три осознанных решения, где код разошёлся с текстом плана:

**Фронтенд без сборочного шага.** План предлагал SvelteKit + Tailwind ради
маленького бандла. Интерфейс написан на нативных веб-технологиях без фреймворка:
это даёт те же 30 КБ, ту же адаптивность и работу как Mini App, но убирает
`npm install` из пути сборки — образ собирается одним `go build`. Если фронтенд
вырастет за пределы семи экранов, SvelteKit имеет смысл вернуть.

**Миграции без `golang-migrate`.** Раннер на 60 строк с `embed.FS` вместо
зависимости: файлы в `migrations/` именуются в том же формате, применяются по
возрастанию, каждая в своей транзакции. Одним бинарником проще, чем бинарником
плюс библиотекой миграций.

**MCP-сервер написан свой,** а не взят готовой библиотекой. Протокол — это
JSON-RPC поверх HTTP; своя реализация на 300 строк дала полный контроль над
проверкой токенов ролей и фильтрацией инструментов по правам, без привязки
к чужому API, который в этой области ещё меняется.

Плюс требование к тулчейну: **Go 1.25+** вместо 1.23 — этого требуют актуальные
версии драйверов ClickHouse и MySQL.

## Лицензия и происхождение

**Watchgoose** — «следящий гусь», по аналогии с `watchdog`. Отсылка к
капитолийским гусям: когда сторожа спали, гуси подняли гогот и спасли Рим.
Ровно то, что делает система — замечает угрозу и будит.

## Версия

```
Watchgoose 0.1.0 · ae65c7f
```

Две записи, а не одна: **версия** отвечает на вопрос «что это за выпуск»,
**коммит** — «из чего именно собрано». Раньше в подвале стоял один короткий
хеш, и на первый вопрос он не отвечал.

Номер лежит в файле `VERSION` в корне и правится осознанно. Если на коммите
стоит тег — берётся он: тег и есть выпущенная версия.

```bash
make up                 # версия и коммит проставляются сами
./install.sh            # то же самое
```

Собираете compose напрямую — прокиньте их сами, иначе останется `dev`:

```bash
WATCHGOOSE_VERSION=$(cat VERSION) \
WATCHGOOSE_COMMIT=$(git rev-parse --short HEAD) \
docker compose up -d --build
```

Что запущено прямо сейчас, видно в подвале интерфейса и в `/healthz`:

```json
{"status":"ok","role":"all","version":"0.1.0","commit":"ae65c7f","uptime":"3h12m"}
```
