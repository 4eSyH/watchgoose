# Watchgoose

Хранилище логов, метрик и трассировок, которое **помнит, чем закончился
прошлый разбор**.

## Зачем это

Логи собирают почти все. Дальше они лежат мёртвым грузом: когда что-то ломается,
дежурный ищет причину с нуля — даже если ровно это уже разбирали полгода назад.
Знание о том, что тогда помогло, живёт в головах, чатах и закрытых тикетах,
и вместе с людьми уходит.

Watchgoose закрывает этот разрыв. Он не только принимает телеметрию, но и ведёт
базу разборов: что за паттерн, какая была причина, что применили и помогло ли.
При следующем срабатывании того же паттерна к событию **автоматически
прикладывается прошлая причина и статистика решений** — «помогло 7 из 9».

Дежурный получает не голый стектрейс, а стектрейс с историей.

## Для кого

Команды, у которых есть прод и дежурства, но нет отдельной команды
observability. Ставится одной командой, работает на одной машине,
не требует ни Kubernetes, ни выделенного человека на поддержку.

## Что важно понимать сразу

- **Это не замена Grafana.** Пороги на метриках и графики остаются там.
  Watchgoose ловит другое: новый паттерн в логах, всплеск относительно
  собственной нормы, обрыв цепочки событий, нарушение правил о бизнес-данных.
- **ИИ внутри нет.** Ключей моделей и вызовов к ним внутри нет: система готовит
  контекст и отдаёт его наружу, а разбор делает внешний агент или человек.
  Данные не покидают периметр, модель может быть любой, включая локальную.
- **Действий не выполняет.** Эндпоинта «сделать» в API нет. Решение применяет
  человек или существующая автоматика — система записывает факт применения
  и результат проверки.

## Как устроено

Watchgoose принимает телеметрию по OTLP, раскладывает её по специализированным
хранилищам и ведёт базу разборов инцидентов в PostgreSQL.

### Ключевые принципы

- **Разделение хранения.** Логи, трассировки и метрики лежат в разных системах,
  подобранных под свою нагрузку; разборы инцидентов — в PostgreSQL.
- **Детекторы на SQL.** Шесть детекторов ищут аномалии обычными запросами;
  фильтр решает, стоит ли событие внимания и сколько контекста к нему приложить.
- **ИИ снаружи.** Ключей моделей внутри нет, вызовов к ним нет. Данные
  не покидают периметр, модель может быть любой, включая локальную.
- **Решение за человеком.** Эндпоинта «выполнить действие» в API нет,
  инструментов действия в MCP нет. Применяет решение человек или существующая
  автоматика — система записывает факт применения и результат проверки.

## Архитектура

### Хранилища

| Данные | Система | Примечание |
| --- | --- | --- |
| Логи | Manticore | посуточные индексы, ротация по бюджету |
| Трассировки | ClickHouse | |
| Метрики | VictoriaMetrics | |
| Разборы, причины, статистика | PostgreSQL | том `pg_data` |
| Архив суток | S3 | батчи закрыты шифрованием |

### Как проходит событие

1. Детектор находит аномалию SQL-запросом к хранилищу.
2. Фильтр определяет, нужен ли внешний разбор и какой объём контекста приложить.
3. Отобранное уходит наружу вебхуком.
4. Внешний агент или оператор возвращает результат разбора через MCP.
5. Результат сохраняется и переиспользуется при следующем срабатывании.

### Накопление знания

При повторном срабатывании того же паттерна к событию прикладывается ранее
записанная причина и статистика применённых решений — «помогло N из M».

Внутри нет ни модели, ни обучения: есть таблица разборов и запросы к ней.

## Установка

```bash
curl -fsSL https://raw.githubusercontent.com/4eSyH/watchgoose/main/install.sh -o install.sh
bash install.sh
```

### Что делает установщик

- Проверяет окружение и **ставит недостающее**: `docker`, `docker compose v2`,
  `openssl`. Пакетный менеджер определяет сам.
- Скачивает файлы развёртывания и сборку под архитектуру машины.
- **Сверяет sha256** скачанной сборки.
- Собирает образ локально и поднимает стек.
- Генерирует `.env` с паролями и ключами, права `600`.

### Требования

- Linux, ~4 ГБ ОЗУ, диск под выбранный бюджет хранения
- Порты **80** и **443** открыты снаружи — по 80 проверяется владение доменом
- Порты **4317** и **4318** открыты снаружи, если телеметрию шлют с других машин
- Запись DNS домена указывает на этот сервер
- Пользователь с правами `sudo`
- Бакет S3 создан заранее — установщик его не создаёт, но доступ проверит

### О чём спросит

- Домен и режим сертификата: `letsencrypt`, свой сертификат или без шифрования
- Бюджет места на всё вместе
- Параметры S3: адрес, бакет, регион, ключи

Пароли к хранилищам, токен приёма и ключ шифрования архива генерируются сами.

### Что нельзя потерять

> **Токен администратора** показывается один раз. В базе лежит только его хэш,
> показать повторно невозможно.
>
> **`ARCHIVE_ENCRYPTION_KEY`** не хранится нигде, кроме вашего `.env`. Батчи
> уезжают в S3 уже закрытыми, ключ выводится из парольной фразы и рядом
> с данными не лежит. Потеряете — архив не прочитать ничем.

### Проверка

```bash
curl -s https://ДОМЕН/healthz    # версия и коммит сборки
curl -s https://ДОМЕН/readyz     # состояние четырёх хранилищ
```

В режиме без шифрования интерфейс наружу не смотрит — проверять с самого
сервера: `http://localhost:8080/healthz`.

## Приём телеметрии

Приложения отправляют данные **в коллектор**, а не в Watchgoose напрямую.

Адрес зависит от того, откуда шлют.

| Откуда | OTLP / gRPC | OTLP / HTTP |
| --- | --- | --- |
| С другой машины | `ДОМЕН:4317` | `https://ДОМЕН:4318` |
| С самого сервера | `localhost:14317` | `http://localhost:14318` |
| Из контейнера стека | `otel-collector:4317` | `http://otel-collector:4318` |

**Снаружи приём открыт только с сертификатом.** Порты 4317 и 4318 на хосте
держит Caddy, а он поднимается профилем `tls` — установщик добавляет профиль
при `letsencrypt` и своём сертификате. В режиме без шифрования Caddy
не запускается и наружу не открыт ни один порт — ни приёма, ни интерфейса:
остаются только адреса на `localhost`, доступные с самого сервера.

**Обращаться нужно по имени домена, не по IP.** Блоки приёма в Caddyfile
привязаны к `WG_DOMAIN`; запрос на адрес сервера в них не попадёт.

### Аутентификация

Заголовок `Authorization: Bearer <токен>`, значение — `INGEST_TOKEN` из `.env`.
Токен нужен на обоих протоколах и одинаково для логов, трассировок и метрик:
все три конвейера коллектора слушают один приёмник. Запрос без заголовка
получит 401.

**Токен один на все приложения.** Коллектор сравнивает предъявленный токен
с единственным настроенным значением и в Watchgoose про каждый не ходит.
Второй выпущенный токен роли `ingest` он отвергнет с 401, хотя в базе тот
будет числиться живым.

### Роли

Роль `ingest` умеет ровно одно — принимать телеметрию. Читать логи, инциденты
или выпускать токены ей нельзя: утечка означает мусор в данных, но не доступ
к ним.

## Обновление

```bash
bash install.sh --update              # до последней версии
bash install.sh --update --tag=1.1.0  # до конкретной версии
```

### Поведение

- Вопросов не задаёт — берёт конфигурацию из `.env`.
- Обновляет файлы развёртывания. Изменённые сохраняются рядом с меткой времени,
  чтобы правку, сделанную руками на сервере, можно было вернуть.
- Пересобирает образ и перезапускает только Watchgoose.

### Версия закрепляется сама

Вписывать номер руками не нужно. После закачки установщик спрашивает у сборки
её версию и записывает в `.env`:

```
WATCHGOOSE_TAG=1.0.1
```

Дальше машина остаётся на этой версии столько, сколько нужно. Реестра в схеме
нет, образ собран локально — поэтому ни `docker compose up -d`, ни перезагрузка
сервера версию не меняют.

Сойти с неё можно только явной командой. `--update` без `--tag` берёт последний
выпуск и закрепляет уже его; `--tag=1.0.0` ставит названную версию, в том числе
чтобы откатиться назад.

## Резервное копирование

В PostgreSQL лежат разборы инцидентов, известные причины и статистика решений.
Логи, трассировки и метрики восстановимы из архива, а это — нет: копится годами
и не воспроизводится ничем.

### Копия базы снимается сама

Раз в неделю, в понедельник в 04:00, в тот же бакет S3, что и суточные батчи.
Зашифрована тем же ключом: внутри дампа хэши токенов доступа, открытым текстом
ему в хранилище не место.

Держатся **последние четыре копии** — месяц глубины. Появилась пятая, самая
старая удаляется.

```bash
docker compose exec watchgoose /watchgoose --pg-backups
```

Список читается **без ключа шифрования** — заголовок каждой копии лежит
открытым ровно затем, чтобы этот список работал, когда система не поднимается
и ключ остался в переменной окружения умершего контейнера.

### Восстановление

Сначала посмотреть, ничего не трогая:

```bash
/watchgoose --pg-restore=2026-W35 --pg-restore-out=/tmp/wg.dump
pg_restore --clean --if-exists --no-owner -d "$POSTGRES_DSN" /tmp/wg.dump
```

Или под ключ — **снесёт содержимое указанной базы**, поэтому требует `--confirm`:

```bash
/watchgoose --pg-restore=latest --pg-restore-into="$POSTGRES_DSN" --confirm
```

Проверить, что копия вообще разворачивается, не трогая боевую базу:

```bash
/watchgoose --pg-restore-check=latest
```

### Что всё равно на вас

**Файл `.env`.** Без `ARCHIVE_ENCRYPTION_KEY` не открыть ни архив, ни копию базы.
Держите его в хранилище секретов, отдельно от сервера: копия, к которой потерян
ключ, — это занятое место, а не резерв.

**Учение раз в квартал.** Копия, которую ни разу не разворачивали, — предположение,
а не резерв. `--pg-restore-check` делает это за минуту.

**Отдельный токен роли `viewer`** для повседневного просмотра: администраторским
ходить каждый день незачем.
